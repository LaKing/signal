# The control library

The web-component controls of ADR 0023 §3 (M2.8-2). They are in the repository's `ui/` folder as plain ES modules, with no dependencies and no build step. `signal ui` serves them at `/ui/` (`docs/ui-protocol.md`).

| File | Holds |
|---|---|
| `ui/signal-ui.js` | The protocol client: `connect`, `connectFromPage`, `Connection` (describe, subscribe, set, ramp, trigger, commit, retry, revert, reconnect; the host's unsaved state as `connection.unsaved` and the `unsaved` event), the default connection the controls use |
| `ui/controls/index.js` | Defines every element below and `<signal-panel>` (import it once) |
| `ui/controls/panel.js` | `<signal-panel>`, the loader of a project panel ("Panels") |
| `ui/controls/schematic.js` | `<signal-schematic>`, the project's signal path as an infinite-zoom SVG schematic ("Schematic") |
| `ui/controls/slot.js`, `ui/controls/slot-dialogs.js`, `ui/lib/slot.js` | `<signal-slot>`, a slot's card; the schematic's slot dialogs; their logic ("Slots", ADR 0037) |
| `ui/schematic.html` | The schematic's page in `signal ui` (`/schematic`) |
| `ui/default-panel.html` | The generated panel of a project without `ui/main.html` |
| `ui/controls/theme.css` | The theme's custom properties and their dark defaults |
| `ui/lib/` | Pure logic with `node --test` tests: `taper.js`, `gesture.js`, `ballistics.js`, `trigger.js`, `skin.js`, `format.js`, `panel.js` (the default panel, diagnostics); `entry.js` (typed values, M2.9-4; its field is `ui/controls/entry-field.js`); `protocol.js` (M2.8-1); the schematic's `schematic-view.js`, `schematic-layout.js`, `schematic-scene.js`, `schematic-hit.js`, `schematic-inspector.js`, `schematic-levels.js` (M2.9-1); the pattern controls' `pattern-text.js`, `piano-roll-model.js`, `step-grid-model.js`, `pattern-sync.js`, `playhead.js` (M2.11-3) |
| `ui/fake-connection.js` | A connection without an engine, for the gallery |
| `ui/gallery.html` | Every control in every mode |
| `ui/assets/` | The gallery's skins; `scripts/ui-strip.mjs` draws its PNGs (`pulse`: the pulse panel's strip) |

## Using them

```html
<link rel="stylesheet" href="/ui/controls/theme.css">
<signal-knob bind="/drums.kick_decay" taper="log" label="decay"></signal-knob>
<script type="module">
  import '/ui/controls/index.js';
  import { connectFromPage, setDefaultConnection } from '/ui/signal-ui.js';
  setDefaultConnection(connectFromPage());
</script>
```

A control uses the default connection (`setDefaultConnection`), or the one given to `element.useConnection(connection)`. From the connection's `describe` it takes the parameter's range, default, unit and base value; the attributes `min`, `max`, `default`, `unit` override them, and without a connection or a `bind` the control works on those attributes alone.

**Edits.** A drag sends a `ramp` (5 ms) per move and a `commit` on release. Keys and the wheel send a live `set` per step and one `commit` 500 ms after the last one; a pending commit is also sent when the control loses focus, leaves the page, or the page is hidden or closed (`pagehide`, `visibilitychange`). A reset (double-click, Delete) commits at once. A typed value ("Value entry") is sent as a release is: a 5 ms `ramp`, then a `commit`. Live edits (`set`, `ramp`) the server refuses are not reported in the console; the next parameter frame shows the value the runner has. **A commit is never dropped silently** (`Binding` in `ui/lib/binding.js`): its refusal is shown on the control ("Unsaved", below). Base and effective values come from a `parameters` subscription (30 per second).

**Unsaved.** The host knows which parameters' live values the file does not hold (`docs/ui-protocol.md` "Unsaved"), and every client shows what it says, so a second window or a reloaded page shows the same. A control whose write failed — on the host (`write-failed` from a read-only folder, for example), or a commit lost with its connection — gets the **unsaved mark**: the `unsaved` attribute (a dashed amber outline, `--signal-unsaved`), the error text (`role="alert"`) and two buttons, **Retry** (`retry`: write the live value again) and **Revert** (`revert`: the live value back to the file's). The mark stays until a write or revert is confirmed or the host no longer lists the parameter. An edit that is only in progress (a drag, a key step before its commit) is listed by the host but gets no mark: only a refused write does. A failed reset of a key the file does not set leaves nothing unsaved (the ports and the file both use the default), so its error mark clears on the next host push. `<signal-value>` writes only a typed value, and shows the mark like the others. The project-level indicator, **"N unsaved parameters — last error"** with **Retry all** and **Revert all**, is in `<signal-panel>`'s bar (so in the default panel and in every project panel), in Signal.app's window (above its messages) and on the raw protocol test page at `/` (`ui/index.html`, below its status line; M2.8-9); it counts every listed parameter, edits in progress included, and is not shown when there are none (its space is kept: "Stable layout"). Signal.app's parameter list shows each row's error with its own Retry and Revert, and Save (Signal.app's File menu, or Cmd-S on its page in a browser) retries every unsaved parameter and says "saved" or what was not, then writes a `.signal` project back to its file (M2.8-12).

**The client.** `Connection` says `hello`, asks `describe` when welcomed, and keeps its subscriptions across reconnects (backoff 0.25, 0.5, 1, 2, then 5 s; the new `sub` ids are mapped). A request that is outstanding when the connection drops, or made while it is down, is rejected with `code: 'closed'` and never sent again: a repeated `commit` or `trigger` would act twice. After close code 1008 (unauthorized, for example a server restarted with a new token) or 1002 (protocol) it stops, with status `failed`. A listener that throws is reported (`reportError`) and the others still get the event (M2.8-11: a throwing meter once kept Signal.app's parameter list from every `describe` while playing). While Signal.app is switched off (`power: "off"` in `welcome` or `app`, `docs/ui-protocol.md` "Signal.app") it sends no subscription and lets go of those it has; switched on, it sends them again.

## Elements

Common to all:
- `bind`: the port address (a control or plan parameter port; an event input for `<signal-button>`; signal outputs or inputs for `<signal-scope>`). In a project panel, the controls that edit (fader, knob, toggle, 2D pad) bind controls, which a release commits ("Panels").
- `skin` (below) and `label`.
- Focusable (`tabindex="0"`), a focus ring (`--signal-focus`) on keyboard focus, an ARIA role, pointer events with pointer capture (mouse, pen and touch; `touch-action: none`).

The pattern controls (M2.11-3, ADR 0028 §2 and §7) edit pattern text, not a parameter: `.value` is the pattern object, `.text` its file text (`ui/lib/pattern-text.js`: parsed and written deterministically, notes sorted by (start, key), a lane's level in a `[levels]` table), and a `change` event (`detail`: the pattern) follows every edit. Their models are `ui/lib/piano-roll-model.js` and `ui/lib/step-grid-model.js` (geometry, snap, hit-testing, the edits, a local undo: ⌘Z / ⇧⌘Z). With `pattern="<name>"` and a connection offering `readPattern(name)` and `writePattern(name, text, base)` (`ui/lib/pattern-sync.js`, over `pattern.read` and `pattern.write`), a control loads the file on connect and writes each edit, debounced, on the last base; on `conflict` it reads the file again and keeps the edit only when the file still means what the edit started from (after 3 conflicts in a row it stops until the next edit). Nothing can be edited until the first read arrives; a reload ends a drag or paint stroke in progress; disconnecting still writes what is pending. Notes overlap by one strict float rule, shared with the server: on one key, `a.start + a.length > b.start` for `a` starting first; touching notes do not overlap, and a trimmed note is shortened until it ends at or before the next. A control reads its file once the connection is open (after the server's `welcome`) and again after a reconnect, sending again a write the drop refused. When another client writes the pattern, the server's `pattern.written` push shows that text at once in an idle control (nothing pending, no write in flight); with an edit pending, that edit's write meets it as a conflict. A file changed on disk by another program is not pushed: it shows on the next conflict or connect. The toolbar shows a notice in a short form (`changed elsewhere — reloaded`, `not written — edit again to retry`), the full text as its title and in its `role=status` element (`shortNotice`, `ui/lib/pattern-sync.js`).

**Playheads.** `position-bind` (piano roll) and `step-bind` (step grid) name a signal output of the plan, a sequencer's `position` or `step` (`std.note_seq`, `std.step_seq8`); the control sets its `position` or `step` from it, once per display frame, and writes nothing (`ui/lib/playhead.js`). The output is read through a `scope` stream (`docs/ui-protocol.md`) at 7680 points per second, a 256-point block every 1/30 s, showing each block's newest point; so a playhead takes one of the run's 8 scope slots, and a refused slot is asked for again every 2 s, as a `<signal-scope>`'s is. `signal ui check` and `panel.check` require a signal output there (an error at the attribute's value otherwise); it counts as a binding.

**Playing the keys** (ADR 0039, the owner's "could the piano keys be pressable?"). A press on the piano roll's keyboard strip sounds that key on the instrument its sequencer drives, while the pointer is held (captured: a release anywhere ends it): the UI protocol's `note` (`docs/ui-protocol.md`) to an event input, on at the press and off at the release, a pointer cancel or a lost capture, the control leaving the page, or its connection changing. The key is lit (amber) while held. Sliding over the keys moves the note: the new key first, then the old one's off, so the voice goes on legato (the sequencer takes over from the held note and ignores the off of a key it no longer holds). **Velocity** from where the key is pressed: 0.3 at its far end (the left) to 1 at its tip, along the key's own length (a black key's is shorter), sent in 127 steps (rather than a fixed velocity: the sequencer's `velocity` output already drives the voice in the studios, so the press is heard as played). **The target**: the `audition` attribute (an input named `audition`, or `none`); without it, the `audition` input of the sequencer whose `position` the roll's `position-bind` follows (`/melody.position` → `/melody.audition`) when it has one, else, when the project has exactly one `std.note_seq`, its `audition`; else none (`ui/lib/audition.js`, `auditionTarget`; hit-testing `keyAt`). `signal ui check` and `panel.check` require an event input named `audition` there when it is given (the server refuses a `note` anywhere else). A note off the server refuses (the Controller's queue full) is sent once more 100 ms later unless the key is held again; the server also keeps it held for the page and ends it when the page goes. With no target, no connection, or nothing playing, a press only lights the key, and a refused note is not shown (no error per press). Nothing is written: a note is a live performance input, recorded in a session as the `set` it is (`session-format.md`). The sequencer merges it into its voice: while held it takes the voice from the pattern (a pattern note starting on the frame of the release plays, on time) (`std.note_seq`, "Audition", `module-contract.md`). The wheel and keyboard rules (ADR 0034) are unchanged: a press on the keys focuses the roll as any press on it does.

The fader and knob show the effective value when it differs from the base (a modulated parameter): an amber mark on the fader, a dot on the knob's arc, and `→ value` on the readout's second line (there, empty, when not modulated) and in `aria-valuetext`.

The meter uses the M2.5-1 ballistics (`crates/signal-app/src/meter.rs`) ported line for line to `ui/lib/ballistics.js`: a 1.5 s peak hold, a 300 ms RMS, and a clip indicator latched at a peak of 1.0 until cleared. A protocol meter frame carries each channel's peak and RMS over `extra` frames, so its block's sum of squares is `rms² · frames`.

The canvas is described under "Canvas" below.

The scope shows the subscribed points from the first crossing of the trigger level on the trigger edge that leaves a full display after it (half of the last two consecutive blocks, at most 256 points), else from the start (free running). X–Y pairs the points of the latest block of each port that fall on the same frames.

### Keys and the wheel

Every shortcut is a command of one keymap (ADR 0034): `ui/lib/keys.default.js` built in, the person's `keys.toml` beside the Setup for overrides, edited in Signal ▸ Settings… (⌘,) and listed in Help ▸ Keyboard Shortcuts (⌘/). The table gives the built-in chords; a control looks its commands up (`keyCommand(scope, event)`, `wheelCommand`, `ui/lib/keys.js`) and never compares `event.key` itself. Shift makes every step fine (×0.1) where the command is marked fine.

**Precedence.** An open text field keeps every key; then the focused control (its scope); then the view; then the project (ADR 0039: Space plays and stops the transport, below); then the app's menu (inside Signal.app the native menu takes each menu command's first chord, and the page hands it the others: `menu.run`, wry's IPC, once per press; in a browser the page runs the ones it can). In a text field, Cmd and Ctrl chords still reach the app's commands (the field commits a changed text first, "Value entry"). A menu command's chord needs Cmd, Ctrl or Alt, or is a function key. What a focused control does not take reaches the page (`ui/controls/keyboard.js`): **Page Up, Page Down, Home, End, ⌘↑, ⌘↓, ↑ and ↓ scroll the view**, the scrolling box around the focus, else the page's view (in Signal.app the shown tab or the panel frame). A focused slider keeps Page Up and Page Down for large steps (ARIA), a focused piano roll scrolls its keys with them, the schematic pans.

**Space plays and stops the project's transport** (ADR 0039, `transport.toggle`, scope `project`), on every page with a connection: Signal.app's main window and its tabs, its panel windows and frames, the schematic window, and `signal ui` in a browser. It is not the power switch nor the run (`transport.play` and `transport.stop` stop the audio): it is the `run` of the project's `std.playhead` instances, through the top-level controls whose plan ports reach one (studio-transport's `/transport.run`; an include's transport is a control too) and that no connection drives (`modulated`), picked from `describe` (`ui/lib/transport-toggle.js`). Several are toggled together: if any runs (its base at least 0.5), all stop, else all play. Each is written as a click on its `<signal-toggle>` writes it (`commit`: live, then `project.toml`), so the unsaved marks and every other client see the same. Nothing to toggle, nothing playing or no connection: nothing happens, silently. A focused button, toggle, step grid, meter or scope keeps its Space, as do a native button or link, an open menu and a text field; a focused fader, knob, 2D pad, value, piano roll or schematic has no Space of its own, so there it plays and stops too. Space and Shift+Space no longer scroll the page (Page Up and Page Down do); a person who wants them back binds them in Settings, which says that Space on the view hides the transport there. It is a page command, not a menu item: a bare key in the native menu would be taken from every text field (ADR 0034 §12).

**The wheel scrolls the page.** A control that scrolls, zooms or changes a value with the wheel (fader, knob, the piano roll, the step grid's level knobs, the schematic) takes it only when it **owns** it: once clicked or focused (until the focus leaves it or **Escape**), while **⌥** is held (`view.wheel_inside`; the modifier only takes the wheel and is left out of the control's own wheel chords), or when it fills its window (the schematic in its tab or window; `wheel="own"` forces it, `wheel="page"` never). A gesture is decided by its first event, over the whole control (`registerWheel(this)`), and goes on where it started: scrolling the page over a focused piano roll keeps scrolling the page, and a gesture a control took never scrolls the page, wherever the pointer goes, also over a part of the control without a wheel use (the piano roll's scrollbars, the step grid's cells). The value and the zoom follow the vertical travel only (a sideways trackpad swipe changes nothing; Shift+wheel's horizontal delta counts). When a gesture starts over a control that does not take it, a one-line hint by the pointer says "Click to use the wheel here, or hold ⌥" (fixed-position, no layout change; once per gesture, and not while the page is being scrolled: none within a second of a gesture of the page's). `wheel` is a panel attribute of the fader, knob, piano roll and step grid (`ui/lib/panel-whitelist.json`). In a control: `registerWheel(this)` once, and in its wheel listener `if (!takesWheel(this, event)) return;` before `preventDefault()`.

The meter, scope and value send nothing to the engine with these keys; they change what they show (and the meter's clip latch). The travel is the control's taper ("Tapers"): a step of 1 % is 1 % of the position, so on a `log` taper it is a constant ratio and on a `db` taper a constant number of dB. Each step is a live `set`; the file is written once, as one release, 500 ms after the last key.

## Value entry

A value can be typed (M2.9-4) on `<signal-fader>`, `<signal-knob>`, `<signal-value>` and `<signal-xy>` (x and y are two fields, side by side in its readout; a press on the readout does not move the puck; Tab from x commits it and opens y), on `<signal-scope>`'s trigger level (in time mode; −1..1, kept as typed, a clamp's reason in the scope's tooltip; nothing is written to a file, as with its keys), in the base cell of every editable row of Signal.app's Parameters tab, on the base readout of the editable rows of the schematic's inspector card, on a wire's scale in the schematic's Edit patch, and on min and max in the panel editor's inspector. `<signal-button>` and `<signal-toggle>` take nothing to type. The pure part is `ui/lib/entry.js` (`parseValue`, `entryText`, `clampEntry`, the field's states `EntryField`, the double-click `ClickPair`, `parseNumber`), the field `ui/controls/entry-field.js`.

- **Opening.** Double-click the readout (on a knob or fader, its value text; elsewhere on the control a double-click still resets), or press Enter while the control (in the Parameters tab and the inspector: the slider) has the keyboard focus. The field opens on the second release.
- **The double-click is told from the presses** (2026-10-22, the owner's "double-clicking a number should let you type it"): two presses of the left button at most `DOUBLE_CLICK_MS` (500 ms) and `DOUBLE_CLICK_PX` (6 px) apart (`ClickPair`), not only the browser's `dblclick`, whose target under a captured pointer (a fader or knob captures it on a press) is the browser's to choose. The browser's `dblclick` that follows such a pair does nothing more; one that comes without presses (a script, an assistive tool) still types on the readout and resets elsewhere. A double-click's second press never drags, and a press on a fader's or knob's readout drags only once it has moved `READOUT_SLACK_PX` (4 px), so a double-click on the value text never moves or writes the value before its field opens (it did, by a hand's jitter: measured in WebKit, a 3 px slip moved the tempo from 130.5 to 128.7 bpm and wrote it). A drag that starts on the readout still works past those pixels. A text field covers exactly the readout's box (`position: absolute` over it, out of the flow): nothing else moves or resizes ("Stable layout"). It holds the base value in full precision, the shortest text that reads back to the same number, with the parameter's unit (`440 Hz`, `0.3333333333333333`), selected.
- **Committing.** Enter or Tab commits: the value is sent live as a drag's release is (a 5 ms `ramp`), then written to the file with `commit`, so the unsaved mark, Retry, Revert and Reset work as for a drag. Enter or Tab on an unchanged text cancels (nothing is sent or written, so opening a field only to read the full value never writes the file; a held Enter's repeats do nothing). Escape cancels; a click elsewhere cancels when the text was not changed and commits when it was. Cmd or Ctrl shortcuts (Save, Open, …) reach the page: a changed text is committed first.
- **Out of range.** The value is clamped to the range and sent; however it was committed (Enter, Tab or a click elsewhere), the field shows the clamped value, read-only, for 2 s (Enter or Escape on it closes it sooner), and the reason (`Clamped to the maximum, 20.00 kHz`) is shown for 2 s in the control's message place: on a panel control the box of the unsaved mark (over what is below it, without Retry and Revert), in the Parameters tab the row's `not in file` cell (cut, the whole reason as its tooltip), in the schematic its message line.
- **Invalid text** keeps the field open while it has the focus, its border red (`aria-invalid`), with the reason as its tooltip; nothing is sent. Editing the text clears the mark; a click elsewhere lets it go (the field never stays open without the focus).
- **Off.** A control inside an element with the `no-entry` attribute (or with it itself) takes no typed value: a double-click on its readout resets, as elsewhere, and Enter does nothing. The panel editor (M2.9-2) sets it in edit mode. A `<signal-value>` bound to a plan parameter that is not a control takes none either (`commit` would refuse it).

**Accepted text** (`parseValue(text, {unit, range, taper})`, returning `{value}` or `{error, reason}`):
- A number: an optional `+` or `-` (or the minus sign `−`, U+2212, as Signal prints it), digits with a decimal dot or comma (`0,5`; there is no thousands separator, so `1,000` is 1), an optional exponent (`1e3`, `2.5E-2`).
- **Every other number typed in the UI** reads the decimal comma and dot alike (`parseNumber`, `parseValue` without a unit): the piano roll's loop length (`8,5` as `8.5`, then snapped to whole beats; ↑↓ step by one) and Signal.app's Setup buffer and CPU workers (whole numbers: `256,0` is 256, `4,5` workers is refused). They are text fields, not `type="number"`, whose WebKit version drops a decimal comma.
- After it, case-insensitively, a form of the parameter's unit: `Hz` also as `kHz`; `ms` also as `s` (×1000), `s` also as `ms`; any other unit (`dB`, `st`, `ct`, `bpm`, …) as itself only, so `st` and `ct` only where the unit is that. `dB` on a linear gain, a parameter without a unit whose plan `kind` in `describe` is `gain` (a control's: its first plan port's), or one shown on a `db` taper, whatever the control: `-6 dB` is 10^(−6/20). `%` where the range is within 0..1 (`50%` is 0.5).
- Or an SI prefix, case-sensitive, `k` (×1000), `m` (×0.001) or `M` (×10⁶), alone (in the parameter's unit: `1.2k`, `500m`) or before a unit form (`1 MHz`). A unit form is read first, so `1ms` and `1MS` are a millisecond, `1M` a million, `1m` a thousandth; `K` is no prefix, and no prefix goes before `%` or `dB`.
- `-inf` or `-∞` (with or without `dB`) is the minimum of a dB taper, of a parameter in dB, and of a linear gain whose range starts at 0.
- Refused, each with its reason: nothing typed (`empty`), no number (`not-a-number`), a unit or anything else after the number that does not fit the parameter (`unit`: `"ms" does not fit a parameter in Hz`), and a value that is not finite (`not-finite`: `1e400`, `inf`, `-inf` where it is none of those).

## Tapers

A position is 0..1 along the travel (`ui/lib/taper.js`):
- `linear`: proportional.
- `log`: geometric from `min` to `max`; needs `0 < min < max`, otherwise linear.
- `db`: positions above 0 are linear in dB from the floor (`floor`, default −60 dB, or `min` in dB if higher) to `max` in dB; position 0 is `min`. Values at or below the floor's value map to position 0 and back to `min`, so value → position → value round-trips only above the floor.

## Skins

`skin="svg:<url>"` uses an SVG whose named parts (`data-part="…"` or `id`) the control moves:

| Part | Moved by | How |
|---|---|---|
| `pointer` | knob | rotated by the knob's angle (0 at 12 o'clock) about `data-cx`, `data-cy` (default: the view box's centre); draw it pointing up |
| `thumb` | fader | moved `data-travel` units: up from the bottom (`data-axis="y"`, default; draw it at the top) or right (`data-axis="x"`; draw it at the left) |
| `puck` | 2D pad | moved `data-travel-x` right by X and `data-travel-y` up from the bottom by Y |
| `on`, `off` | button, toggle | shown when on, off |
| `value` | fader, knob | its text is the formatted value |

Before it is used the SVG is sanitized (`ui/lib/skin.js`, conservatively: what it cannot read as local is dropped):
- `script`, `foreignObject`, `iframe`, `object`, `embed`, `audio`, `video` and the animation elements are removed;
- every `on…` attribute and `xml:base` are removed;
- `href`, `xlink:href` and `src` stay only when they are a fragment (`#id`) or a path on the same host: a reference with a control character (a URL parser drops tabs and newlines, so `java⇥script:` is `javascript:`), a backslash, a scheme or a host is removed;
- `<style>`, `style` and any other attribute holding `url(` (`fill`, `filter`, `mask`, `clip-path` …): comments go, CSS with an escape or control character (`u\72l(` spells `url(`) or with `image-set(`/`src(` is dropped whole, `@import` rules go, and `url()`s other than same-host ones become `none`.

So a skin cannot run code or load anything from another host.

`skin="strip:<url>;frames=N"` uses a PNG filmstrip or sprite sheet, one frame per position (rounded):
- `orientation=vertical|horizontal`: frames top to bottom or left to right; by default vertical when the image is at least as tall as it is wide.
- `columns=C`: a sprite sheet, frames row by row.
- Retina: a name ending in `@2x` is a double-resolution image (shown at half its pixel size; `scale=S` for another scale), and `2x=<url>` names a double-resolution copy of a 1x image (CSS `image-set`). URLs are used as written: the server refuses `%`, so names are never percent-encoded (`knob@2x.png` stays `knob@2x.png`).

URLs are relative to the page. A skin that does not load falls back to the built-in drawing with a `console.info` line.

## Canvas

`<signal-canvas>` (M2.8-7, ADR 0023 §5) draws the state of a visual-rate model, streamed as vector frames (`ui-protocol.md`, the `vector` stream, frame kind 4): one subscription per bound port, the latest snapshot drawn at the next animation frame. It simulates nothing: the engine's modules (`std.particles`, `std.mesh2d`, `std.body2d`) are the model, so a replay of a recorded session draws the same.

| `renderer` | Binds | Draws |
|---|---|---|
| `points` | a positions vector (x, y pairs), optionally a life vector (0 dead) | each live particle: a dot sized and faded by its life, or a skin's frame |
| `mesh` | a displacement vector of `grid` × `grid` nodes | a slanted wire grid (depth foreshortened by `tilt`, displacement times `height`) |
| `bodies` | a bodies vector (x, y, size, kind per body) | the box [−1, 1]² and each body: a circle (size its radius) or a box (size its half-width), or a skin stretched over it |

The world is the box [−1, 1]², y up, fitted to the canvas with its aspect kept (`fitBox`). **Backends.** With `backend="auto"` (the default) an unskinned `points` or `mesh` canvas draws with WebGL when the browser gives a context (`ui/canvas/gl.js`: round point sprites, line pairs), and everything else with Canvas 2D; `2d` forces Canvas 2D. **Skins** are the controls' (`strip:…` and `svg:…`, "Skins"), loaded as images and drawn with `drawImage`, never inserted: for `points`, the frame of a sprite sheet is chosen by the particle's age (`spriteFrame`: the frames spread evenly over its life); for `bodies`, frame 0 for circles and the last for boxes, or the SVG over every body. The spark sheet (`ui/assets/spark-strip.png`, `projects/physical-av/ui/assets/spark.png`: 8 frames of 32 × 32 in a row, a glow cooling and shrinking with age) is drawn by `node scripts/ui-strip.mjs sparks`; `ui/assets/body.svg` is a shaded disc.

The pure parts (`ui/lib/canvas.js`: projection, scaling, sprite frame choice, the draw lists, the backend choice, colours) are tested by `node --test ui/`; the renderers are `ui/canvas/points.js`, `mesh.js` and `bodies.js`.

## Theming

Every color and size is a CSS custom property with a dark default (`ui/controls/theme.css` lists them): `--signal-bg`, `--signal-panel`, `--signal-fg`, `--signal-muted`, `--signal-track`, `--signal-accent`, `--signal-effective`, `--signal-thumb`, `--signal-knob`, `--signal-focus`, `--signal-clip`, the meter colours, `--signal-font`, `--signal-radius`, and the sizes (`--signal-fader-length`, `--signal-knob-size`, …, `--signal-readout-width`, `--signal-value-width`, `--signal-card-min`). Set them on the page, a container or one control.

## Stable layout

**The rule (M2.8-11, the owner's: "things keep vibrating, jumping and repositioning").** A value changing, a stream frame, a hover, a drag or an unsaved mark appearing never changes the size or the position of any other element. Only the dragged control's own thumb moves. Everything in `ui/` follows it:

- **Readouts have a fixed width, in tabular figures, with their space reserved.** A control's `.readout` is a box of `--signal-readout-width` (11ch by default; the meter's 9ch, the 2D pad's as wide as its pad, the scope's and canvas's their own width) and fixed height, `white-space: pre`, cut with an ellipsis rather than grown. The fader's and knob's effective value has its own second line, there (empty) when not modulated. `<signal-value>` is `--signal-value-width` wide. Where text is built for a column, `formatFixed` (`ui/lib/format.js`) gives every value of a unit the same number of characters (`fixedWidth(unit)`), in exponent form when it would not fit.
- **Table columns have fixed widths** (`table-layout: fixed` with a `<colgroup>`): Signal.app's parameter list.
- **Unsaved and error marks reserve their space or overlay.** A control's unsaved mark is placed over what is below it (`position: absolute`), never in its flow; a row's mark, the indicator in `<signal-panel>`'s bar and in Signal.app's messages keep their space and are only made visible (`visibility`), never inserted; their changing text ("1 unsaved parameter", "2 …", "… — error") sits in a box sized by its row or of fixed width, cut with an ellipsis, so Retry and Revert beside it never move.
- **A `describe` with the same structure updates the values in place.** Signal.app's parameter list rebuilds its DOM only when the instances or parameters change (`structureKey`, `planUpdate` in `ui/app/lib/parameters.js`), and never under the slider being dragged: that waits for its release. Meters are rebuilt only when the meters change; the generated panel only when what it shows does (its controls, meters and scope, `defaultPanel`), not on a new plan version with the same structure.
- **Meters, scopes and status lines have fixed sizes.** The meter's art is fixed; the scope and canvas are as wide as their card and of a fixed height; Signal.app's toolbar status is `compactStatus` (`ui/app/lib/status.js`), always 25 characters, its status card fixed-width fields (`statusFields`), its meters box and messages fixed heights (the newest messages, each cut to one line, the whole text in its tooltip).
- **No layout depends on text that changes while running.** Labels, titles, the bar's status and the toolbar's notice are cut with an ellipsis in boxes of fixed width; hover and focus change colours and outlines only, never a border width, padding or size.

`node --test ui/` checks these from the source (`ui/app/lib/layout.test.js`, the fixed widths in `ui/lib/format.test.js` and `ui/app/lib/status.test.js`). Whether nothing moves on the screen is checked by a person: the bounding boxes of every element, recorded over 5 s in headless Chrome and in Signal.app's window while playing with streams and during a drag.

## Gallery

`ui/gallery.html` shows every control in every mode. Without a fragment in the URL it runs against `FakeConnection` (a demo project with deterministic signals, a modulated control and a meter that clips every few seconds). With the `#ws=…&token=…` fragment that `signal ui` prints it connects to the running project and adds a section built from its `describe`: a fader and a value per control, the output meters and a scope of the first signal output. `window.signalConnection` is the connection, for the console.

Load it:
- from the server: `signal ui <project>`, then open `http://127.0.0.1:<port>/ui/gallery.html` (add the printed fragment to connect);
- from a file, in Safari (`file:///…/ui/gallery.html`). Chromium refuses ES modules from `file://` (CORS, origin `null`); use the server there. Under `file://`, a browser may also refuse to fetch the SVG skins; those controls then draw their default.

## Panels

A project carries its panels as text (ADR 0023 §4): HTML files in its `ui/` folder, `ui/main.html` the main one, with their SVG and PNG files in `ui/assets/`. `signal ui` serves them under `/project/` and prints the main panel's URL (`docs/ui-protocol.md`). A panel is a page with the controls inside a `<signal-panel>`, laid out as a grid of cards (M2.8-11): `.signal-cards` (as many columns of at least `--signal-card-min` as fit the width) holding `.signal-card`s (a `wide` one spans the grid), both from `theme.css`. Every text of a panel is inside a card: its title and description too (`ui/lib/cards.test.js` checks the example panels and the default one). Inside a card, a `.row` lays controls out in a line that wraps; controls that belong together, such as a stereo meter pair, go in a `.signal-group`, which is never broken across lines and wraps as a whole.

```html
<link rel="stylesheet" href="/ui/controls/theme.css">
<signal-panel>
  <div class="signal-cards">
    <section class="signal-card">
      <h2>kick</h2>
      <div class="row">
        <signal-knob bind="/drums.kick_decay" taper="log" min="100" max="1500" label="decay" skin="svg:assets/knob.svg"></signal-knob>
        <signal-meter bind="/out.l" label="L"></signal-meter>
      </div>
    </section>
  </div>
</signal-panel>
<script type="module">import '/ui/controls/index.js';</script>
```

A panel has no scroll container of its own (no `overflow: auto`, no `100vh`): its page scrolls, which in Signal.app is the Panel tab's frame.

Panels import the library by its served path (`/ui/…`); their own files are relative to the page (`assets/knob.svg` is the project's `ui/assets/knob.svg`).

**`<signal-panel>`** connects with the page's `#ws=…&token=…`, makes that the controls' connection (`setDefaultConnection`), shows the connection's status and the project's name in its bar (a card of one line), and once described asks the server's binding check for its file (`panel.check`; `file` overrides the file the page's path names), once per plan version (`BindingCheck` in `ui/lib/panel.js`); a check the connection dropped is asked again with the `describe` of the reconnect. Every diagnostic is listed at the top of the panel as `ui/main.html:36:28: error: …`, and the control it is about gets an outline (red for an error, amber for a warning), the diagnostic as its tooltip and, for an error, `aria-invalid`. It checks again when the plan version changes. With `generated` it builds the default panel instead.

**The binding check** (`crates/signal-ui/src/bindings.rs`) is the same for `signal ui check <project>` (every `ui/*.html`, against the project's plan; exit 1 on an error) and for `panel.check` (one file, against the running plan). It reads every `signal-*` start tag (comments and the content of `script`, `style`, `textarea`, `title` skipped) and checks each `bind` as the browser gives it to the control, with character references decoded as the HTML tokenizer decodes an attribute value (numeric ones, `&#46;` or `&#x2E;`; every name of the WHATWG table, `crates/signal-ui/src/entities.rs`, the longest that matches; a legacy name without `;`, such as `&amp`, is left as written before `=` or an ASCII letter or digit):

| Control | Binds | Addresses |
|---|---|---|
| `<signal-fader>`, `<signal-knob>`, `<signal-toggle>` | a control: a top-level parameter (`/<instance>.<parameter>`, a composite's exports included), which `commit` writes to `project.toml` | 1 |
| `<signal-xy>` | controls, x then y | 2 |
| `<signal-value>` | a parameter: a control or a plan parameter port (it only shows the value) | 1 |
| `<signal-button>` | an event input of the plan | 1 |
| `<signal-meter>` | a signal input of the audio sink (none with `source="input"`) | 1 |
| `<signal-scope>` | signal outputs or inputs of the plan (a primitive's: `/drums/kick/dc.out`, not the composite's `/drums.out`; an input shows the sum of its sources) | 1 or 2 |
| `<signal-canvas>` | vector outputs of the plan (`/membrane_v.z`) | 1 to 3 |
| `<signal-piano-roll>`, `<signal-step-grid>` | nothing (no `bind`): `pattern="<name>"` names a pattern file of the project, `patterns/<name>.toml` (`project-format.md` §12), of kind `notes` for the piano roll and `steps` for the step grid (M2.11-1, ADR 0028 §7) | 0 |

Errors: an address that is not one, an unknown port (the message lists what the instance has, or says that it is a composite), a port of the wrong kind or shape (`wrong kind: /out.gain is a parameter; <signal-scope> binds a signal output or input of the plan`), an editing control on a parameter inside a composite, which `commit` refuses (`not editable: /drums/kick/amp_env.decay_ms is a parameter inside the composite /drums, …`: export it, or show it with `<signal-value>`), the wrong number of addresses, a `bind` missing where one is needed, an unknown `signal-*` element, and for a pattern control a missing `pattern`, a pattern the project does not have, one of the other kind, or a `bind`. Warnings: an editing control without `bind` (it edits only its own value), `taper="log"` where the range does not start above 0 (the control is linear), and a file without `<signal-panel>`. Positions are `file:line:column` (1-based, columns in characters) at the address in the source (where a character reference starts, if it does), or at the tag's `<`, as the project loader's.

**Edits** are the controls' own: a drag sends ramps and commits on release, which writes the value into `project.toml` (`commit`); the panel file is never written by them (only Edit layout writes it, below). The running project already holds the written value, so the file watch does not reload it (no `reload`, nothing in the log). A write that fails leaves the edit unsaved, with the control's mark and the bar's indicator ("Unsaved" above).

**The default panel.** For a project without `ui/main.html`, `/project/main.html` is `ui/default-panel.html`, whose `<signal-panel generated>` builds from `describe` (`defaultPanel` in `ui/lib/panel.js`): the top-level parameters (`controls`) grouped by instance, a fader for a level (unit `dB`, or a gain without unit; a dB taper for a gain) and a knob for anything else (a log taper for Hz and times whose range starts above 0); a meter per signal input of the audio sink; and a scope on the sink's first input (`/out.l`: the sum of every source feeding it, each scaled, as the sink receives it). Each instance is a card, the meters and the scope a wide `output` card. It is rebuilt only when that structure changes; a new plan version with the same structure keeps its elements, which take the new values.

**The example panels.** `projects/kick/ui/main.html`: decay and drive knobs (an SVG skin, `projects/kick/ui/assets/knob.svg`), the gain fader, the output meters, a scope of the kick. `projects/pulse/ui/main.html`: cutoff and resonance on a 2D pad, the delay's time, feedback and level on knobs (a PNG filmstrip, `projects/pulse/ui/assets/knob-strip.png` and `@2x`, drawn by `node scripts/ui-strip.mjs pulse`), the eight sequence steps as faders (55–440 Hz), the gain, meters and a scope of the filter. `projects/physical-av/ui/main.html` (M2.8-7): three canvases (the membrane seen, as a mesh; the sparks with the PNG sprite sheet; the bodies with the SVG skin), a strike button, knobs, meters and a scope of the membrane heard. `projects/studio/ui/main.html` (M2.11-4): three sections styled after the instruments they recall, with generic titles and no marks, by the project's own `ui/studio.css` (custom properties per section, group captions as `::before` text of class tokens, so the panel stays within the editor's whitelist) and SVG skins: MONO SYNTH (black panel, wood cheeks, the voice's knobs grouped as controllers, oscillator bank with three-position waveform levers — knobs with `sweep="60"` —, mixer, modifiers, contours and output) with the melody's `<signal-piano-roll>`, RHYTHM COMPOSER (warm grey, a knob column per drum voice, tempo, shuffle and accent) with the beat's `<signal-step-grid>`, TAPE ECHO (cream and green, chicken-head knobs), and the master bus's gain (its fader stops at 0.25), meters and scope.

### Cards across windows

Signal.app can show the project's panel over several windows (ADR 0032): a main window's Panel tab and any number of panel windows (`ui/app/panel-window.html`, the main panel in a frame). The main panel stays the one source of the cards. A panel window shows the cards it holds, in its order, and nothing else: a new one is empty (hidden until told, so never the whole panel for a moment), with the hint "Right-click an instrument … and choose Move to". A main window shows every card; a card another window holds stays in its place as a compact **placeholder**, "MONO SYNTH — in Panel window 1 (screen 2)", with **Show** (that window to the front) and **Bring back** (the card back here), so nothing disappears. Closing a panel window gives its cards back to the main window (written like any change). Cards are hidden (`display: none`) and ordered (`order`) with inline CSS only; a held card keeps only its place in the grid, one line high and wholly invisible (`visibility: hidden` on it and, by a style the page adds, on everything inside it and its `::before`/`::after`, so no decoration of a panel's own CSS shows: the owner saw the studio's MONO SYNTH header stay behind), and its placeholder, a one-line bar, is drawn there; the placeholders are an overlay in the frame's `<body>`, outside `<signal-panel>`: nothing is added to the panel's DOM, so the panel file, Edit layout and `panel.written` see the panel as written. Which window holds which card is the project's `ui/windows.toml` (`project-format.md` §13), per screen configuration.

**Card ids.** A card (a `.signal-card` not inside another, or a generated panel's group) is known by its `id` attribute when it has one (letters, digits, `-`, `_`, `.`, `:`), else by the slug of its first heading (`<h2>Tape echo</h2>` is `tape-echo`), else `card`; a second card of the same slug gets `-2`, then `-3`, in the panel's order (`cardIds` in `ui/app/lib/cards.js`). A panel that will be split over windows should give its cards an `id`, so a renamed heading or a new card of the same heading keeps each in its window; the example panels are left as they are, their headings giving `kick`, `kick-2`, `output`, `scope`.

**The card menu** (owner's decision, 2026-10-22: moved from the context menu, not by drag and drop). A right click on a card, on its background or heading, opens its menu: **Move to** each other window by its name, **Move to new panel window** (a window of the card's size, centred on this window's screen), in a panel window **Bring back to main window**, and where the window shows other cards **Move up** / **Move down** (off at the first or last). A control bound to a parameter keeps its own menu (Reset, Copy address), a text field the system's, and Edit layout its own interactions: there the card menu does not open. In a main window the card's items come first in the app's own menu (the card is a `part` of it, as the schematic is: `contextMenu(event)` on the card's element); in a panel window the same menu element (`ui/controls/context-menu.js`, its look and keys: arrow keys, Home, End, Enter, Space, Escape, Tab) opens in the page. A panel window whose cards change fits its height to them (within its screen) until the person resizes it.

**Window names**, in the menu, the placeholders and the titles: "Main window" ("Main window 2" when there are several), "Panel window 1 (screen 2)", "Schematic window"; a panel window's title is "Signal — Panel window 1 — kick.signal".

The messages between a window's page and the app (wry's `window.ipc.postMessage`, JSON; a window event the other way) are not UI protocol messages:

| From | Message | Meaning |
|---|---|---|
| page | `{"type": "window.ready"}` | the page listens; the app answers with `signal-window` (and runs a menu action waiting for a new main window) |
| app | `signal-window` event, `detail` `{"view": "panel", "cards": [ids], "targets"}` or `{"view": "main", "held": [{"card", "where"}], "order": [ids], "targets"}`; `targets` `[{"index", "label"}]`, the other windows a card may move to | what this window shows |
| page | `{"type": "card.move", "card": id, "to": index, "new", "main" or "here", "size": {"width", "height"}}` | Move to, Move to new panel window (`size`: the card's, with the page's margins), Bring back to main window, a placeholder's Bring back: into that window (at its end), a new panel window, the front main window, or this one |
| page | `{"type": "card.order", "cards": [ids]}` | Move up / Move down: this window's cards in that order |
| page | `{"type": "window.show", "card": id}` | a placeholder's Show: the window holding the card comes to the front |
| page | `{"type": "window.fit", "height"}` | a panel window's content height after it showed its cards; the app fits a window whose cards changed and that the person has not resized |

After each move the app tells every window and writes `ui/windows.toml` once it settled. In a browser (`signal ui`) there is no `window.ipc`: nothing of this runs and the panel shows every card.

### Editing a panel

**Edit layout** (M2.9-2, ADR 0026 §4–5) is a switch at the start of `<signal-panel>`'s bar: the Panel tab's top line in Signal.app, and the panel page of `signal ui` in a browser (`ui/controls/panel-editor.js`). It needs a plan, since every write is checked against it: without one the switch is shown disabled and its tooltip says why. In edit mode:

- **Nothing is sent.** Pointer, wheel and keys in the panel never reach a control, and value entry stays closed; the controls' streams go on, so values and meters keep moving. Every card, row, group and control has a dashed frame, a handle (⠿) and its address (a control's `bind`, a card's number). Escape (wherever the focus is, an editor field included: text not yet applied there is let go) or the switch leaves edit mode; there is nothing to save, every change was written.
- **Cards**: drag one to another place in the grid's order; **Wide** spans the grid or not; the card's title (its `<h2>`, or the title card's `<h1>`) and description (its `<p>`, empty removes it) are the fields under the buttons; **Add card** adds an empty one after the selected card; **Remove card** removes an empty card at once and asks for one with controls (the button reads "Remove card? Click again"; anything else cancels).
- **Controls**: drag one within its row, into another card (its last row, made if it has none), or into or out of a `.signal-group`; Shift-click selects adjacent controls of one row and **Group** puts them in a group, which is never broken across lines; **Ungroup** puts them back; **Remove control**. A dragged group moves as a whole. The drop's place is shown by a frame and a caret over the page; nothing moves until the drop.
- **Add**: the palette lists every parameter and port of the plan (from `describe`), searched by words in the address, a few at a time (the list keeps its height; "N more" says to narrow it), with the kinds that bind it: knob, fader, toggle, 2D input and value for a control, value for a plan parameter, button for an event input, meter and scope for a signal input of the audio sink, scope for other signal ports. A 2D input takes a second pick for its y. A new knob or fader gets the parameter's range and the generated panel's taper (log for Hz and times above 0, dB for a gain fader); it goes after the selected control, else into the selected or last card.
- **The inspector** sets the selected control's label, taper, skin, min and max, and **wide scope** (the scope's card wide, with the `scope` class). Min and max are typed with the value entry of the controls ("Value entry": units, `k`, clamping to the parameter's range and its note).
- **Undo and redo** (⌘Z and ⇧⌘Z, or the buttons) write the version before or after: the history is the versions written in this session, and a new change drops what redo would have written. It lasts across leaving and entering edit mode while the file is still the version it last wrote, and starts again when the file changed elsewhere. In a text field ⌘Z is the field's own.

The layout stays the responsive card grid: no position is ever written, "next to each other" is a group. The frames and labels are outlines and absolutely placed, so nothing in either mode moves while values change ("Stable layout"); entering edit mode adds the tools card above the grid once.

**What is written.** Each change is written at once (`panel.write`, `docs/ui-protocol.md`): the page serialises the `<signal-panel>` content canonically (`ui/lib/panel-tree.js`: a line per element, two spaces per level, attributes in a fixed order, `bipolar` bare; the same tree always the same text) within the whitelist of `ui/lib/panel-whitelist.json`, which the server checks again: the controls of "Elements" with their attributes (those each element reads, as the table lists them, and `class`), `div.signal-cards`, `section.signal-card`, `h1` (a title card's heading, without a class), `h2`, `p`, `div.row`, `div.signal-group`, lowercase class tokens (`[a-z][a-z0-9-]*`, so `wide`, `scope` and a panel's own such as `steps` or `view`) and text. It also lists the pattern controls, `<signal-piano-roll>` (`pattern`, `label`, `snap`, `beats-per-bar`, `position`, `position-bind`, `audition`) and `<signal-step-grid>` (`pattern`, `label`, `step`, `step-bind`), so a panel holding them is written and checked like any other (M2.11-1, M2.11-3). The server keeps everything outside the `<signal-panel>` element byte for byte, refuses a file changed since the editor read it (the page then shows the file as it is now; when that version is not editable here, the page writes nothing more and says why until the panel is read again), checks the bindings as `panel.check` does, and writes atomically. Every other client shows the written panel in place; a `.signal` project becomes edited.

**Hand-edited panels** stay editable while they have exactly one `<signal-panel>` element, in the project's own `ui/` (a file reached through a link, or a linked `ui/` folder, is served but never written). Comments inside it are dropped by the first write (outside it they are kept). A panel with anything else inside `<signal-panel>` that the whitelist refuses (a script, a `style` element or attribute, an event handler, another element or attribute, a character reference other than `&amp; &lt; &gt; &quot; &#…;`) is shown as not editable, with the reason, and never stripped: it is edited by hand.

**The default panel** is editable too: its first write creates `ui/main.html` from the generated layout (each instance a card with its module as the description, the output card wide with the meter pair grouped), with the standard head (`/ui/controls/theme.css`) and the controls module; the page then is that file.

Tests: `ui/lib/panel-tree.test.js` (canonical form, the whitelist and its attributes against each element's, comments dropped on reading, the round trip of the three example panels and the generated one) and `ui/lib/panel-edit.test.js` (every operation, the two-step remove, the palette, undo and redo, drops and keys) in `node --test ui/`; the protocol tests are listed under `panel.write`.

## Schematic

`<signal-schematic>` (M2.9-1, ADR 0026 §2–3) draws the `graph` message (`ui-protocol.md`): the project's signal path as written, not flattened. It fills its container (it is `display: block; height: 100%`), takes the default connection, and has no attributes. Right of its sidebar it is a toolbar row, then the drawing area (the stage) below it (the owner's, 2026-10-22: "these buttons should sit on a toolbar that belongs to the schematic view. It is disturbing that they float and sometimes cover elements"): the toolbar has its own background and a bottom border, 32 px high as the sidebar's head; left are Edit patch (with Undo and Redo while editing) and the breadcrumbs, right Fit, Reset layout and Reset all. Breadcrumbs that do not fit are cut in the middle: the top level and the innermost stay, those between are hidden behind a "…" (its title names them), never wrapping and never scrolling. The stage starts below the toolbar and nothing of the toolbar lies over it: the view, Fit, Enter, a breadcrumb and opening keep no margin for a bar any more (only the plain 24 px margins, and Enter's 120 px at the sides for the frame's labels). Still over the stage: the status line (bottom left), the stale-graph diagnostics and Edit patch's notices (bottom), the hover tip and the marquee; the Add module browser is a modal over the whole window. Signal.app shows it in its Schematic tab; `signal ui` serves it alone at `/schematic` (`ui/schematic.html`), a page of its own rather than a tab of the generated panel, so that it fills the window and the panel stays a grid of cards.

- **Drawing.** Every instance is a box with its name and module, its inputs (ports, then parameters) on the left and its outputs on the right; a composite has a second, dashed frame. Wires are smooth curves, as patch cords (the owner's, 2026-10-16: "I would prefer a smooth cable flow"; `ui/lib/schematic-wire.js`): a wire leaves its output to the right and enters its input from the left, both horizontally, as one cubic Bézier whose handles reach `max(40, run / 2, min(height / 2, 120))` layout units, so that two boxes close together are joined by an S that swings out past them rather than a line down their edges; a feedback connection, or a wire whose input is not right of its output, loops out to the right, down to a lane of its own below every box (6 units apart, so loops do not lie on each other), back along it and up into its input from the left, every turn rounded (a quarter circle of up to 16 units). They are coloured by the source's shape (signal: accent, vector: the effective colour, events: green), dashed where a converter changes the rate. A pin has its port's colour, as its wires (the owner's, 2026-10-16: "if the wires are colour-coded, the connection points should be too, and show whether something is connected"): filled when a wire of its level reaches it, a ring when nothing does; a parameter nothing reaches (set by its value alone) keeps the muted ring (`connected` on the layout's pins, `ui/lib/schematic-layout.test.js`). A wire is drawn as its curve (`C` in the path, exact at any zoom; past the clip distance it is split until the pieces near the screen are whole Béziers, `bakedPath`) and hit on its curve (within 4 px at any zoom); its exact bounding box (`box`; a short wire swings out past its pins) is its extent for the bounds and culling, and a polyline of it (`points`, within 1 unit, at most 16 pieces per cubic) is kept for what wants one. Clipped, the chords drawn where a curve crosses the clip edge are within 0.01 px of it at every zoom its bake holds for. `ui/lib/schematic-wire.test.js` checks the curves (ends exact, horizontal at both pins, the reach not collapsing between close boxes, the exact box, loops down to their lane and back without a corner, deterministic), the hit, and the bake at deep zoom and at every zoom and pan its bake holds for; `ui/lib/schematic-layout.test.js` that a dragged box's wires are the next layout's, a level above y = 0 included; `ui/lib/schematic-drag.test.js` the drag on stand-in elements (what is written, once, put back on a cancel, a composite's labels following its box, a cluster's following or hidden, the insides moved and kept in SVG's bounds, another instance following, the view kept inside a composite on release). Hovering a wire names its ends and its converter. Strokes do not scale (`vector-effect: non-scaling-stroke`), text below 4 px on screen is not drawn. The layout (`ui/lib/schematic-layout.js`) is layered left to right by signal flow: longest-path layers, barycentre ordering, feedback edges reversed; a node with a position in `ui/schematic.toml` keeps it and the others move down past it.
- **Boundary labels** (M2.13-2, ADR 0030 §1; the owner's, 2026-10-19: "on the outside of the composite you can't see which of the 20 inputs is what … labels on the edge of the composite too"). The pins of a closed composite's box and of the frame inside an open one are labelled, never on each other and never left out (`placeLabels` in `ui/lib/schematic-labels.js`); since 2026-10-20 in the level's own units, scaling with the drawing (**Text that scales**, below). A box side shows every pin while its rows are a label's pitch apart; closer, its runs of one name prefix (up to the first `_`, else without trailing digits: `osc1_* (3)`, `f_* (4)`), then the closest of those runs merged until they are apart (`hz, gate (2)`, `osc1_* … f_* (14)`), then a count (`31 inputs`). A closed composite's labels stay **inside its box**, never over its neighbours or their wires: a label longer than the box is cut short (ending in `…`, a group's count dropped first: `osc1_*`; a noted pin keeps its name whole and its note is never cut: its short form, `hz → 2`, else its name alone), and where a left and a right label share a row the longer is cut so both fit side by side; a pin's name is never cut to fewer than four characters (`trig…`, never `tr…`), nor a group's, else the box shows one summary (`synth: 31 in · 1 out`), wrapped onto lines inside the box below its title, else its name alone, else nothing (a box too small to read, whose name is not drawn either; the whole text stays the label's title). A collapsed box (below) narrower than 66 px on screen shows its summary, so zooming out goes from every pin named, to its groups named, to the summary, once each. One pass over every label on screen resolves collisions between boxes the same way: of two labels that overlap, the box whose label leaves its own box (else the finer, else the later) is made one step coarser, and two summaries become one cluster (`synth, echo +2: 98 ports`); every step coarsens a box (five at most) or merges two, so it ends within six steps per box, at worst as one label. More than 400 labels on screen: every box is made coarser, then neighbours share one, until at most 400. Widths are measured: the element measures each text once in the labels' own font (canvas `measureText`, `setMeasure`), the pure module estimating them from a per-character table no narrower than that font until then; a label is as wide as its text and its padding, so its text always fits and none is ever on another (a bundle's count is never cut); the labels of a level are placed once in its units and built again only when what they say changes (its detail, notes, the trace, the box under the pointer, a new layout or bake); a pan or a zoom moves and scales them with the drawing. A frame's pin says where it connects outside, one connection away (`/melody.hz → hz`, `out → /echo.in`, `2: /a.gate, /b.gate → gate`, at most three names, then `… n more`); a note shows the signal's path (2026-10-21, the owner's "show the signal's path"): its arrow points the way the signal flows and the source comes first, so the pin's name follows what feeds it (`/melody.hz → hz`, `inside a library composite → x`, `nothing → x` for a port; 2026-10-22, the operator's review: a parameter nothing outside connects to has no note, its name alone, as `nothing → cutoff` on 28 of the synth's 31 inputs was noise: it is left to its value, which its hollow ring and the sidebar say) and precedes what it feeds (`hz → /echo.in`); a closed composite's pin says where it goes inside when the box is under the pointer or the pin is traced (`hz → 2: glide.in, hz_prev.in`), inside the box against its edge, never over its neighbours' wires: a note that does not fit its half of the box shows its short form (`hz → 2`, `2 → out`, the count of what it names) or none (the pin's name alone; `hz → 2:…` read as noise, the operator's review of 2026-10-20), never narrower than the pin's name (as far as the box allows), so a hovered or traced box keeps its pins' labels (the whole note is the label's title and the tip). A frame's labels go outside its pins, unless one of them on screen (its row in the drawing area) would leave the drawing area at a side (past its edge, by the sidebar; 2026-10-22, the operator's review: at deep zoom they did, as the labels in the level's units no longer knew the drawing area): then that side's labels go on the pins' other side, inside the frame; they are placed again only when a side turns (`frameSides`), never on every pan. A traced pin's label keeps its note and adds the trace's summary after it (`/melody.hz → hz · trace: from /melody.hz`). Hovering a boundary pin shows its whole label in the tip. A primitive's pins keep their labels in the drawing (scaled, from 4 px).
- **Text that scales** (2026-10-20, ADR 0030 Refinements; the owner's "not every letter scales when zooming — everything should zoom nicely" and "on the outside and on the inside of the composite, the connecting interface should be named"). Every text of the drawing is in its level's units, inside the SVG, and scales with the view exactly as the boxes and wires do: box titles and modules, primitives' pin names, composites' and frames' pin labels and notes, group labels, summaries and bundle counts (each level's labels in a group of its own, `levelLabels` and `levelCounts` in `ui/lib/schematic-labels.js`; a pin label 9 units, 11 a row, as a primitive's pin names). Nothing is kept at a size on screen: what a level's labels say goes by size (`labelDetail` in `ui/lib/schematic-groups.js`): every pin named while the groups are open (a row 11 px or more on screen, k ≥ 0.69); below, each group's pin named (`osc1_* (4)`, a frame's runs of the same groups) while that text is 4 px or more; below that, one summary per box (`synth: 31 in · 1 out`), drawn as large as its box holds it whole (up to six times a pin label) and hidden in turn when smaller than 4 px. A boundary pin's note (`/melody.hz → hz` on a frame, `hz → 2: glide.in, hz_prev.in` on a box hovered or traced, a trace's summary after it) shows from 7 px text (k ≥ 0.78), so zoomed in a frame names **each** exported port with where it connects outside, never merged runs (merging is only the coarser step). Any text under 4 px on screen is hidden (each text size is one group, shown or hidden by the zoom alone). Labels carry a halo of the background's colour, so they read over wires; a traced label has a focus-coloured outline, a count is a pill (18 units: read while bundles are drawn). An open composite's box keeps its pins named, outside its edge (its inside is drawn in it), hidden above 40 px text, when the view is deep inside and its frame names the same ports. At the owner's scales the studio synth reads: 0.3 summaries, 0.5 groups, 0.8 every pin with its note inside, 1.2 and 2.0 the same, larger.
- **Ports in groups** (M2.13-2, ADR 0030 §3). A composite's box lays its pins out in groups (`portGroups` in `ui/lib/schematic-groups.js`, the layout's `factsOf`): an export's `group = "…"` (`project-format.md` "Groups"), else its name's prefix (`osc1_*`, `f_*`, `a_*`), else the pin alone; groups in the order of their first export in the file (`graph`'s `order`), inputs before parameters, and each group's pins in that order too. Below 11 px a row on screen (a label's pitch: a pin drawn on its own always has room for its name) a group of several pins collapses to one pin at its middle, labelled with its name and count (`osc1_* (4)`), and the wires to its pins join that pin, as one bundle from each box (a single wire is drawn to it); zoomed in, every pin is back. Collapsed, a group is one target as it is drawn (`groupHit` in `ui/lib/schematic-hit.js`): its pin, not its members' rows; hovering lists its members, a click selects them all (the sidebar shows them as the group, `/synth osc1_* (4)`, with Trace signal) and Trace signal, from the menu, the sidebar or **T**, traces them together, never one picked for you (`traceTarget`: several pins selected are traced together), and the pin is marked when any member is traced or selected; a patch is not dropped on it (zoom in until it opens, then take the one port). While a box of the level is dragged its groups are open, as its wires are. A box without facts (a library composite, whose exports `graph` does not list) groups by prefix in its ports' order.
- **Wires that scale** (M2.13-2, ADR 0030 §3; the owner's "let there be a down-scaling wiring"). The wires between the same two boxes (into one composite from one box is the same pair), whatever their routing, are one bundle at small scale (`bundleWires` in `ui/lib/schematic-bundle.js`): a thicker curve from the mean of their outputs to the mean of their inputs (a pair's loops as one loop, on the lane of its first), with its count over the drawing at its middle, or a third or a quarter of the way along it where a label already is there, else moved off it a row at a time, else further rows off it: never on another label, never left out (`placeCounts`; since 2026-10-20 in the level's units, `levelCounts`, scaling with it). Zooming in fans it out by the height of a pin row on screen: one bundle up to 4 px per wire, each wire on its own from 8 px, between them in quarter steps, each wire's ends (and lane) moving from the bundle's to its own. A traced or selected wire is always drawn on its own, above its bundle, which still counts it. Hovering a bundle lists its wires; a click selects the bundle (its wires, drawn on their own from then on), a second click on it selects its wire nearest the pointer alone (`bundleClick`), a right click opens the menu of that nearest wire; patching, which starts and ends on pins, is unchanged. While a box is dragged its level is drawn unbundled, so every wire follows the box as before (`DragFollow`), and bundled again on release.
- **Zoom and pan.** One view transform (`ui/lib/schematic-view.js`): the wheel zooms about the pointer (the schematic fills its window, so it owns the wheel: "Keys and the wheel"), a pinch (ctrl+wheel, Safari's gesture events) too; dragging the background pans; `+` `−` zoom about the centre, `0` goes out to the top level, Home fits, the arrows pan, Page Up and Page Down pan a window (`commandView`). The zoom is unbounded but for staying finite (M2.9-1b): the view is kept in the coordinates of the deepest level drawn under the screen's centre (re-rooted on every redraw), its origin moves to the pointer on every zoom, and the levels above and below are derived from it by links computed without rounding. Inside one level the point under the pointer stays within half a pixel up to about 1e13 px per layout unit (float64, measured against exact arithmetic; the camera before M2.9-1b drifted by pixels past 1e9); through nested composites the zoom goes on without limit.
- **Numbers handed to SVG** (M2.9-1b, `ui/lib/schematic-draw.js`). Browsers keep transforms in float32, so each level is baked against a point of its own near the screen and a power of ten: every matrix has a scale between 1e-6 and 1e6 and translations within ±1e7, however deep or far the view. Geometry more than 1e7 px off screen is clipped; a pin wider than 1e7 px is drawn as the part of its disc near the screen (to 0.01 px); text is drawn whenever it is at least 4 px, however large. A parent of which only the inside of open boxes shows (the background's colour) is not drawn at all, and boxes of a level far off screen are culled like any other. Where a level's coordinates are coarser than a pixel at the screen (its nearest point to the centre more than 1e15 px away: past the camera's precision, above), it is not drawn rather than handed out-of-bounds numbers.
- **Incremental drawing** (M2.9-1b). Each drawn level is one group with its elements; a pan or a zoom changes only the groups' matrices. Elements are kept by key and built again only when what is visible changes: culling (nodes, and wires shorter than 2 px on screen), levels opened or closed, a new layout, the text sizes, or a new bake (a zoom past 1e6 or below 1e-6, a pan of 1e6 px).
- **Semantic zoom.** A composite opens in place (M2.13-3, ADR 0030 §2) when the person opens it, and closes when they close it (the owner's, 2026-10-22: "When I zoom in, a composite opens automatically. It would be better if it opened on a click, and there were an × in the top-right corner to close it"): a plain click on a closed composite's box (a press and release that moves less than 3 px; not on a pin, which selects, traces and patches as before) opens it and selects it; a double-click, Enter, Open in place and a trace's reveal open it too. Every open frame has a close button, "×", in the top right of its header, inside the frame and in its level's units, never smaller than 20 px square on screen (2026-10-22, the operator's review: it was about 12 px at Fit; zoomed out it keeps that size, its letter about 14.5 px, and reaches below the header), hidden only where it would cover the frame's title (its name and module while they are drawn) or not fit in the frame (Escape still closes), with a pointer cursor and the title "Close /synth"; a click on it closes that composite and everything open inside it, and neither selects nor starts a drag or a pan. Escape, once a trace has ended (a trace takes the first Escape), closes the innermost open composite, one per press, before it lets the selection go or leaves Edit patch (a click that opens a composite also selects it); Close in the context menu and the sidebar closes the composite it is on. Zooming and panning only move the view: a composite never opens because the view's scale reached a threshold (0.45 of a layout unit per pixel before 2026-10-22, closing below 0.28), and never closes because a zoom out or a pan took it away. Neither an opening nor a closing moves the view: opened by a click, the point of the box under the pointer is the same point of the frame (`openAnchor`), the frame's header (with its ×) kept on the stage when the frame fits; closed, the pan its opening made is undone (kept in its parent's units, so at the scale shown now), so its box is back where it was before it opened and a click there opens it again; one opened otherwise (Enter, a reveal) closes with the levels around kept still. The open composites are the pinned set (`pinOne`, `unpin`), view state, never written to the project. Opening, its box grows where it is into a frame that holds its inside at 0.4 of the parent's units (at most 8 times the scale its box holds it at, never smaller than the box), the inside centred on the box; its pins move to the frame's edges in their order. The boxes around it are moved out of the frame's way in the drawing only (`makeRoom`; the operator's review of 2026-10-20: "make room for the frame"): each side by one shift, a box left of the composite leftward past the frame's left edge and the room for its pins' names, one right of it rightward, one above or below up or down, along each axis on its own, so the order of the boxes and the gaps between them are kept and no box covers another or the frame. The wires to the frame are routed again in the direction they ran to the box (into its left pins from the left, from its right pins on to the right; never a loop below the level because the frame grew), and continue across the edge through the links to the frame's pins inside, one drawing (nested frames too). Every other forward wire that would pass under the frame goes around it (2026-10-22, the operator's review: the studio's drum triggers ran under an open voice's frame corner): along the shortest of four lanes outside it (a column left of it between the boxes moved aside and its pins' names, one right of it, a row in the gap above or below it), leaving its output and entering its input horizontally as every wire does; bundled, a pair's bundle goes the same way (`detour`, `ui/lib/schematic-wire.js`). The level around it stays drawn, dimmed (its other boxes and wires; the frame, the wires crossing into it, the links and what is traced stay full), and the wires crossing into it are drawn each on its own, never bundled at the edge. One composite is open per level: opening one closes an open sibling and what was open inside it. A level that is itself drawn in a frame keeps its frame's size whatever is open inside it, so the room made there may reach past that frame. The growth is one step (no animation). Positions are the stored layout's: a grown frame is never written. Library composites (`lib.*`) stay closed: their inside is not in `graph`. Double-click and Enter open it and fit the inside's own layout to the stage (with 120 px at each side for the frame's labels), never less readable than 0.4725 (a wide inside overflows the view); the second click of a double-click whose first opened (or closed) a composite does nothing of its own. A breadcrumb does the same for its level and closes what is open below it; Fit and `0` show the whole top level with every composite closed (`ui/lib/schematic-open.js`). Patching and moving happen at the innermost open level only (the last breadcrumb), undo and redo included; around it a press selects and inspects, a drag on a box there moves nothing and says so ("Not moved: /kick is around the open /synth; close it (×) first"; the view is not panned instead), a drag begun at the innermost level that a click leaves outside moves nothing, and the edits of a part around it (Delete, Edit scale, Disconnect all, Add module here…, Delete selected, a connection's × in the sidebar) stay in their place, disabled, their title saying why ("the top level is around the open /synth: close it (×) to edit it"); an open composite's own Add module here… adds inside it and stays on. A library composite's Open in place is off ("its inside is not in the graph"); its sidebar says "yes, a library composite (its inside is not in the graph)", and the project's counts its types as "library composites". An open composite's own pins keep about 4 px on screen, however far the view zooms into it, and its selection glow is off. A level drawn smaller than 3.2 px a pin row shows no bundle counts (they would only pile up). The breadcrumbs (the open levels, the innermost last) show where the view is; a breadcrumb goes back out to its level, Escape or the × closes the innermost. Only what is on screen is in the DOM (`ui/lib/schematic-scene.js`).

Let go, the level is laid out with the box there and drawn at the next frame, as the pushed `graph` is: the box, its wires and the loops are where the drag showed them. What may still move on release, and only then: (1) boxes without a stored position. One the dropped box now overlaps moves down past it, and one that had been moved down past the box's old place (or past a box that itself moves) moves back up to where its layer puts it; boxes with a stored position never move. (2) The level's bounds change with the box, and a composite's inside is drawn fitted to its frame (M2.13-3: the box grown, so a change of the inside's bounds moves the inside): when the view is inside the composite whose level was edited (it is in the breadcrumbs), that inside stays where it is on screen and the levels around it are fitted to it instead (`reroot` in `ui/lib/schematic-scene.js`); seen from outside (open in place, not entered), the inside is fitted to its box again, and so is every other open instance of the same composite. `schematic.move` writes the position to `ui/schematic.toml` (`project-format.md` §11); "Reset layout" forgets the shown level's positions, "Reset all" removes the file.

- **Path tracing** (ADR 0030 §1; the owner's, 2026-10-19: "the outer shell is a wire diagram dead end. We can not trace neither visually, nor in the side panel where the signal goes and comes from"). Trace signal (the context menu of an instance, a wire or a pin, a frame's pin included; or **T** on the selection, the part selected last) follows the connections from that part **upstream, downstream or both** (both at first; the sidebar's toggle changes it, and the next trace keeps it) to the real endpoints, computed from `graph` as written, every level, by instance path (`trace` in `ui/lib/schematic-trace.js`, pure): a composite's exported input or parameter leads to the inner ports it forwards (`to`) and an exported output to its source (`from`), both ways and through nested composites; fan-out and fan-in are followed to every branch, and a connection's converters are named on the way. Its **depth** (M2.13-2; the sidebar's second toggle, kept for the next trace like the direction): **through modules** (at first; the owner's, 2026-10-20: a trace from the sidebar should step across levels by default) or **to the next module**. To the next module, a trace never passes through a primitive: a primitive's port is an end, as is a composite port that leads nowhere (an export with no target, an output nothing takes: an open end) and a **library composite's** port, whose inside `graph` does not carry (`lib.*`, ADR 0027 §6; `graph` lists no `lib.*` level), so the trace stops at its pins and says so. Through modules, a primitive is crossed too: downstream from any of its inputs or parameters to all its outputs, upstream from an output to all its inputs and parameters, until **sinks** (a module without outputs, the audio output) and **sources** (one without input ports, a constant's parameters set by their values); a trace from the studio synth's `hz` reaches the glide, the oscillators, the mixer, the ladder filter, the VCA, the echo and the audio output. This is a **structural path, not a signal-dependent one**: every output of a module crossed is followed, whatever its parameters' values (a gain at 0, an oscillator turned down) and whether the module actually passes that input to that output. Library composites still end it. Loops end: each pin is reached once. A pin's trace goes upstream and downstream from it; an instance's from its inputs and parameters upstream and its outputs downstream, and a composite instance's through its inside as well (2026-10-20, the owner's "tracing must be able to go through the composite": its inputs followed inward downstream, its outputs inward upstream, its ends still the outside ones); a wire's from its source upstream and its target downstream, the wire included. A studio-sized project's trace takes about 1 ms (measured in Chrome on the studio, 18 top-level instances and nine composites: 1.2–1.4 ms for one pin, about 2 ms for every top-level instance; the node test bounds a 191-instance project at 10 ms, and a deep trace of the studio's `/synth.hz` both ways, through modules, on a copy of its `graph` (`ui/lib/fixtures/studio-graph.json`), at 10 ms).

  - **In the sidebar**, a Trace section above the selection's: the start, the levels, wires and pins it spans, the direction toggle (← Up, Down →, Both), the depth toggle (To next module, Through modules), × to end it, what it **comes from** and **goes to** (the endpoints, each with its module, "sink", "source", "library composite, inside not in the graph", and the converters on the way; **open ends** last, counted apart in the heading, "Goes to (2, 2 open ends)", marked with a dashed edge and "open end: nothing connected (std.ladder)": a composite port leading nowhere, and through modules a module's output that nothing takes, or its input nothing feeds, which is never a sink or a source), notes (through modules: a structural path; a library composite reached, a loop), and the trace **by level** (top level → composite → instance → pin, an output pin marked `label →` and an input `→ label`, the way the signal flows, each level with its count of wires and pins, an endpoint marked ●, an open end ○ open end, the start bold). - **Selection** (the owner's, 2026-10-17: "a selection is not visible — make it bold or similar"). - **Context menu** (the owner's, 2026-10-17: "every node and every cable should have its own context menu"). A right click (a control-click on a Mac) on an instance, a wire, a pin or the background opens its menu; the ContextMenu key or Shift+F10 opens the selection's (the background's without one) at it. The items are a pure function of the target and the schematic's state (`schematicMenu` in `ui/lib/schematic-menu.js`); one that does not apply stays in its place, disabled, its title saying why (an edit outside Edit patch: "Turn on Edit patch to change the patch"):

  Edits are written as the keys and the drag write them, through the editor's `patch` with undo ("Editing the patch"). There is no "Reset position" of one instance: `schematic.reset` forgets a whole level's positions, and the protocol has no per-instance removal. The menu is a named `role="menu"` with `menuitem` buttons (`ui/controls/context-menu.js`, the keys `menuKey` in `ui/lib/context-menu.js`); a disabled item's reason is its `aria-description` as well as its title. ArrowDown and ArrowUp move (wrapping, past separators; a disabled item takes the focus, so its reason can be read, and does nothing), Home and End, Enter or Space activates, Escape or Tab closes. No key pressed in the menu reaches the schematic: Escape does not leave Edit patch, and Delete or ⌘Z do not act on the selection. When the menu closes with the focus in it (an item chosen, Escape, Tab, or closed by its owner), the focus goes back to where the right click was. It closes on a press outside it, a wheel or pinch zoom or a key zoom or pan, the window's blur, and a `graph` push without its target; Disconnect all writes the pin's connections as they are when chosen, and nothing when none is left. **One menu.** In Signal.app the app's context menu claims the page's document and the panel frame's (`claimMenus`) and takes their right clicks as they bubble, so a handler before it keeps them (the panel editor's edit mode swallows them, and no value can be reset). It asks the element under the click for items (`contextMenu(event, close)` on `<signal-schematic>`, returning `{items, act, closed}`) and shows the schematic's items first, then its own Restart from Files and the other tabs; the schematic, in a claimed document, opens nothing of its own. A right click on the open menu changes nothing. In a browser (`signal ui`'s `/schematic`) no page menu takes it, and the schematic shows the same items in its own menu, of the same element and look. Right clicks on the toolbar, the sidebar and the palette are not the schematic's: there Signal.app's menu is as elsewhere (a parameter row's Reset and Copy address), and a browser's is its own.
- **Level bars** (since 2026-10-25, the owner's "csak a kijelölt elem kapjon mérőket, de minden bemeneten és kimeneten - a tartományának megfelelően": only the selected element gets meters, but on every input and output, each scaled to its range). Only the **selected instance** has meters (the instance of a selected pin counts as selected; nothing selected, or an open composite, none: select a box inside it), one on **every signal input, parameter and output** of it on screen (any rate divisor), in its box: an input's at the left under its name, an output's at the right. Event and vector ports have none (a trigger has no level to show; a vector's elements are its own view). A signal output's meter is a `scope` stream of it at 7680 points per second (a 256-point block about every 33 ms), a signal input's a `scope` stream of the input, which is the sum the instance receives (`ui-protocol.md` "Streams"); a composite's input or output is metered at its export's first target, or at the primitive it comes from. A parameter's meter is its **effective value** (base and modulation) from one `parameters` stream for all of them (at most 64), which takes no scope slot. **Scale:** a port with a declared range (`{min, max}`, a composite export's own range included, ADR 0042) shows where its values lie in it: a block's lowest to highest value as a segment of the bar (a steady value is a 1 px tick), a parameter's value as a bar from the minimum; a port without one (most audio ports) shows the block's peak from −60 to 0 dBFS, as before. Scopes have 8 slots per run, shared with every other scope of every client (`ui-protocol.md` "Schematic level bars"), and the limit stays 8 (each slot costs the audio thread a copy per point): the selected instance's signal ports are taken in order, inputs then outputs, top to bottom; those past the free slots show the same bar with a mark across it, **"no slot"**; while stopped a bar is **idle** (empty). **Muted:** an instance the fault guard muted in the run (`app.mutedInstances`, Signal.app) has a dashed red edge and the word **muted** at its box's top right; a composite that holds one, **muted inside**. Panel scopes get slots first: the schematic asks only for the slots the host says are free, and takes a freed one only 2.5 s after it was freed (a refused `<signal-scope>` asks every 2 s); no timer runs while no slot is free (`ui-protocol.md` "Schematic level bars", which also says what this costs). Live, no slot and idle bars have the same size, and nothing moves when a slot frees. A port that leaves the screen lets its slot go; the tab or page hidden (the element 0×0), the power off or nothing playing lets every slot go. Nothing runs between events: a redraw is asked for (one animation frame) only when the view, the graph or a stream frame changed, and nothing is asked for while hidden or off.

### Editing the patch

**Edit patch** (M2.9-3, ADR 0026 §6) is a switch at the start of `<signal-schematic>`'s bar: the Schematic tab's top line in Signal.app, and the `/schematic` page of `signal ui` (`ui/controls/schematic-editor.js`). Off, the schematic is exactly as above; its Undo and Redo buttons keep their place, hidden. The switch or Escape leaves edit mode (Escape closes the open composites and lets the selection go first, then leaves edit mode; a value field's Escape closes the field, and with the Add module browser open Escape closes the browser only, its search and name fields included: a second Escape leaves). In edit mode:

- **Connect**: drag from an output pin (the cord follows the pointer as a wire's curve, from the pin); the inputs of the same shape (signal, events, vector) and, for a signal, the parameters of the same level are marked (`connectTargets`, ui/lib/schematic-patch.js, from `graph`); dropped on one, the connection is written. The server's verdict is final: a compile error is the reason shown, and nothing is written.
- **Remove**: select an instance or a wire and press Delete or Backspace, or use its context menu's or the sidebar's Delete; a pin's Disconnect all removes its connections in one patch, and the sidebar's × one of them. Several parts selected: Delete removes them all, one patch per level ("Selecting several parts"). An instance goes with its connections at its level, its parameter values and its position; one a composite exports or a panel binds is refused, `in-use`, and the references are listed (file, line, address).
- **Scale**: a selected wire's sidebar has its `scale`, typed with the value entry ("Value entry"; finite numbers only; 1 removes the key).
- **Add** (the Add module browser; the owner's request of 2026-10-27: "the list view is quite compact, and from the modules it's hard to tell exactly what they do"): double-click the background (the top level, or the inside of an open composite), or Add module here… in the context menu, and the browser opens: a modal dialog over the whole window (not a new window; `ui/controls/module-browser.js`), in light and dark themes alike (it is drawn with the theme's custom properties only). At its top the search field (it has the focus), at its left the module types as a tree, at its right what the type under the cursor is, and at its bottom the new instance's name, Cancel and Add. Escape or Cancel closes it and adds nothing; Enter in the search or the name field, Add, or a double-click on a type adds the type under the cursor exactly as before: named as proposed (the type's last segment with the lowest free `_n`, `svf`, `svf_2`, editable before Add; names are `[a-z][a-z0-9_]*` and unique at the level, a refused name said in the footer), written where the browser was opened (`ui/schematic.toml`, as a moved box), one `patch` with its undo. The keys pressed in it are its own: none reaches the schematic (⌘Z and ⇧⌘Z there are the field's, Delete removes nothing), but for the other ⌘ and Ctrl chords, which go on to the app's commands as from any text field; a key that composes text (an IME's Enter or Escape) is the field's. The focus goes back to the schematic when it closes. Its types are `modules`' (the registry's, the project's composites and the built-in library's, asked with `inside: true`), asked once per state of the project's files (`graph.files`): while they are the same, an opening shows the last reply's at once and asks nothing. A refused `modules` is said in the tree and the detail pane ("No module types: …"), not as an endless "Loading…".
  - **The tree** (`ui/lib/module-browser.js`): first by source, in a fixed order kept as data (`SOURCES`): This project (the project's composites), Library (the built-in `lib.*` composites, ADR 0027 §4; added as any type, `module = "lib.<name>"`, named by the last segment, `tape_echo`), Standard primitives (`std.*`), Lab primitives (`lab.*`, a lab build only); a primitive of another namespace gets a source of its own (`<ns>.* primitives`, after these, by name) and one without a namespace goes under Other. Then by category, the `category` the registry's types and the library's composites already carry (ADR 0027 §1), in the palette's fixed order (`core`, `generator`, `filter`, `envelope`, `delay`, `physical`, `event`, `visual`, `io`; a category not in that list after them, by name; a type without one under `other`), and last, under Library, `reference`: the validation references (M2.10-4), whose `modules` entry names the native type they rebuild as `reference_for`. A source none of whose types names a category (a project's composites, unless their files name one) lists its types directly. Types keep the reply's (name) order. Each branch shows its count; each type its name and the first sentence of its description. This project and Standard primitives start open (their categories closed), the rest closed; what is open is kept for the page's session (in memory only). The tree scrolls inside its pane.
  - **Search**: words in the name, the description, the category or the source's name, any case, every word; only the branches with a match show, all open, and the line at the top counts the matches. A type chosen during a search stays the cursor's once the search is cleared (its branches open).
  - **Keys** (the `palette` scope, `ui/lib/keys.default.js`): ↑ and ↓ (PageUp, PageDown; ⌘ or Ctrl with Home and End) move across the rows (with a search, over the types alone); → opens a closed branch, else goes to its first row; ← closes an open branch, else goes to the branch above (on a type only while the search field is empty: otherwise it is the field's caret key); Enter opens or closes a branch and adds a type. A click on a branch opens or closes it (a double-click toggles it once; with a search every branch is open, and a click on one changes nothing), on a type chooses it.
  - **The detail pane** (it scrolls inside its pane): the type's name; its source, category and how many inputs, outputs and parameters it has; its full description (a primitive's descriptor `doc`, a composite's `[composite] description`, ADR 0027 §6), and a validation reference's native type; then tables of its **inputs** and **outputs** (name, kind, shape, rate, range `[min, max]` or —, unit) and its **parameters** (name, kind, the range or, for a discrete one, its value set as `value → label` lines (ADR 0043), the default (`1 (saw)`; a default off the set with the entry it snaps to, `1.4 (→ saw)`), unit and how modulation combines). An unbounded end is `∞`.
  - **Previews**, built in the page from the type's `modules` entry, read-only: no instance exists, nothing is sent and nothing plays until Add (`ui/lib/module-preview.js`). **Panel**: the card the generated panel gives a top-level instance of it (`defaultPanel` of a `describe` holding only that instance, drawn by `generatedSections` of `ui/controls/panel.js`, the same code as the generated panel): its real knobs and faders, at their defaults, inert, over a connection that streams nothing and refuses every edit; a type without parameters gets no card, and says so. **Schematic**: its box as the schematic lays it out and draws it (`layout` of `ui/lib/schematic-layout.js`, the schematic's classes and wires), and for a composite its inside (`modules`' `inside`, laid out as a composite's level, with the frame's inputs and outputs; a project composite at its stored positions). Both show the instance by the name in the footer, following it as it is typed (while it is a name; else the type's last segment). Each preview is at most its size at a scale of 1, smaller to fit the pane. The dialog's backdrop is `--signal-backdrop` (`ui/controls/theme.css`).
  - At small window sizes the tree goes above the detail (below 720 px wide), and both scroll inside the dialog: the window's only scroll containers besides the Schematic sidebar's (`ui/app/lib/layout.test.js`).
- **Inside a composite** (a level open by semantic zoom), edits write `composites/<name>.toml`, and the sidebar says how many instances that reaches ("edits every instance of kick: 2"). Exports are not edited.
- **Undo and redo** (⌘Z and ⇧⌘Z, or the buttons) write the inverse the server answered with, as a patch against the file's newest SHA-256 (`graph.files`); the history is the patches written in this session, and a new change drops what redo would have written. A conflict, an undo the server can no longer apply (the file changed by hand meanwhile), or another project shown (`graph.projectId`: two folders of the same name are two projects), empties the history with a notice: an undo only ever goes to the project it was written in.

Every change is written at once (`patch`, `docs/ui-protocol.md`) and the drawing follows the `graph` push, laid out as any other: the stable layout and the incremental drawing hold in both modes; the rubber band, the marked pins and the notice are placed over the drawing (the Add module browser over the window), never in it. What the editor writes, the server checks again: the comments, order and formatting of everything a change does not touch are kept byte for byte, and an undo restores the file byte for byte. Not in this mode: renaming an instance, changing its module, editing exports, new composites, copy and paste.

### Slots

ADR 0037 phase 3 (2026-10-27; `docs/adr/0037-slots.md` Notes; the owner's "I haven't found yet how to create a slot and configure its inputs and outputs"). A **slot** is an instance whose inputs, outputs and parameters are its own interface, and whose content is whatever is loaded into it. Phase 2 (glitch-free unload-then-load, following a host's transport) is not built yet: until it is, a Load, Replace or Unload is one structural edit, applied by the reload as any added or removed instance (added instances fade in, removed ones out). The logic is `ui/lib/slot.js`; the dialogs `ui/controls/slot-dialogs.js`; the card `ui/controls/slot.js`.

- **In the schematic** a slot is a box with its interface's pins, loaded or not, outlined in the accent colour. An empty slot is hollow and dashed, "empty: lib.voice" (its template's name, or "empty") under its name; a loaded one shows its content there, a project's with ↗. A port that its content does not match has a hollow, dashed pin, the reason in its tooltip. Wires on a slot are the host's, drawn as written.
- **Create one**: in Edit patch, Add slot here… in the background's (or an open composite's) context menu: its name, and the interface it starts from: none (its own ports, added afterwards), `lib.voice`, `lib.instrument`, `lib.deck`, or a template of the project (`interfaces/<name>.toml`). It is placed where the menu opened.
- **Its ports and parameters**: Edit interface… on the box (or a "+" pin, below its last pin on either side in Edit patch, which adds an input or an output; or a pin's Rename or retype port…) opens the interface editor: one row per port and parameter, with its name, role, kind, shape (a vector with its width), rate divisor, unit and group, each edited in place; "+ input", "+ output", "+ parameter" add rows, × removes one; Apply writes one `slot.interface` patch. A rename rewrites the wires, exports, `map` keys and panel bindings on the port; removing a port that wires name is refused, naming them, unless "Remove the wires of removed ports too" is ticked (a pin's Remove port and its wires does the same). On a template's slot, removing one of the template's ports names it in `remove`. Save as template… writes the interface to `interfaces/<name>.toml` and sets the slot to it; Detach from template writes the template's ports into the slot. Make interface from this instance… (any instance) writes its ports and parameters as a template. A template is written by `file.write`, not undone by ⌘Z.
- **Its content**: Load… (empty) or Replace… (loaded) opens the **Load dialog**, the Add module browser in its load mode: the module types and, under Projects, the project folders beside this one (`slot.projects`), each row saying how many of the slot's ports it matches by name ("3/4 match"), most first; the detail says which and names the content's ports the slot lacks; "Add its unmatched ports to the slot" adds them in the same patch. A Replace keeps the slot's `map` and `set` entries the new content accepts and removes the rest, and the notice says which. Unload empties the slot: its wires stay and read 0. Edit map… sets what each slot port takes of the content: by name, a content port or parameter of its role, or none (`false`).
- **On the panel**, every slot has a card, `<signal-slot bind="/deck_a">`: the default panel gives one to every top-level slot, loaded or not, and a hand-written panel places it like any control. Its header says "DECK_A: lib.deck ◂ ../studio ↗" (or "◂ empty") with Load… (or Replace…), Unload and Levels; its body lists the interface's ports, filled when matched, hollow with the reason when not (with Levels on, the matched signal ports' levels, at most 4 per card, each taking one of the run's 8 scope slots), and the interface's matched parameters as knobs, which write the slot's entry. A module name, a project path or a folder dropped on the card loads it. A host panel's binding on a slot's port (`/deck_a.l`) reaches the content's matched port; on an empty slot or an unmatched port it is inactive (a warning of the binding check, not an error). The content's own cards (a project's `ui/main.html` rooted at the slot) come with ADR 0035 §10.
