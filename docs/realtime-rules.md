# Real-time rules

**Normative.** These rules apply to all code that can run on the audio thread: the engine's per-frame executor, plan swapping, and every primitive's `process`. Review checklist at the end.

Why: an audio callback has a hard deadline (128 frames at 96 kHz is 1.33 ms). Missing it is an audible dropout. Most dropouts come from operations whose worst-case time is unbounded, even when their average is fast.

## Forbidden on the audio thread

| Never | Because | Do instead |
|---|---|---|
| Allocate or free memory (`Box::new`, `Vec::push` beyond capacity, `String`, `format!`, `clone()` of heap types, dropping heap types) | The allocator may lock or call the OS | Allocate in `prepare`. Hand drops to the control thread via the return queue. |
| Take a lock (`Mutex`, `RwLock`, `std::sync::mpsc`, `println!`, logging macros) | Priority inversion: the audio thread waits on a lower-priority thread | Lock-free SPSC queues (rtrb); atomics |
| Make syscalls or do I/O (files, network, `std::time::SystemTime`, thread spawn, sleeping) | Unbounded latency | Do it on the control thread and send results as events |
| `panic!`, `unwrap()`, `expect()`, unchecked indexing that can fail at runtime | Unwinding allocates; an abort ends the session | Handle with defaults or a fault flag. Validate in `prepare`. |
| Unbounded loops or recursion, or work dependent on input data size | No worst-case bound | Fixed iteration counts; bounded buffers |
| Read wall-clock time for semantics | Breaks determinism | Use the frame counter |
| Use randomness not derived from the instance's seeded stream | Breaks determinism | `ctx` RNG stream |

## Required

- **Bounded work per frame.** Document the worst case for any primitive whose cost varies.
- **Finite output.** NaN/Inf or absurd magnitudes trigger the engine's fault guard (fade, mute, report). Primitives should not rely on that guard.
- **Denormal safety** per `dsp-conventions.md` (M1): flush decaying state in feedback paths.
- ***k*-partition invariance** (ADR 0002): results must not depend on how frames are grouped into calls.
- **No semantics tied to the callback.** Control-rate work ticks on an absolute frame grid, never "once per callback".

## How it is enforced

- **Contract suite** (M1), run on every primitive in `crates/` and `lab/`:
  - allocation-counting global allocator during `process`;
  - random *k*-partitions compared bit for bit;
  - fuzzed inputs must give finite outputs.
- **Lints:** real-time crates deny `clippy::unwrap_used`, `clippy::expect_used`, `clippy::panic`, `clippy::indexing_slicing` (configured per crate when it is created).
- **Runtime reporting** (M2): xrun counter, worst-case callback time, fault reports. The runner's status reports late commands and queue overflows, the audio adapter clipped samples and dropped meters ("The runner" below).
- **Soak tests** (M2): ≥ 30 min with scripted live edits.

## The trust boundary

Synchronous primitive calls (`process`, `emit`, `absorb`, and a latent module's `due` and `miss`) run inside the audio callback, on the audio thread or a worker, and the callback returns only when every one of them has (ADR 0020: the caller waits for every joined worker before the block's buffers may be reused, `crates/signal-engine/src/gate.rs`). So each must be **bounded in time and never block**: no waiting on I/O, a device, a lock, another thread or a sleep. The engine contains a call that **panics** (`semantics.md` §14). It does **not** contain a call that **hangs**: the callback stalls, the device underruns, and nothing can safely take the call's buffers back. It only detects it ("Hangs are detected, not contained" below). Computation that is experimental or may block runs behind a **latent (asynchronous) boundary**: a declared latency, its work on its own thread or device, and a `due` that answers at once, as the GPU modules do ("GPU" below, ADR 0019 §3; `module-contract.md` "Trust boundary").

## The runner

`signal_engine::Runner` is what a driver's audio callback calls; `signal_engine::Controller` feeds it from the control thread (`signal_engine::realtime()` builds both). The engine's Runner knows sinks generically: after each block it hands every sink's inputs to the driver's output (`SinkOutput`, ADR 0022). The audio adapter (`signal-output`) wraps both: `signal_output::realtime()` builds the audio `Runner` and `Controller`, which choose the audio sink, apply its `gain`, map its channels and convert for the device. Drivers implement `signal_output::Driver` (ADR 0011, its place amended by ADR 0022): CoreAudio in `signal-audio`, and `NullDriver`, which draws callback sizes from 1 to 4096 from a seeded stream and runs synchronously or on its own thread.

**Order of operations in the audio `Runner::process(out, channels)`**, per callback (the engine's `Runner::process(frames, output)` does 1 and 2 and the parameters and status of 3; the adapter writes the device channels and the meters):

1. **Commands.** Take every queued command in send order. Each has a **requested frame**, its stamp. Its **effective frame** is the frame it applies from:
   - an event: the latest of its stamp, the next frame to run, and the last event's effective frame;
   - a suspend or resume: the same over suspends and resumes;
   - a swap: the latest of its stamp, the next frame, and one past the last swap's frame (one swap per frame).

   These are the engine's own rules (`semantics.md` §12). Events, suspends and resumes go into the engine's queues; swaps wait for their frame.
2. **Frames, in blocks.** Commit the swap whose effective frame has come, then run a block of up to the engine's block capacity (`EngineConfig::block_capacity`: the device buffer, at most 256, set by `RealtimeConfig::with_buffer`), ending before the next swap's frame and before the next command's effective frame (`Engine::next_command_frame`; `semantics.md` §13). For each frame of the block, write the audio sink's channels (each times the sink's `gain` in that frame, as the offline driver records them; the gain is resolved again in each plan a swap brings, without allocating, since the new plan's sink may add or drop it) to the same device channels, interleaved, as f32. Device channels beyond the sink's are 0; sink channels beyond the device's are not played. Each value is **clamped to [−1, 1]** before the conversion, and every clamped (or non-finite, written as 0) sample is counted in `clipped`. Then push the block's log records, frame by frame (the engine's log holds one block). The output is bit-identical whatever the blocks, except after a panic in a `process` call of several frames, whose fault acts from the call's first frame (`semantics.md` §14).
3. **Meters, scopes, parameters and status.** Push one meter per sink channel (peak and sum of squares over the callback), each full block of every running scope (the scope adapter, M2.8-1: the scope commands are taken before step 1; during step 2 each scope keeps its signal output's value, as readers saw it, at every frame that is a multiple of its decimation, `Engine::signal_output_at`), the base and effective value of up to `PARAMETERS_PER_CALLBACK` (64) parameters, going round the plan's parameters from callback to callback, send the input the engine has used back to the control thread, and push the status last: the next frame, the plan version and every counter.

**Hangs are detected, not contained** (M2.7-9). A callback that has not returned after `RealtimeConfig::hang_periods` device periods (default 4; 0 turns it off) since `Controller::poll` first saw it running is counted once (`Controller::hangs`) and handed to `ControlSink::hang` with the instances whose primitive call is still running, one per thread lane, by address; `signal play` and Signal.app write it to stderr (`hangs` in `signal play --json`). The runner publishes, in relaxed atomics only, a callback count (odd while a callback runs), the plan version and, per lane, the instance its current call belongs to, set and cleared around every primitive call on the calling thread and on the workers; the Controller reads that snapshot on its own clock. Nothing waits, allocates or locks on the audio thread or the workers, and nothing reaches the run: a hang is a diagnosis, not part of the log, the session or the audio. Detection depends on the control thread polling during the hang. Verified by `crates/signal-output/tests/hang.rs` (a test primitive blocked for 3 periods, on the calling thread and on a worker, under the null driver).

**Latency.** A command stamped `Stamp::Default` is requested for the current frame, as last reported, plus the latency: two device buffers by default (`RealtimeConfig::latency_frames`, `2 × buffer_frames`). A command whose requested frame has already run is **late**: it applies on the next frame that runs. Its report carries both frames, and the runner counts it in `late`. The engine's log (`log.jsonl`) carries only effective frames, so a live log equals its replay.

**Queues.** Only `rtrb` SPSC queues cross threads:

| Queue | Direction | When full |
|---|---|---|
| commands | control → audio | `Controller` refuses the send, hands the command back and counts it (`command_overflows`). |
| returns: reports, used events and addresses, replaced plans | audio → control | Never full: the Controller keeps at most as many commands in flight as the engine's queues and half this queue hold, and refuses further sends as above. Should it fill anyway, the runner holds the item, counts `return_stalls`, and withholds the status until the item is sent; nothing is dropped. |
| log | audio → control | The record is dropped and counted (`log_overflows`). |
| meters (the audio adapter's) | audio → control | The meter is dropped and counted (the audio `Runner::meter_overflows`). |
| scope commands, and the ports they replace (the scope adapter's) | control → audio, audio → control | Never full: the Controller keeps at most as many scope commands outstanding as the return queue holds, and refuses another (`ScopeError::Full`). |
| scope blocks | audio → control | The block is dropped and counted (`Controller::scope_overflows`). |
| parameter values (observation only) | audio → control | The value is dropped and counted (`parameter_overflows`); the next round reports it again. |
| status | audio → control | Dropped and counted (`status_overflows`); counters are cumulative, so the next status says everything. |

None of them blocks, and none changes the audio: a dropped log record or meter is a report, not an input.

**Dropping.** Nothing that owns heap memory is dropped on the audio thread. Used events and addresses, and a committed swap's box (which then holds the replaced plan), go back on the return queue, and `Controller::poll` drops them on the control thread. `poll` also hands reports, log lines and parameter values (read with the plan that wrote them) to a `ControlSink` without allocating (the audio Controller's `poll_with` hands its meters to a closure the same way); the Controller performs no file I/O.

`NullDriver` in threaded mode checks a one-slot `rtrb` stop queue between callbacks and may sleep for a callback's duration after it (`pace`), outside `process`; `stop` joins its thread and hands the Runner back.

`CoreAudioDriver` (`signal-audio`, M2-4) runs the Runner in cpal's output callback through `OutputCallback::fill`: the Runner writes the sink's channels into a scratch buffer allocated at `start` (a device buffer larger than it is run in pieces), and `ChannelMap` copies sink channel *i* to device channel *i*, other device channels 0. `stop` pushes a token on a one-slot `rtrb` queue; the callback then moves the Runner into a one-slot return queue (if that push fails it keeps the Runner and retries, never dropping it on the audio thread) and plays silence, and `stop` drops the stream on the control thread. Each callback is timed with `Instant` into `CallbackStats`, atomics only, for statistics only: xruns are the stream's errors (CoreAudio overloads among them) plus callbacks whose duration exceeded their period. `signal play` polls the Controller at least once per buffer period, and right before sending a file edit, so `Stamp::Default` (two buffers ahead) is normally still ahead of the runner.

**Joining the device** (ADR 0036). **The device's clock is the run's** (the owner's decision of 2026-10-23): a live run is prepared at the rate the output device runs at (`signal_audio::live_rate`; the engine's `EngineConfig::sample_rate`, which primitives read at `prepare`, and the session recorder take it), and no device's nominal rate is ever switched; the project's `sample_rate` is the rate of its renders and replays. A device whose rate changed between the open and the start is refused (`rate_moved`), never switched. Before it builds a stream, the driver reads the device's shared state (`signal-audio/src/device_props.rs`, read only, on the control thread): whether it runs somewhere (`kAudioDevicePropertyDeviceIsRunningSomewhere`), its I/O buffer and its nominal rate. A device that runs for another app (or for Signal's own input) is joined as it is: no buffer is set (cpal's `BufferSize::Default`, the callbacks hold the device's buffer, run in pieces up to `max_frames`). Only when Signal is the device's only client is the Setup's buffer requested; `buffer = "device"` in the Setup never requests one. The engine is sized for the period the device will run at (`CoreAudioDriver::period`): block capacity, latency and the hang period follow it. **The fade:** at `start` the driver asks the Runner to ramp the device output in over 10 ms (raised cosine, `signal_output::fade`, after the conversion and the ceiling); on `stop` the callback ramps it out over 10 ms, running the Runner on, and hands the Runner back once it has faded out (the meters measure the samples before the fade). Offline renders and the null driver never fade.

Verified by `crates/signal-engine/tests/realtime_no_allocation.rs` (V11), `blocks_no_allocation.rs` (callbacks larger than the block capacity) and `realtime.rs`, by `crates/signal-cli/tests/realtime.rs` (V9, replay of a live session), and for the CoreAudio callback body by `crates/signal-audio/tests/no_allocation.rs` and `callback.rs`.

## Worker threads

The engine runs a block's units on several threads (ADR 0019 §2, M2.6-2): `EngineConfig::threads` threads, the calling thread (the audio callback, or the offline driver) included. 1 runs no worker threads; 0 is auto (below). The `threads − 1` workers are created with the engine on the control thread and kept across plan swaps; they are joined when the engine is dropped, which happens on the control thread (the Runner comes back there). They are ordinary threads, except while a CoreAudio stream plays (below, "Real-time workers").

**Auto (`threads = 0`).** Offline it is every performance core, read once per process (`signal_engine::performance_cores`). In real time (`realtime()`, so `signal play` and the app) it is **two thirds of the performance cores, rounded down, at least 1** (`signal_engine::realtime_threads`; 12 of 18 on the M5 Max), the rest left to the control thread, the GUI and the system. *Revised by the operator at the M2.6-3 checkpoint (2026-10-12), from the first rule below (P − 1), on the device measurement in `docs/benchmarks.md` "Real-time workers on the device": with 120 kick voices on the SSL 2+ (96 kHz, 128 frames), 18 threads gave 2 xruns and a worst callback of 1.86 periods, 17 (P − 1) gave 0 xruns but 0.77, and 12 gave 0 xruns and 0.53.* The reasoning for leaving cores free, which still holds: the audio thread waits for every worker that joined a block's job before the callback returns, so a joined worker that the system preempts to run something else delays the whole block; with every performance core busy in real time, that something else (the control thread polling the Controller, the GUI, the system's own threads) has nowhere to go. The cost is at most one core in P: on the operator's 5cb390c scaling, 107 kick voices within 25 % of the budget on 8 threads and 175 on 18. The evidence: the seat's sandboxed `signal bench --realtime` table (`docs/benchmarks.md` "Real-time workers (M2.6-3)") measured P − 1 = 17 threads no worse than P = 18 in p99 per block, with real-time scheduling (410–418 µs against 395–417 µs) and without (726–1 176 µs against 1 096–1 777 µs). The operator re-measures it outside the sandbox at the checkpoint; if P − 1 is clearly worse there, the rule is revised (ADR 0019 §2, amended 2026-10-12, operator note 002 (2)). An explicit `--threads` or Setup count is used as given.

**Which segments run on the workers.** A segment (the frames between two edit frames of a block) runs on the calling thread alone unless the plan has two tasks or more, the segment has at least `min_frames` frames (16) and the plan's estimated cost times the segment's frames reaches `parallel_min_ns`, and every task's log has room for the segment's staged external events. So a *k* = 1 block never goes to the workers. A segment on the calling thread alone indexes the plan's buffers directly, as M2.6-1 did, without the views a parallel segment's tasks use (ADR 0020). On the seat, in one session alternating with the base build, the kick at *k* = 1 on one thread measured 375.5 and 369.1 ns per frame against the base's 379.5 and 377.8 (`docs/benchmarks.md` "Threads (M2.6-2)"); the operator re-measures outside the sandbox. The thresholds and the cost table are in `docs/benchmarks.md`; they change the timing, never the output.

**The worker budget** (M2.10-5, M2.10-6). A plan uses only as many threads as its estimated schedule can use, not every worker. When a plan is instantiated or swapped in (control-thread code), the engine computes its **budget**, the threads it may use with the calling thread included (`crates/signal-engine/src/tasks.rs`, `worker_budget`):
- **The schedule rule.** For each thread count *p* from 1 to `threads`, it simulates one segment at the block capacity: a greedy list schedule of the tasks over their estimates (the same `COST_NS` figures as the task chains; `makespan`). On more than one thread every task also costs `HANDOFF_NS` = 1.5 µs (claiming it, completing it, its inputs moving between cores), and worker *i* arrives only after its wake, (⌊log₂ *i*⌋ + 1) × `WAKE_HOP_NS` = 6 µs (the wake tree). The budget is the *p* with the least simulated time plus `THREAD_GAIN_NS` = 6 µs for each thread beyond the first, the fewest on a tie. So a thread is used only if it shortens the segment by at least one wake hop. `HANDOFF_NS` and `WAKE_HOP_NS` are measurements, taken once on the M5 Max; their ranges and method are in `docs/benchmarks.md` "Idle cost, part 2 (M2.10-6)", "The schedule rule's constants". `THREAD_GAIN_NS` is not a measurement: it is a chosen penalty, set equal to one wake hop. Nothing is timed at run time.
- **In real time, the share rule** (M2.10-6). If the plan's serial estimate at the block capacity is at most `SERIAL_SHARE` = **0.15** of the block's period, the budget is 1. The period is the **engine block's**: the block capacity at the sample rate. That is the device buffer clamped to 256 frames (`RealtimeConfig::with_buffer`), so for a buffer above 256 frames it is shorter than the device period, and the estimate is taken at the same block. The engine applies the rule when `EngineConfig::realtime` is set (`realtime()`, so `signal play`, and `signal bench --realtime`); offline renders keep the schedule rule alone, because there only speed counts.

Only the first budget − 1 workers are **eligible**:
- a segment's open, a joiner's wake of two and the callback-start wake of `semaphore` and `fanout` take only eligible workers' flags (`Parking::wake`'s limit);
- an ineligible worker that finds a job open marks it seen and parks instead of joining (`Gate::join_if`: the gate's word, then eligibility, then the join);
- a budget of 1 runs every segment on the calling thread and wakes nobody at a callback's start.

Workers beyond the budget stay parked until a plan with a larger budget is swapped in. A driver's requests and the shutdown still signal every worker. The budget is deterministic. It depends on the plan, the thread count, the block capacity, the sample rate and whether the engine runs in real time, all of them configuration. It is timing only, because the calling thread runs every task no worker takes; `schedule_stats().worker_budget` and the trace's `worker_budget` report it. `Schedule::DEFAULT` (so `realtime()`, `signal play`, renders) uses the budget; `Schedule::FORCED` (tests) and the bench's pinned `base` schedule keep every worker (`plan_budget: false`).

**Why the share rule** (M2.10-6). A worker that joins a segment spins in it until the segment's last task is claimed, so every thread a plan uses costs CPU for the whole segment, and parallelism only buys deadline margin. No per-thread gain separates the plans that need the threads from those that do not. The studio's 4th thread shortens its simulated segment by about 34 µs, and 80 kick voices' 18th by 6.9 µs, so any gain that stops the studio at 2 or 3 threads also cuts the 80 voices. What separates them is load against the period: the studio's serial estimate is 10.1 % of its period and the 80 voices' 104.8 % (`docs/benchmarks.md` "Idle cost, part 2 (M2.10-6)").

**`SERIAL_SHARE` is an assumption, not a measurement.**
- It is related to the workers' computation fraction (`--rt-computation`, default 0.25 of the period, below): a plan the rule pins to the audio thread should still fit in that quarter on one thread.
- **Underestimated plans** are the failure direction. A plan estimated at 15 % whose estimate is more than 1.67× too low fills the quarter on one thread, and it gets a longer callback than with workers.
- **Measured estimate errors** (one host, `docs/benchmarks.md` "Idle cost, part 2 (M2.10-6)"): the studio's, the kick's and the 80 voices' estimates are 1.24–1.32× too *high*. physical-av's is 6.1× too *low* even after M2.10-6 added `std.mesh2d_audio`'s cost (it was 22.8× low). The rest of its error is not located in the cost table (an assumption: its instances' parameters against the bench's defaults, or its visual-rate types). Its budget is 1 under every rule, because its time is in one unit that cannot be split (its simulated schedule gains nothing from a second thread), and on one thread it measured 16.4 % of its period, under the quarter. The rule would pin a plan of physical-av's error at 15 % to the audio thread at about 90 % of the period. No such plan is known, but this is the case the operator should watch for.
- The estimate is ratio-checked against measurement per project in `docs/benchmarks.md`.

What the budgets are at 128-frame blocks (deterministic; `crates/signal-cli/tests/blocks.rs` checks the real-time ones):

| Plan | Serial estimate, share of the period | Real time, 12 and 18 threads | Offline, 12 threads |
|---|---:|---:|---:|
| kick (96 kHz) | 1.7 % | 1 | 1 |
| pulse (96 kHz) | 2.9 % | 1 | 1 |
| physical-av (48 kHz) | 2.7 % | 1 | 1 |
| 4 kick voices (96 kHz) | 5.6 % | 1 | 4 |
| studio (48 kHz) | 10.1 % | 1 | 8 |
| 80 kick voices (96 kHz) | 104.8 % | every thread (2, 8, 12, 18) | 12 |

**Performance and efficiency cores: considered, not modelled.** The M5 Max has 6 performance-level-0 cores of 18, and the studio measured fastest at 6 threads. A slower speed for lanes beyond them would make the budget machine-dependent. It would also cut 80 voices' 18th thread (its 6.9 µs gain times a slower lane's speed falls below `THREAD_GAIN_NS`), while 80 voices measured faster up to 12 threads and beyond. Under the share rule the studio uses no worker in real time, so its 6-thread optimum no longer decides anything.

**Early leave: dropped** (M2.10-6). A worker that finds no task ready for its spin would leave the job and park. It was written for M2.10-5 but never tested, and it is not part of the engine:
- under the share rule the plan that motivated it, the studio, runs no worker in real time;
- a worker that leaves cannot rejoin the same job (the join records its epoch in `seen`, `gate.rs`), so in a plan with a second wide phase after a narrow stretch longer than the spin, the callback gets longer: a capacity risk only the device can measure;
- finishing it needed a board model scenario and more line shifts in the time M2.10-6 had.

The budget changes nothing for a worker that is eligible: it still spins in a job until every task is claimed, then for the idle spin below ("Waiting and its cost").

**A parallel segment.** The calling thread publishes the segment's job (`crates/signal-engine/src/shared.rs`, ADR 0020), wakes at most one parked worker, and takes ready tasks itself, as the workers do: a task is ready when its dependency counter reaches 0. It returns when every task is complete and every worker that joined the job has left it. Nothing in a segment allocates, frees, locks or blocks: claiming a task, completing it and joining or leaving the job are atomic operations on memory sized when the plan was built.

**Waiting and its cost** (the `park50` wake policy; the others are in "Wake policies" below).
- An idle worker spins on the job gate after its last job (or a wake that brought none), then parks (`std::thread::park`). How long is `Schedule::spin_ns`: **offline 50 µs**; offline renders run blocks back to back, so their workers rarely park. **In real time too, 50 µs** (`realtime()` sets `Schedule::realtime`, which is the default). M2.6-5 measured spinning through the device period (`Schedule::spinning`): in the sandbox, without real-time scheduling, it cut the p99 per block 2.5–7× (`docs/benchmarks.md` "Real-time wake-up tail (M2.6-5)"). **On the device it failed:** with the workers in the audio workgroup, 80 kick voices on 12 threads gave 4 060 xruns in 15 s (worst callback 12.4 periods) against 0 xruns parking after 50 µs, and 120 voices 5 397 against 0. A worker that spins through the period runs far past its computation budget, and the kernel throttles it (see "The policy" below). Operator decision at the M2.6-5 checkpoint (2026-10-12): the real-time default stays parking after 50 µs until a device-measured policy beats it. An explicit schedule (tests, the bench) is used as given.
- **The bound.** Whatever a schedule asks, a worker spins at most `MAX_SPIN` = **3 ms** (`crates/signal-engine/src/pool.rs`), a little over two periods of 128 frames at 96 kHz; a longer device period (a larger buffer or a lower rate) parks the workers between callbacks again. A worker spins only after a job or a wake, so an engine that runs no parallel segment (stopped, between runs, or a plan too small for the workers) has every worker parked within 3 ms of its last job: an idle engine burns no core (`pool::tests::idle_workers_park_after_the_spin_bound`). The cost is while it plays a plan large enough for the workers: each worker then keeps its core busy for the whole period, so `threads − 1` cores show as fully used. That is why the spin is limited to the real-time auto count (two thirds of the performance cores, above), which leaves the rest to the control thread, the GUI and the system.
- The calling thread wakes at most one parked worker per parallel segment, and each worker that joins wakes up to two more (a tree: depth about log₂ of the workers). Waking is `Thread::unpark`: an atomic swap, and `dispatch_semaphore_signal` only when the worker is parked. It neither allocates nor blocks. It is the one system call a parallel segment can make on the calling thread, at most once per segment.
- The calling thread never waits for a wake: it runs ready tasks itself. Measured on the seat (planner probe, M2.6-2 plan): `unpark` costs the caller a median 1.7 µs (p99 5.0 µs); a parked worker starts running a median 10 µs (p99 44 µs, worst seen 1.6 ms) after its wake, so the *n*-th worker of the tree arrives after about log₂ *n* such hops. With ordinary workers the caller may therefore run much of a short block alone; real-time workers (below) are woken with the audio thread's deadline.
- The handshake loses no wake. A parking worker stores its `parked` flag, fences and then re-reads the gate; the caller opens the gate, fences and then reads the flags. All four operations are SeqCst, and so are both fences (M2.7-6, `crates/signal-engine/src/park.rs`), so in their single order either the worker sees the open gate and does not park, or the caller sees the flag and wakes it. The SeqCst operations alone already give that order; the fences make it hold in the loom model too, which treats SeqCst accesses as AcqRel and, without them, found a worker re-reading the gate from before the open (`docs/testing-and-evaluation.md`, "Synchronisation model tests", P1). A fence is an ordering instruction: it allocates, locks and blocks nothing. An `unpark` that comes before the `park` is kept by the thread, so it is not lost either.
- Every wake goes through one function of the pool (`Shared::signal`) and every block through another (`Shared::block`): `Thread::unpark` and `thread::park`, or under `semaphore` the policy's waiter. That holds for all four wake paths: a segment's open, a callback's start, a driver's request (`Workers::post`) and the shutdown (`Pool::drop`). The last two signal every worker unconditionally; a signal a worker did not need (a park token, a semaphore count) only makes its next block return at once, and the worker loop re-checks the shutdown, its requests and the gate after every return.
- The calling thread waits for a task a worker has claimed, and for every joined worker to leave the job before it returns. A worker preempted at that moment delays the block. With ordinary-priority workers this is bounded only by the OS scheduler: it is the real-time risk of this milestone, and the reason small plans and *k* = 1 stay on the calling thread.

**Wake policies** (M2.7-1). How idle workers wait and are woken is a machine setting, chosen per run: `--rt-policy <name>` on `signal play` and `signal bench --realtime`, `rt_policy` in the Setup (advanced, not in the dialog; `docs/project-format.md` §9), `RealtimeConfig::rt` in code (`crates/signal-engine/src/wake.rs`). **The default is `park50`, the behaviour before M2.7-1, until the operator decides from the device matrix** (`scripts/rt-matrix.sh`, `docs/benchmarks.md` "Real-time wake policies (M2.7-1)"). Sandbox numbers never change it. Timing only: every policy gives the same samples and log bit for bit (the determinism matrix runs under each: `crates/signal-cli/tests/realtime.rs`). Each new policy changes one thing from `park50`, so that a device result can be attributed to it:

| Policy | Mechanism | Idle bound | System calls on the audio thread per callback | Risk |
|---|---|---|---|---|
| `park50` (default) | Spin 50 µs after the last job or wake, then `park`. A segment's open wakes one parked worker; each worker that joins wakes up to two more. | 50 µs after the last job or wake. | At most one `unpark` per parallel segment. | The measured tail: parked workers are woken only when the first parallel segment opens, and each tree hop costs a wake (about 0.4–0.5 of the period worst at 80–120 voices on the device). |
| `budget-spin` | As `park50`, but an idle worker spins until 0.9 × its computation budget (`--rt-computation` × the period) has passed since it last resumed, at most 3 ms, then parks. It keeps a worker that has just run within the budget the kernel granted it. The budget supersedes the schedule's 50 µs spin (`Schedule::spin_ns`), so `signal bench --rt-schedule spin=…` has no effect under this policy. | 0.9 × the computation after its last resume (at most 3 ms). | As `park50`. | A time-constraint thread's computation counts from when it became runnable until it blocks, so a worker that stays awake across callbacks would overrun it: this policy can only keep workers spinning within a callback, not across. **Its interaction with the computation knob:** at `--rt-computation` near 1 it spins most of a period after each job, close to the spin through the period that broke up the stream on the device in M2.6-5 (thousands of xruns); `scripts/rt-matrix.sh` flags those rows. The kernel's accounting may differ from this reading: the device decides. |
| `semaphore` | As `park50`, but each worker blocks on a Mach semaphore of its own (`MachSemaphores`, `crates/signal-audio/src/rt_thread.rs`), and at the start of each callback that can run in parallel the audio thread signals every parked worker, so they wake while it takes the commands, as Apple's audio-workgroup guidance does. Without the semaphores (another driver crate, or creation failed) the workers park, and `signal play` says so (`waiter`). | 50 µs after the last job or wake. | Up to one `semaphore_signal` per parked worker at the callback's start (a Mach trap that neither allocates, locks nor blocks; the same kind of call as `unpark`), plus `park50`'s. | W traps on the audio thread per qualifying callback (about 1.7 µs each if like `unpark`: some 19 µs at 12 threads). When the plan qualifies, every parked worker is woken every period; one that finds no job spins 50 µs and blocks again. In M2.6-5 a callback-start wake (`prewake`) was rejected in the sandbox only; the device has not measured it. `std::thread::park` is itself a dispatch semaphore on macOS, so the gain, if any, is in when and whom it wakes. |
| `fanout` | As `park50`, but at the start of each callback that can run in parallel the audio thread wakes two parked workers, and each worker that resumes wakes two more parked ones, once per callback (a generation per callback; so at most 2 + 2W wakes, and the tree ends). `park50`'s tree runs only from a segment's open and only after a worker has joined it. | 50 µs after the last job or wake. | Two `unpark`s at the callback's start, plus `park50`'s. | As `semaphore`'s per-period wakes, at two calls on the audio thread instead of W; the last worker arrives after about log₂ W hops. |

- **When the callback-start wake comes.** Only when the running plan can run on the workers in the callback (`Engine::begin_callback`), and only for its eligible workers ("The worker budget" above): a budget above 1, two tasks or more, a callback of at least `min_frames`, and the plan's estimate for it reaching `parallel_min_ns` (the test of a parallel segment, without its staged-event check). A *k* = 1 run, a plan too small for the workers or a callback shorter than `min_frames` wakes nobody, so the idle bounds above hold. While a qualifying plan plays, the workers of `semaphore` and `fanout` are woken every period by design.
- **The computation budget** is a separate knob: `--rt-computation <fraction of the period>` (more than 0, at most 1; default 0.25), `rt_computation` in the Setup. It sets the workers' time-constraint computation (`TimeConstraint::for_period`) and `budget-spin`'s budget, under any policy. See "The policy" below for what the kernel does with values up to 0.5.
- **Tested** with the null driver under every policy (C12): idle workers park within their bound and a callback that cannot go parallel wakes nobody (`pool::tests`, `parallel.rs`); every wake path reaches workers blocked on the waiter and no wake is lost: once the workers wait again, the waits that returned equal the signals sent, requests and the shutdown included (`pool::tests::every_wake_path_reaches_workers_blocked_on_the_waiter`, and with Mach semaphores `crates/signal-audio/tests/rt_workers.rs`); the `fanout` tree ends; the engine stops while every worker waits; and 1 000 callbacks on 8 threads with random task delays and random gaps match one thread (`parallel.rs`, and on Mach semaphores `rt_workers.rs::semaphore_workers_match_one_thread_under_random_delays_and_gaps`). Nothing allocates on the audio thread or a worker during a callback under any policy (`blocks_no_allocation.rs`, and with Mach semaphores `crates/signal-audio/tests/no_allocation.rs`).

**Wake-up trace** (M2.7-1, extending M2.6-5's). With `signal play --rt-trace` (always in `signal bench --realtime`), the engine records per callback, atomics only:
- each worker's **wake latency**: from a wake sent by the audio thread or a worker to that worker running again, stamped by the sender and recorded by the worker when it resumes, even after its callback has ended, so a late resume counts for the wake that sent it, never the next callback. `wakes_signalled` and `wakes_observed` count them. A driver's request and the shutdown are not stamped, and a wake that interleaves with one may go unobserved: if a worker already running on a request's surplus signal is stamped after it has looked for its stamp, it blocks again with the stamp set and the next wake overwrites it. So `wakes_signalled − wakes_observed` is the pending wakes plus such lost observations, not strictly the pending count (rare, and only while requests are posted during play);
- the time from the callback's start to the **first and the last worker joining** a job. A callback in which no worker joined adds nothing and counts in `callbacks_without_join`: a missing observation is never a 0;
- the **slowest task** body of the callback, whether the task ran on a worker, on the audio thread in a parallel segment, or in a segment the audio thread ran alone (there task by task in the same order as without the trace), so every callback that ran a block contributes one. On one thread (no workers) the trace is kept too: the slowest task of each callback, with no wake or join observed (counted in `callbacks_without_join`, empty distributions); the engine then holds a pool of no workers that spawns no thread and never runs a parallel segment.
Each is a histogram, eight buckets per octave, with the exact maximum (so a median or p99 is within 12.5 %). `signal play --json` reports them under `wake` (µs, per worker too), with the callback's median and p99 (`median_callback_ratio`, `p99_callback_ratio`, steps of 0.01 of the period) beside the worst.
- **Throttling and demotion: the system exposes no count.** macOS gives a process no counter of real-time throttling or demotion events: the kernel's fail-safe is only a kdebug trace code (`MACH_FAILSAFE`, `sys/kdebug.h`: "tripped fixed-pri/RT failsafe"), readable through `ktrace` as root. So `signal play` samples instead: on the CoreAudio path, at each control step (about once per period, at most 1 ms), it reads the policy in effect of each worker that entered the time-constraint policy (`thread_info`, `THREAD_BASIC_INFO`) and reports `rt_demotions: { exposed: false, samples, sampled_timeshare, unsampled }`. `sampled_timeshare` counts reads that found the standard policy. A demotion shorter than a step is not seen; a read that fails (the thread has ended) is `unsampled`, never a sample. **Assumption:** that a fail-safe demotion shows as the standard policy there; the device will tell.

**A panic in a block** (M2.7-3, `docs/semantics.md` §14) never ends a thread and never passes silently. A primitive's panic is caught at its call, on whichever thread ran it, and mutes that instance (a `panic` fault); the block goes on. Anything else that unwinds in a task (engine code, or the test hook) is caught in the job, fails the task on the task board and stops the engine with an error (`Engine::failure`; the runner then outputs silence and reports it). Catching allocates, locks and blocks nothing; the panic itself allocates its payload and the default hook prints to stderr, the cost of the broken contract. After a failure the calling thread waits only for the claims already made, each settled by one completion, so it never hangs; the pool keeps every worker (`schedule_stats().task_failures` counts the failed tasks). The calling thread no longer unwinds out of a parallel segment; the job's close guard still waits for every joined worker to leave before `serve` returns or unwinds.

**Determinism.** A task writes only its own instances' rows; every sum and event merge is computed by the consumer in canonical source order; the tasks' logs are joined in task order after the segment. The output and the log are the same bit for bit for every thread count (`docs/semantics.md` §13).

## Real-time workers (M2.6-3)

ADR 0019 §2 and §4: while a CoreAudio stream plays, the workers are scheduled like the device's I/O thread.

**The driver's hook.** `Runner::workers()` (and `Engine::workers()`) hands the driver a `signal_engine::Workers` handle, which stays usable while the Runner is in the callback. `Workers::post(f)` runs `f(w)` once on each worker thread `w`, in posting order, between jobs: a worker checks for requests at the top of its loop and again before it parks, and `post` unparks every worker after publishing the request (the same SeqCst handshake as the gate, so no request is missed). `Workers::wait(generation, timeout)` says how many live workers have run it. A request is kept until every live worker has run it, so a wait that times out drops nothing: a late worker runs it when it next loops. The request queue is a `Mutex` taken only by the control thread and by workers between jobs, never in a job, and never by the audio thread. A worker whose request panics ends, as one whose task panics does (it no longer counts; the pool runs one short until the engine is rebuilt).

**Entering and leaving** (`crates/signal-audio/src/rt_thread.rs`, the audited module, and `scheduling.rs`). `CoreAudioDriver::start`, before it builds the stream (so before the first block):
1. finds the output device's CoreAudio object: cpal hides it, so its id is matched by position in the system's device list (`kAudioHardwarePropertyDevices`, which cpal's `Host::devices` lists in the same order, unfiltered), read before and after cpal's listing, which must agree (three attempts); and reads its I/O workgroup (`kAudioDevicePropertyIOThreadOSWorkgroup`), or keeps why there is none;
2. posts `rt_thread::enter` to the workers: each sets the Mach **time-constraint policy** from the device's period, then **joins the workgroup** (only real-time threads can join one); it reports `workgroup` (policy and join), `time-constraint` (the policy, with the join error or why there is no workgroup) or `none` (the policy was refused);
3. waits up to 1 s; a worker that has not answered is reported `none (pending …)` and enters later.
If building or playing the stream fails, the workers leave again. `stop`, once the Runner is back (or the callback is gone) and the stream is paused, posts `rt_thread::exit`: leave the workgroup, then the standard policy back. A worker that ends while joined leaves first (its thread-local state does it on drop). Each joined thread holds its own reference to the workgroup, and so does each pending request, so no one leaves a released workgroup.

**The policy.** `TimeConstraint::for_period(frames, rate, timebase, computation)`: period and constraint are the device period (128 frames at 96 kHz: 1.333 ms, 32 000 ticks of 125/3 ns), computation the fraction `--rt-computation` of it (default a quarter, `from_period`: 333 µs, the V12 budget of a callback), clamped to 50 µs – 50 ms, preemptible. **Fact (SDK `mach/thread_policy.h`, `THREAD_TIME_CONSTRAINT_POLICY`):** "If (computation < constraint/2) it will be forced to constraint/2 to avoid unintended preemption". With the constraint the period, the kernel therefore raises the quarter to half the period, and every `--rt-computation` up to 0.5 asks for the same policy (unless the header is wrong for threads in a workgroup; the device matrix can show it by comparing 0.25 with 0.5). A quarter, not more: a time-constraint thread that keeps running beyond its computation can be demoted by the kernel, and the workers of a project within V12 need less. *M2.6-5 tried idle workers that spin through the period, so far past their computation: on the device the kernel throttled them and the stream broke up (thousands of xruns, "Waiting and its cost" above), which the sandbox could not show. Workers therefore park after 50 µs in real time as well.**assumption** that the operator's V12 soak and `signal bench --realtime --rt-schedule base --rt-schedule default` on the device decide.* In the seat's sandboxed table the device-like rows (`rt-all`: the calling thread in the same policy) ran 24 kick voices in a median of 280–411 µs and a p99 of 395–418 µs per block on 8 to 18 threads, at or near that budget (`docs/benchmarks.md`).

**Only beside a real-time caller.** In the same table, time-constraint workers beside an *ordinary* calling thread (`rt-workers`) had a p99 of 13–16 ms per block and a worst of 2.7 s: workers waiting at real-time priority for a task the ordinary caller holds can keep it from running. The driver therefore puts the workers into real time only around a CoreAudio stream, whose callback thread is real-time; the null driver, offline renders and replays leave them ordinary (only `signal bench --realtime` sets the policy, to measure it).

**Reporting.** `signal play` prints `signal: T threads (W workers): <path>` and adds `threads`, `workers` and `scheduling` (`path`, `summary`, each worker's path, why there was no workgroup) to its JSON, with `rt_policy`, `rt_computation`, `waiter`, `wake` and `rt_demotions` ("Wake policies" above); the app's status line shows `threads T (W workers, <path>)`. Statistics only: none of it reaches the Runner, the engine log, `log.jsonl`, a recorded session or the audio, so the determinism matrix is untouched (`crates/signal-audio/tests/rt_workers.rs` plays the kick with time-constraint workers bit for bit like the offline render).

## GPU (M2.6-4)

ADR 0019 §3. The per-block graph never runs on the GPU; GPU-backed modules declare a latency of *L* ≥ 1 blocks of their own (`module-contract.md`, "Declared latency").

**The device service** (`crates/signal-gpu`). `GpuService` creates one adapter's wgpu device (Metal backend) on the control side. It owns one thread, `signal-gpu-<id>`, the **only** thread that submits work to that device or polls it (`Device::poll`). M2.7-2: there is no process-wide service; a `DevicePool` owns one service per device (below). A module talks to it through a `Channel`: a fixed pool of job buffers, allocated in `prepare`, moved (never copied, allocated or freed) through two `rtrb` SPSC queues, submit and done; the queues' atomic indices are the completion signal. `submit`, `peek_done`, `take_done` and `recycle` neither block, lock, allocate nor make a system call. The GPU thread never parks: it polls every channel and sleeps 50 µs when idle (`IDLE_SLEEP`; 1 ms while no channel exists, `UNUSED_SLEEP`), so a submitting thread never has to wake it. A dropped channel's jobs are dropped on the GPU thread; a stopped service makes every channel report its jobs lost.

M2.7-5 (the external audit of 986cc16, findings 3–5):
- **Preparation refuses what cannot run.** The pipeline cache holds only compiled pipelines, keyed by the shader's text and entry point; workgroups, buffers and bind group are each channel's own. `channel()` refuses (`GpuError`) workgroups of 0 or beyond the device's limit, buffers beyond its limits, a shader that uses any resource but the input (group 0, binding 0, read-only storage) and output (binding 1, read-write storage) through one explicit pipeline layout, and buffers smaller than the shader needs, by recording one dispatch it never submits (wgpu checks the bound sizes then). A shader that never writes its output is accepted (its output stays 0).
- **Every job ends with an explicit outcome** (`Outcome`): `Ok`, `Failed(reason)` (`Validation`, `OutOfMemory`, `Internal` from error scopes around its submission; `Mapping` from its `map_async` callback or scope; `Uncaptured` when an error no scope captured was raised while it was in flight; `Stopped` when shutdown came before it started) or `DeviceLost`. Only `Ok` reads the staging buffer; a readable buffer is never taken as success. After every attempted map, answered or refused, the staging buffer is unmapped inside the job's own scopes, so the next map can succeed and no error reaches the next job. `DeviceLost` is reported once wgpu's device-lost callback has run (wgpu drops the typed device-lost error before any scope); a job in between may end `Failed(Mapping)` or `Failed(Uncaptured)`, a fault all the same.
- **A job belongs to its channel.** `recycle` refuses another channel's job (or one the pool has no room for) and hands it back: it never frees on the caller's thread. Drop a refused job outside real time.
- **Asynchronous completion.** At most one job per channel and `MAX_IN_FLIGHT` (16) per device are on the device at once; the GPU thread starts them in turn, polls without blocking and completes each job when its map has answered, so a slow job holds back only its own channel.
- **States.** `Running → Draining → Stopped`, and `Lost` from any state, for good: a lost device's jobs, in flight or later, end `DeviceLost` without a device call. `shutdown()` (and `Drop`) lets jobs in flight and held results finish for up to `SHUTDOWN_TIMEOUT` (1 s), returns jobs not yet started as `Failed(Stopped)`, and joins the GPU thread only once it has ended: if it has not within `SHUTDOWN_TIMEOUT` + `JOIN_MARGIN` (250 ms), it is left, not joined, and the `ShutdownReport` says so.
- **The engine path is unchanged.** A module turns a job that is not `Ok` into `Due::Lost` and gives its cause (`lost_cause`); the engine logs the `late_result` fault with that `cause` (`semantics.md` §9). Verified by `crates/signal-gpu/tests/service.rs` (noop device) and `lab/tests/fault_causes.rs`, `lab/tests/device_loss.rs`.

**Devices, placement and generations** (M2.7-2). `signal_gpu::inventory()` lists every Metal adapter with a stable id (`<backend>-<name>`, then `-<PCI bus id>` where the backend reports one, then `-2`, `-3`… for adapters still alike; an assumption, since wgpu exposes no Metal registry id), sorted by id; it creates no device. A `DevicePool` opens the adapters the machine Setup's `gpu_devices` allows (`"all"` by default), each with its own service; its device list is fixed when it opens, and a lost device keeps its place.
- **Placement** (`GpuHost`, the registry's `Host`, so the engine lends each instance its device through `PrepareContext::lent` without knowing what a GPU is): an instance pinned in the project (`gpu = "<id or index>"`, `project-format.md` §4) runs on that device; every other GPU-backed instance, in address order, takes device *r* mod *n* of the pool's devices sorted by id, *r* being its rank among the plan's instances placed this way. A pin that names no device of the pool is reported and placed by the rule. An address keeps its first device for the run, so a live edit never moves a survivor and the real-time mirror's second `lend` of a plan gets the same answer. Without devices nothing is lent, and every due result is lost, logged. The render manifest records the device set and the placement (`semantics.md` "Artifacts").
- **Generations.** A lost service is replaced, not left. `Shared::lose` (wgpu's device-lost callback, or the test hook; never a real-time thread) wakes the pool's control-side thread, `signal-gpu-pool`, which otherwise sleeps. It retires the lost service (its shutdown bounded as below), opens the same adapter again as the next generation and offers every channel made on it a replacement, through a lock-free queue. If the adapter is not listed or its device cannot be made, the slot stays lost with its reason (`DevicePool::status`) and is tried again after 100 ms, doubling to at most 5 s; there is no limit on generations. The module takes the replacement at its next block's `due` with `PlacedChannel::refresh` (no allocation, lock or system call; the old channel goes back to the pool to be dropped there). The blocks in flight on the old channel are lost with the cause `device_lost`, as is every miss while the channel's service is lost (`Channel::service_lost`, an atomic load). The pool, and so every service, is dropped by the program that opened it, after the engine; never on the audio thread.
- **Splitting** (`SplitChannel`): a large module may split one job across devices only through a fixed split and a fixed combine order: the type fixes the number of parts *P* (never the number of devices), part *i* runs on device (*first* + *i*) mod *n*, and the combine is called for parts 0 … *P* − 1 in that order once every part is back; a job with any part not `Ok` fails as a whole, and parts of different jobs are never combined: when a part is replaced after a loss, every job then outstanding is reported `DeviceLost` at once, without waiting for its parts, nothing is combined, and its surviving parts go back to their pools, so even one job per part keeps running. No module splits yet.

Verified on 3 noop devices by `crates/signal-gpu/tests/{placement,pool,split,scope}.rs` and `lab/tests/placement.rs`; on Metal by the operator (`docs/benchmarks.md`, "Multi-GPU device pool (M2.7-2)").

**Never waited on in real time.** The engine asks a latent module whether its due result is in (`due`) before each `emit`: in real time once, and a result not in is a `late_result` fault (silence for that block, logged and counted), never a wait. So the GPU is never waited on by the audio callback or the real-time workers. Offline (renders, ideal replays, the bench) the engine waits for it, yielding the thread; an exact replay applies the recorded outcome instead (`semantics.md` §15). Verified by `lab/tests/realtime.rs` (the null driver while the service's test hook, `set_completion_delay`, holds every result back for 60 s: one second of audio runs in a fraction of a second with a fault per due block) and `crates/signal-engine/tests/latency.rs` (a fake latent module, no GPU). The audio side of `lab.gpu_partials` per block is its phases and the job's input: bounded, about 2.3 µs per 256-frame block on the seat (`docs/benchmarks.md`).

**Boundary records** (M2.7-4, `session-format.md` §4a). Each due block's outcome is a log record: a miss is the `late_result` fault, a delivery a `Delivered` record that `log.jsonl` never shows. Both go through the block's preallocated log and the runner's `rtrb` log queue to `Controller::poll`, which hands them to `ControlSink::boundary`. With `EngineConfig::record_boundary_data` the delivered result's words are copied into a block buffer preallocated for every latent instance and sent ahead of their record through a preallocated `rtrb` boundary-data queue (`RealtimeConfig::boundary_data`); the runner checks room in both queues first, and a record whose words do not fit says `lost`. Nothing allocates or waits; every drop is counted (`log_overflows`, `boundary_data_overflows`), and the recorder compares the runner's counts with what it received, so a lost record is detected. Verified by `crates/signal-engine/tests/realtime_no_allocation.rs` (recording on, the data queue overflowing: no heap call in `Runner::process`).

**Optional.** Only `lab.*` types use the GPU, and they compile in only with the `lab` feature (ADR 0015); every other module, and so every existing project and golden, runs on the CPU, bit-exact as before. Without the `lab` or `gpu` feature nothing but `signal-gpu` (and `signal-app`, through eframe and, since M2.7-2, for the compute inventory of its interface setup) links wgpu. The default `signal` binary, the bundled helper of `scripts/bundle-app.sh` included, therefore lists no GPU adapter (`signal devices --compute` says so); a `--features gpu` or `lab` build does (decision of 2026-10-14, made for the run by the top-level supervisor; the operator confirms or reverses it at the checkpoint).

## Review checklist (paste into PRs touching real-time code)

- [ ] No allocation, free, lock, syscall, I/O, or logging reachable from `process` / the executor
- [ ] No `unwrap` / `expect` / `panic` / unchecked indexing on the real-time path
- [ ] Worst-case work per frame is bounded and stated
- [ ] State updates are *k*-partition-invariant (contract suite passes)
- [ ] Feedback/decay paths are denormal-safe
- [ ] Randomness comes only from the seeded `ctx` stream
- [ ] Contract suite and benchmarks pass; new costs recorded
- [ ] GPU-backed modules (ADR 0019 §3): GPU work and every wait for it only on its device's `signal-gpu-<id>` thread; `due` never blocks; the engine waits offline only; a device is lent (`PrepareContext::lent`), never reached through a global
- [ ] `crates/signal-engine/src/shared.rs` (ADR 0020): every `unsafe` block has a `SAFETY:` comment naming its ordering (Release on completion, Acquire before reading; the gate's SeqCst open, AcqRel join, Release leave); shared reads require `T: Sync`; no view escapes its `Access`; the checked-mode tests report no violation
- [ ] `crates/signal-audio/src/rt_thread.rs` (ADR 0019 §4): every `unsafe` block has a `SAFETY:` comment (`unsafe_scope.rs` checks); every workgroup call holds a live reference; a joined thread leaves with its own token and reference before it ends; a semaphore is destroyed only after every worker that waits on it has been joined
