# The UI protocol (version 1)

The interface through which a web page describes, observes and edits a running project (ADR 0023 §1). Signal.app's WebView, a browser and later remote devices all use it. The server is the crate `signal-ui`; `signal ui <project>` runs it (see "Running it"). LLM clients use it through `signal mcp`, an MCP server that is a client of this protocol (ADR 0029): see [`agent-interface.md`](agent-interface.md).

## Servers

Two servers, both bound to **127.0.0.1** by default:

| Server | Port | Serves |
|---|---|---|
| HTTP (a small `std::net` server, `crates/signal-ui/src/http.rs`) | `--port N` (a free one without it, or with 0) | Static files only (below) |
| WebSocket (`tungstenite`) | a free port | The protocol |

They are separate: each WebSocket client has a thread that both waits for its messages and writes the frames queued for it, while the HTTP server serves one request per connection from a fixed pool (below). (Until M2.8-8 the HTTP server was `tiny_http`, whose upgraded connection could not be split either.)

**No client can block the HTTP server (M2.8-8).** An accept thread hands each connection to a queue of 32 (more are closed at once), and a fixed pool of **4 workers** serves them, one request per connection (`Connection: close`, with `Content-Length`). A connection holds one worker at most: it has **2 s** to send its request head (at most 8 KiB; otherwise 400), and a response is streamed in 64 KiB chunks, never read whole into memory; a client that takes nothing for **3 s** is dropped and its worker freed. Every wait is a poll of 100 ms that looks at the stop flag, so dropping the server (`signal ui` ending, Signal.app's window closing or quitting) returns within a few polls whatever its clients do. A client that keeps reading, however slowly, keeps its worker. Tests: `crates/signal-ui/src/http.rs` (deadlines, stop, streaming, without a socket) and `crates/signal-ui/tests/http.rs` (a client that stops reading a 32 MiB asset; another request answered within 1 s; dropping the server within 2 s; the deadline; over TCP and in process).

**The URL to open** (printed by `signal ui`, opened by `--open`):

```
http://127.0.0.1:<http port>/#ws=<websocket port>&token=<session token>
```

The fragment is never sent over HTTP, so the token is in no request, Referer or server log. A page reads both values from `location.hash` (`parseFragment` in `ui/lib/protocol.js`). `signal ui` also prints the project's main panel with the same fragment, `http://127.0.0.1:<http port>/project/main.html#ws=…&token=…`, and `--open` opens that one.

### Static files

| Path | File |
|---|---|
| `/` | the repository's `ui/index.html` (the raw protocol test page) |
| `/ui/<path>` | the repository's `ui/<path>` (the UI library; `signal ui --ui-dir` names another folder) |
| `/schematic` | the repository's `ui/schematic.html`: the schematic, `<signal-schematic>` alone filling the page (M2.9-1; also at `/ui/schematic.html`). `signal ui` prints its URL with the same fragment; it is its own page rather than a tab of the generated panel, so it fills the window |
| `/project/<path>` | the project's `ui/<path>`: its panels, and `ui/assets/` for their SVG and PNG files. `/project/main.html` of a project without `ui/main.html` is the generated panel, the repository's `ui/default-panel.html` (`ui-controls.md` "Panels") |

Only `GET` and `HEAD` (else 405); a response to `HEAD`, a refusal (403, 404) included, is the head alone, with the length the body would have. A path with `..`, `%`, `\`, NUL, an empty segment or a segment starting with `.` is not served, nor one that resolves (links followed) outside its folder; there are no directory listings (404). Content types: `.html` `text/html; charset=utf-8`, `.js` and `.mjs` `text/javascript; charset=utf-8` (ES modules), `.css` `text/css`, `.json` `application/json`, `.svg` `image/svg+xml`, `.png` `image/png`, `.jpg` `image/jpeg`, `.gif`, `.webp`, `.woff2`, `.txt`; anything else `application/octet-stream`. Every response carries `X-Content-Type-Options: nosniff`, `Cache-Control: no-cache` and `Referrer-Policy: no-referrer`.

## Messages

Control messages are JSON text frames, each an object with a `type`. A request may carry an `id` (any JSON value); its reply carries the same `id`. Data streams are binary frames (below). Messages without an `id` are pushed by the server.

**Which project a mutation means** (ADR 0049). `welcome`, `describe`, `graph` and `app` carry `generation`, a number for this opening of the project (a new one on every open, and for every run of the app). A mutation (the file writes below, the live edits `set`, `ramp`, `trigger`, `note`, `revert`, `project.save`, `project.revert`, and `project.open`, whose `generation` names the opening it replaces) may carry `generation` (the opening it is meant for) or `projectId` (`graph.projectId`); one that does not match the open project is refused, `{"type": "error", "code": "project-changed"}`, and nothing is done. A mutation carrying neither is taken to mean the open project.

**Requests that wait for the writer lock** (ADR 0048). Requests that write the project's files (`commit`, `retry`, `patch`, `schematic.move`, `schematic.reset`, `snapshot.save`, `snapshot.restore`, `snapshot.delete`, `snapshot.undo`, `snapshot.move`, `snapshot.transition`, `snapshot.exclude`, `panel.write`, `pattern.write`, `file.write`, `vendor`) run holding the project's writer lock (ADR 0040), which the host takes **without waiting**. When another writer (another Signal process, `signal mcp`, `signal vendor`) holds it, the request waits in the host's queue, not on the control thread, and runs when the lock is free, its checks (`base`, conflicts) made then. To keep each client's order, these wait behind the queue too: a later file request; `project.save` (and the window's Save and Save As), `project.open` and `project.revert`; and a live edit (`set`, `ramp`, `trigger`, `note`, `revert`) of an address a queued request can change (a `commit`, `retry` or live edit of it, a `snapshot.restore` or `snapshot.undo`, an open or revert). Everything else is answered meanwhile (`ping`, `describe`, `stats`, subscriptions, reads, live edits of other values), so a reply to a waiting request can come after replies to later messages. A request that has waited 10 s fails as before (`write-failed`; a commit's value stays live and unsaved); one waiting when 64 already wait is refused at once (`busy`); one queued for a project that is no longer open (Signal.app's menu opened another) is refused unrun (`project-changed`). A Save whose corrections meet the lock waits for it, so it is never made without them. A queued commit sends its live value when it runs.

### `hello` (the first message)

```json
{"type": "hello", "protocol": 1, "token": "<session token>"}
```

The first message on a connection must be `hello`, with the session token and protocol 1, within 5 s of the connection's acceptance: one deadline for the WebSocket handshake and `hello` together, however slowly their bytes arrive (see Clients below). Then the server answers

```json
{"type": "welcome", "protocol": 1, "client": 3, "project": "kick", "sampleRate": 96000, "frame": 123456, "planVersion": 0}
```

(Signal.app's adds `"power": "on"` or `"off"`, its power switch: "Signal.app" below.)

Otherwise it sends `{"type": "error", "code": "unauthorized", …}` (a wrong or missing token, another first message, not JSON) and closes the connection with code 1008 (policy), or `{"type": "error", "code": "protocol", …}` (another version) and closes it with 1002. Nothing else is answered on that connection, and the control thread never hears of it. A later `hello` is an error (`already-authenticated`).

### `describe`

`{"type": "describe", "id": 1}` → the running project:

```json
{"type": "describe", "id": 1, "planVersion": 0, "sampleRate": 48000, "project": "tone", "playing": true,
 "instances": [{"address": "/a", "module": "std.sine_osc", "sink": null,
   "ports": [{"name": "out", "address": "/a.out", "direction": "out", "shape": "signal", "rate": 1, "kind": "audio", "unit": null, "range": null}],
   "parameters": [{"name": "freq", "address": "/a.freq", "kind": "frequency", "rate": 1, "unit": "Hz", "range": {"min": 0.0, "max": 24000.0}, "default": 440.0, "combine": "add", "base": 440.0}]}],
 "controls": [{"address": "/out.gain", "instance": "out", "parameter": "gain", "module": "std.audio_out", "ports": ["/out.gain"],
   "unit": null, "min": 0.0, "max": 4.0, "default": 1.0, "base": 0.5, "inFile": true, "modulated": false, "combine": "multiply"}],
 "sinks": [{"index": 0, "address": "/out", "kind": "audio", "inputs": 2}],
 "meters": {"output": [{"channel": 0, "device": 0}, {"channel": 1, "device": 1}], "input": []},
 "scopes": {"slots": 8, "free": 8, "sinceFreedMs": null, "points": 256, "maxRate": 48000}}
```

(Values here are illustrative.) `instances` is the flattened plan: every primitive instance with its ports and parameters (kind, unit, range, default, combine, and the parameter's initial base in the plan). `controls` are what the parameter panel edits: the parameters of the project's top-level instances, a composite's exported ones included, at the address `/<instance>.<parameter>`, with the plan ports a value goes to (an export can fan out to several), the range they share, the value without a key in the file (`default`), the base (`base`: the live value, the last one the Controller took for every port, even if a runner refused it afterwards; the file's value or the default when nothing else was sent) and whether the file sets it; a discrete control's `values` (ADR 0043: `[{value, label}]`, null for a continuous one), which a client shows as a selector, and its `snap` (`"positive"` for one its modules read as `> 0`, else null: the nearest, of two as near the greater); `set`, `ramp`, `commit` and a restore snap a value to them by that rule. A control's `base` is the value that plays: a file's value outside the range or value set shows corrected (it is not unsaved). `unsaved` lists the parameters whose live value the file does not hold ("Unsaved", below). `planVersion` is the running engine's plan version; `meters.output` lists the sink's channels, the device channel each plays on, and its `label` (`out 1 → 3`, or `out 2 (not played)`). `content` is what the project brings in (ADR 0035 §8, ADR 0037 §7): `{"includes": [...], "slots": [...]}`, each include as it is written, with a rate `note` when it plays at another rate than it is written for, and each slot with its resolved interface, its load, the match table, the wires dropped and the outputs nobody hears; `null` for a project with neither (`Project::content_json` in `crates/signal-project/src/include.rs`).

**`parts`** (ADR 0046 §11, additive): each slot's part that exists, `{"slot": "/synth" | "rack/fx", "file", "base", "root", "roots": [every instance's root], "controls", "error"}` as `graph`'s `slot.part` gives it, its controls rooted at the first root; `[]` without parts.

The server pushes `describe` (without `id`) when a plan swap commits, after a reload that changed values, after a `commit` (or `retry`) is written and after a `revert`, and after `setup.apply` played again (then with `"restarted": true`).

### `graph`

`{"type": "graph", "id": 1}` → the project's structure **as written, not flattened** (ADR 0026 §1), for the schematic (`ui-controls.md` "Schematic"):

```json
{"type": "graph", "id": 1, "project": "kick", "planVersion": 0,
 "top": {
   "instances": [{"name": "drums", "address": "/drums", "module": "drums", "composite": true,
     "ports": [{"name": "trigger", "address": "/drums.trigger", "direction": "in", "shape": "events", "rate": 1, "kind": "trigger", "unit": null, "range": null}, …],
     "parameters": [{"name": "kick_decay", "address": "/drums.kick_decay", "kind": "control", "rate": 1, "unit": "ms", "range": {"min": 0.1, "max": 60000.0}, "default": 400.0, "combine": "add"}]}, …],
   "connections": [{"from": "/lfo.out", "to": "/drums.kick_decay", "scale": 120.0, "converters": []}, …]},
 "composites": {
   "drums": {"inputs": [{"name": "trigger", "to": ["kick.trigger"], "direction": "in", "shape": "events", …}],
             "outputs": [{"name": "out", "from": "kick.out", "direction": "out", "shape": "signal", …}],
             "parameters": [{"name": "kick_decay", "to": ["kick.decay"]}],
             "instances": [{"name": "kick", "address": "kick", "module": "kick", "composite": true, …}],
             "connections": []},
   "kick": {…}},
 "layout": {"file": "ui/schematic.toml", "positions": {"": {"drums": {"x": 120, "y": -40}}, "kick": {"osc": {"x": 0, "y": 30}}}, "error": null}}
```

- `top`: the project's instances, each with its `module`, whether it is a `composite`, its ports (as in `describe`: direction, shape, kind, rate divisor; a composite's are its exported inputs and outputs, with the shape of what they reach) and its parameters (a composite's: its exported ones); and its connections (`from`, `to` as written, with the leading `/`), each with `converters`.
- `converters`: the converters the compiler inserted on that connection (ADR 0005, `semantics.md` §16), each `{"name", "module", "conversion", "fromRate", "toRate"}`: `name` the converter instance's name (`out_d800`), `module` its type (`core.decimate.d1.d800.signal.control`). It is empty when there is none. **A connection between two primitives has at most one entry; a connection to an exported input or parameter that fans out to several ports may have several**, one per distinct conversion. Converters are never listed as instances.
- The schematic's path tracing (ADR 0030 §1, `ui-controls.md` "Path tracing") reads only this message: exports' `to` and `from` map a composite's ports to the inner ports they forward, so nothing was added for it; nor for M2.13-2's boundary notes, bundles or the trace through modules (the instances' ports say which outputs a module has). A library composite's inside is not here (below), so a trace stops at its pins. The schematic's node tests read a copy of the studio's (`ui/lib/fixtures/studio-graph.json`), which `crates/signal-project/tests/structure.rs` keeps equal to `Project::structure`.
- `composites`: every composite the project uses (reached from the top level, nested ones included), by name, in name order: its exported `inputs` (`to`: the inner ports each reaches), `outputs` (`from`), `parameters` (`to`), each listed by name and carrying (M2.13-2, additive, for the schematic's port groups) `order`, its place among the composite's exports of its kind as the file writes them, and `group` when the file names one (`project-format.md` "Groups"); and its inside as the top level's, with addresses relative to an instance of it (`kick.out` is `/drums/kick.out` in `/drums`). Its connections' converters are those of its first instance; a composite's rates are the same in every instance.
- **Order:** instances and connections in source order (the file's), composites by name; the same project always gives the same reply.
- `layout`: the positions of `ui/schematic.toml` (`project-format.md` §11) by level (`""` the top level, else the composite's name), read with every `graph`; `error` says why the file was ignored (it is never a reason not to answer).
- `planVersion` is the running plan's (null while Signal.app is stopped).
- `files` (M2.9-3): `{"": "<sha-256 of project.toml>", "<composite>": "<sha-256 of composites/<composite>.toml>", …}`, every file the project has, read with every `graph`: the `base` a `patch` names.
- **Slots** (ADR 0037 §7, phase 3, 2026-10-27, additive): a slot is an entry of `instances` in its file's place, loaded or empty (an empty slot is in no plan, but it is here). Its `ports` and `parameters` are its **interface's** (`name`, `address`, `direction`, `shape`, `rate`, `kind`, `unit`, `range`, `group` when declared, and `auto` on an auto port, below; a parameter matched to the content's has the content's `range`, `default` and `combine`, else null), its `module` the content as written (`load`; `""` when empty), `composite` true when the content is a composite of the project or the library, and it carries `slot`: `{"interface": {"from", "description", "ports": [{name, role, shape, rate, kind, unit?, range?, group?, auto?}]}, "from", "load", "project" (whether `load` is a project path), "map" (as written: `{port: name | false}`, null without one), "matches": [{port, role, content?, reason?}], "unmatched": [{port, reason}], "unheard": [content outputs], "dropped": ["from -> to"]}` (what `describe`'s `content.slots` says of it). An instance that is no slot has no `slot`. The wires are listed as written, by the slot's port names. **Auto ports** (ADR 0045 §9, phase 1, additive): every port keeps its effective `shape`, `rate`, `kind`, `unit` and `range`, so a client reads it as before; an auto port (`project-format.md` §14, typed by its connections) adds `"auto": {"inferred": [...], "from": {"end": "host" | "content" | "default", "port"}}`: `inferred` the fields not pinned (in the order shape, rate, kind, unit, range), `from.end` the side that typed them and `from.port` that end (a host endpoint qualified by the level as the slot's address is, `/osc.out`, `rack/osc.out`; the content's port name; null for the default). A typed port has no `auto`. A template's auto port in `interfaces` carries `auto` with `from.end` `"default"`. Editing auto ports (`add.auto`, `retype.unpin`) and `retyped` are ADR 0045's phase 2.
- **Editable insides** (ADR 0037 "Editable insides", 2026-10-27, additive): every slot box's `slot` carries `inside`: `{"level", "own", "make"?, "name"?, "reason"?}`. `own: true`: the slot loads its **own inside**, the project composite `level` (= `name`) whose `[composite] inside_of` names the slot (`project-format.md` §14); that level in `composites` has the slot's **interface on its frame**: its `inputs`, `outputs` and `parameters` are the interface's ports and parameters in the interface's order (`order` their place, `group` the interface's), each with the targets of the export it matches (`to`, `from`; `export`, the export's name, when it differs from the port's through a `map`), or with none and `"unmatched": true`, then the inside's exports no slot port reaches, `"extra": true`, and the level carries `"slot": "<key>"` (`/fx`, `rack/fx`: the slot's address as `describe`'s `content.slots` writes it). `own: false` and a `level` (`/fx`, `rack/fx`, a key no composite can have): the slot has no own inside yet, and **`insides`** (a new top-level field, absent when no slot has one) gives that level read-only, with the same frame: what `slot.inside` would make (`make`: `empty`, `copy` of a project or library composite, or `wrap` of a primitive; `name` the composite it would write, as `slot.inside` names it). `level: null`: the slot opens into nothing, `reason` says why (a project as its content). A shared composite's own level in `composites` keeps its exports as they are.
- **A slot's part** (ADR 0046 §6, additive): every slot box's `slot` carries `part`: null without one, else `{"file": "ui/parts/<key>.html", "base": "<sha-256>", "root": "/synth", "controls": [{"tag", "label", "bind" (as written, relative), "binds" (rooted at `root`: `/synth.cutoff`; an address that cannot be rooted is left out), "attributes"}], "error"}` (`error`: the file's `<signal-panel>` marker does not name the slot, or there is none; null otherwise), read with every `graph`. A slot in a composite's level is rooted at that level's instance address.
- `interfaces` (ADR 0037 §3, phase 3, additive): the interface templates a slot may start from, the library's (`lib.deck`, `lib.instrument`, `lib.voice`) then the project's `interfaces/<name>.toml` that read, each in name order: `{"name", "library", "description", "ports", "base"}` (`ports` as `slot.interface.ports`; `base` the file's SHA-256, null for a library template), read with every `graph`.
- `projectId` (M2.9-3): which project folder this is, opaque: the SHA-256 of the folder's canonical path (the path itself is not sent). It tells apart projects whose folders and names are the same; the schematic keeps its undo history for one `projectId` only (`ui-controls.md` "Editing the patch").

Playing, `graph` describes the running project (the last version that loaded, as `describe`); stopped (Signal.app), the folder as it is now. A folder that does not load is `{"type": "error", "code": "does-not-load", "message": <its diagnostics, one per line>}`; Signal.app without a project open answers `no-project`.

**Cached** (M2.9-1b): the structure is built once per running plan version, and stopped once per state of the folder (each file's modification time and length, `ui/schematic.toml` aside), which opening the project and playing it record from the load they already do; the positions are read with every `graph`. So a `graph`, a `schematic.move` (one write, no load), `app.power`, `transport.stop` or `project.open` loads nothing the folder did not change for. The load is counted by a test hook (`Host::graph_counts`).

**Pushed** (without `id`) after every plan swap (once it commits, beside `describe`), and whenever the `graph` it would give differs from the last pushed (compared by a hash of its text, serialised once for every client): after a reload of the folder (an edit of `ui/schematic.toml` included), after `transport.*`, `project.open`, `app.power` and `setup.apply` playing again, after each `schematic.move` and `schematic.reset`, after a `commit` or `retry` (their write changes `files`), and after a `patch` (stopped at once, playing once its reload swaps). Stopped, Signal.app watches the folder every 100 ms for the same push; switched off it watches nothing, and switching on pushes what changed meanwhile. When the folder stops loading, the push is `{"type": "graph.error", "folder": <the project folder's name>, "code": "does-not-load", "message": <its diagnostics, one per line>}` (`no-project` without a project), once, and the schematic keeps its last drawing, marked stale, if it is of the same folder (`graph` carries `folder` too; another folder's error clears the drawing); the next `graph` that loads is pushed again. Tests: `crates/signal-project/tests/structure.rs` (`order` of the studio voice's exports, the kick's exports with it) and `crates/signal-project/tests/load.rs` (`group` read from the table form and given in `graph`, the table's keys), `crates/signal-ui/tests/schematic.rs` (kick, pulse, physical-av's converter, the push after a structural reload, positions, the structure built once per plan version) and `crates/signal-ui/tests/app_mode.rs` (stopped, does not load, switched off, the cache, `graph.error`, a `schematic.move` on 4096 voices), both transports; `crates/signal-project/tests/structure.rs`. A 4096-voice project's `graph` is about 6 MB, more than a client's 4 MiB write buffer; it is sent as one message larger than the limit ("Delivery: slow and gone clients").

### `schematic.move`, `schematic.reset`

```json
{"type": "schematic.move", "id": 8, "level": "", "instance": "drums", "x": 120.4, "y": -39.6}
{"type": "schematic.move", "id": 11, "level": "", "moves": [{"instance": "drums", "x": 120, "y": -40}, {"instance": "lfo", "x": 300, "y": 0}]}
{"type": "schematic.reset", "id": 9, "level": "kick"}
{"type": "schematic.reset", "id": 10}
```

`schematic.move` writes instance `instance` of `level` (`""` the top level, else a composite the project uses) at `x`, `y` (finite, at most 1e9 in size, rounded to integers) into `ui/schematic.toml` (`project-format.md` §11), with `toml_edit` and atomically through a hidden temporary file, as `commit` writes; the watch takes the write as seen (no `reload` push), and `graph` is pushed to every client. Reply `{"type": "schematic.moved", "id": 8, "level": "", "instance": "drums", "x": 120, "y": -40, "file": "ui/schematic.toml"}`. The batch form (2026-10-17, a group of boxes dragged together in the schematic) gives `moves`, a non-empty list of `{instance, x, y}` of the same `level`, in place of `instance`, `x` and `y` (any of those beside `moves` is `bad-message`; an instance named twice is `bad-value`): every entry is checked first, as above, and one write holds them all (`set_positions`: the file parsed and written once), so one `graph` is pushed; an entry refused refuses the message and nothing is written. A message is at most 64 KiB ("Limits"), about 1500 moves of short names: the schematic splits a larger group into as few `moves` messages as fit (`moveMessages` in `ui/lib/schematic-select.js`), each its own write and `graph` push (positions are presentation only, so a group need not be written at once), and keeps the boxes of the messages not yet answered where the drag left them meanwhile. Its reply is `{"type": "schematic.moved", "id": 11, "level": "", "moves": [{"instance": "drums", "x": 120, "y": -40}, {"instance": "lfo", "x": 300, "y": 0}], "file": "ui/schematic.toml"}`, the coordinates rounded, in the message's order. Tests: `crates/signal-ui/tests/schematic.rs` (both forms, both transports). Errors: `unknown-level`, `unknown-instance`, `bad-value` (not a finite number, or too large), `bad-message`, `does-not-load`, `write-failed` (also when `ui/` or `ui/schematic.toml` is a link: the file is written only in the project's own `ui/`, and nothing is written). `schematic.reset` removes the table of `level` (it must be a level of the project), or without a `level` the whole file; reply `{"type": "schematic.reset", "level", "file"}`, then the `graph` push. Neither changes the project: the file is presentation only.

### `modules`

`{"type": "modules", "id": 4}` (or `{"type": "modules", "id": 4, "inside": true}`, below) → the module types an instance can be added from (M2.9-3, the schematic's Add module browser and its sidebar, `ui-controls.md` "Editing the patch"):

```json
{"type": "modules", "id": 4,
 "primitives": [{"module": "std.svf", "composite": false, "description": "…",
   "ports": [{"name": "in", "direction": "in", "shape": "signal", "rate": 1, "kind": "audio", "unit": null, "range": null}, …],
   "parameters": [{"name": "cutoff_hz", "kind": "control", "rate": 1, "unit": "Hz", "range": {…}, "default": 1000.0, "combine": "add"}, …]}, …],
 "composites": [{"module": "kick", "composite": true, "description": null, "ports": […], "parameters": […],
   "inside": {"instances": […], "connections": […], "inputs": […], "outputs": […], "parameters": […]}}]}
```

`primitives` are the registry's types; `composites` the project's (every `composites/*.toml`, used or not), then every composite of the built-in library (`lib.<name>`, ADR 0027 §4 and §6, used or not; since the M2.10-4 review), each part in name order. A primitive carries its palette group as `"category"` (ADR 0027 §1, e.g. `"filter"`) when its type has one; the key is absent otherwise. A project composite carries its file's `[composite] category` and `description` (2026-10-27, additive: before, its `description` was always `null` and it had no `category`); without them the key is absent and the description `null`. The schematic groups the project's composites under `project` whatever their category (`ui/lib/schematic-palette.js`); the Add module browser puts them under This project and, when they name one, by category. A library composite's entry is the one `signal modules` gives it: `"library": true`, its `category`, `description` (the composite's text) and content `hash`, its exports as ports and parameters (each parameter's default the composite's own), and, on a validation reference (M2.10-4, `signal_lib::VALIDATION`), `"reference_for": "std.<type>"`, the native type it rebuilds, absent on every other entry. The Add module browser lists library composites under Library, by category, and the validation references in their own category `reference`, listed last; Library starts closed. A `patch` adds one as any type (`instance.add` with `"module": "lib.<name>"`, its parameters its exports). Opening a library composite's inside in the schematic is not offered yet: `graph` lists no `lib.*` level (ADR 0027 §6, a later issue). A primitive's `description` is its descriptor's `doc`, the rustdoc summary that states its formula (`std.add`: `"Adds its two signal inputs: out = a + b."`), which the Add module browser and the sidebar show (ADR 0027 §6); a project composite's is its file's, else `null`. Ports and parameters are what `graph` gives an instance of the type (a composite's: its exports, with the shape of what they reach) **without `address`**: there is no instance. Asked with `"inside": true` (2026-10-27, additive; any other value than a boolean or null is `bad-message`), every composite entry, the project's and the library's, also carries `inside`, for the Add module browser's schematic preview (`ui-controls.md` "Editing the patch"); without it (the sidebar's request, the agent interface's) no entry has it. `inside` is its level exactly as `graph` gives a composite's in `composites` (instances and connections with relative addresses, its exported `inputs`, `outputs` and `parameters` with `order` and `group`), except that the connections' `converters` are always empty (there is no plan). It makes the reply larger (the studio's: about 1.2 MB with it, of which `inside` is about 0.5 MB); the browser asks for it once per state of the project's files (`graph.files`). `signal modules` and the agent interface's `modules` tool and `signal://modules` resource have no `inside`. Tests: `crates/signal-project/tests/structure.rs` (`modules_give_each_composite_its_inside_description_and_category`: the studio voice's `inside` equal to its `graph` level, a library composite's, `signal modules` and `modules_without_inside` without it, a project composite's `description` and `category`), `crates/signal-ui/tests/patch.rs` (`modules` without `inside`, with `inside: true` the same reply with it, a non-boolean refused; both transports), `crates/signal-cli/tests/mcp.rs` (the tool and the resource without it), `ui/controls/module-browser.test.js` (the editor asking with `inside: true`, once per `graph.files`). The registry holds lab types only in a `lab` build. Of the project `graph` describes (playing, the running one; stopped, the folder's, cached with its structure), and the same reply every time. Errors: `does-not-load`, `no-project`.

### `patch`

Patching from the schematic (M2.9-3, ADR 0026 §6): ops written into one level's file **as text**, applied live by the normal reload. Nothing is held anywhere but in the files.

```json
{"type": "patch", "id": 5, "level": "", "base": "<sha-256 of project.toml, from graph.files>", "ops": [
  {"op": "instance.add", "name": "svf", "module": "std.svf", "params": {"cutoff_hz": 800}, "x": 120, "y": -40},
  {"op": "connection.add", "from": "svf.lp", "to": "out.l", "scale": 0.5},
  {"op": "connection.scale", "from": "lfo.out", "to": "drums.kick_decay", "scale": 60},
  {"op": "connection.remove", "from": "transport.beat", "to": "drums.trigger"},
  {"op": "instance.remove", "name": "accent"}]}
```

`level` is `""` (the top level, `project.toml`) or a composite (`composites/<level>.toml`); one patch writes that one file, and `ui/schematic.toml` for positions. `base` is the file's SHA-256 the patch was made against. The ops are applied in order and fail together:

- `instance.add`: `name` (`[a-z][a-z0-9_]*`, unique at the level), `module` (a registry type or a project composite), `params` (optional), `x`, `y` (optional, both or neither: its position, written into `ui/schematic.toml` as `schematic.move` writes it). Written as the last key of `[instances]`, an inline table, its parameters in declared order: `svf = { module = "std.svf", cutoff_hz = 800 }`.
- `instance.remove`: `name`, with every connection to or from it at the level, its parameter values and its position.
- `connection.add`: `from`, `to` (`instance.port`, without a leading `/`), `scale` (optional). The last element of `connections`, on its own line. A connection with the same `from` and `to` as one the level has is `bad-value`.
- `connection.remove`: the first `from` → `to` in source order.
- `connection.scale`: the first `from` → `to`'s `scale`; 1 removes the key.
- **Slots** (ADR 0037 §2, §6–7, phase 3, 2026-10-27; `docs/adr/0037-slots.md` Notes):
  - `slot.add`: `name`, `slot` (optional: a template's name, `"lib.voice"` or `"<name>"` of `interfaces/<name>.toml`, or an interface table such as `{"inputs": {"in": "audio"}, "outputs": {"out": "audio"}}`; absent: `{}`), `load` (optional: a module reference or a project path), `x`, `y` (optional, as `instance.add`'s). Written as `instance.add` writes an instance: `name = { slot = …, load = "…" }`; its inverse is `instance.remove` (a slot is removed as any instance is).
  - `slot.load`: `slot`, `load`, `map` and `set` (optional). Writes `load`: a **Load** into an empty slot, or a **Replace**. Without `map`, the slot's `map` entries whose value the new content does not offer, or whose key is no port of the interface, are removed; without `set`, its `set` keys the new content does not take; a module loaded in place of a project drops `seed`; the reply's `notes` say what was removed. Given, `map` and `set` replace the slot's (`{}` removes the key). The reload that follows applies it live (ADR 0037 §6): a Load is one swap whose content fades in; a Replace is an unload then a load, one frame apart (the old content fades out, the new one in, no state carried over); the `reload` message says so (`replaced`, `loadSwap`).
  - `slot.unload`: `slot`. Removes `load` (and `seed`); `map` and `set` stay, for what is loaded next. `bad-value` for an empty slot.
  - `slot.map`: `slot`, `map` (`{port: "<content name>" | false}`; `{}` removes it). A key that is no port or parameter of the interface is `bad-value`.
  - `slot.interface` (each renamed key keeps its place; one op renames each port once, a chain such as `{x: z, z: w}` is `bad-value`: rename in separate ops, applied in order; a renamed interface parameter's `snapshot_exclude` entry follows it, a removed one's goes): `slot`, and `add` (`[{name, role: "input" | "output" | "parameter", shape?, rate?, kind?, unit?, range?, group?}]`), `remove` (`[names]`: an own entry deleted, a template's port named in the slot's `remove`), `rename` (`{old: new}`: the level's wires and `[exports]` on it, its `map` key and an interface parameter's value follow in the same write, then the panels' bindings, below; a loaded slot's port matched by name gets `map.<new> = "<old>"`, keeping its match), `retype` (`[{name, …the fields that change}]`), `removeWires` (true: the wires on removed ports are removed too; without it a removal a wire names is `in-use`, naming the wires; a port the level's `[exports]` name is `in-use` either way), or alone `detach` (true: the resolved interface written inline, without `from` and `remove`) or `template` (`"<name>"`: `slot = "<name>"`). Applied in that order: remove, rename, add, retype.
  - `slot.restore` (inverse-only, as `edits`): `slot`, `changes` (`[{path, value, at}]`: a key of the slot's entry by its path, `["slot", "inputs", "x"]`, its value as TOML text, null to remove it, `at` its place among its table's keys, `decor` in a section the key line's spacing and comments as written: `[key prefix, key suffix, value prefix, value suffix]`) and `wires` (`{port: port}`, renamed back). It may write only the slot's own keys (`slot`, `load`, `map`, `set`, `seed`, `snapshot_exclude`, its interface parameters' values) and the wires on its ports, its `decor` spacing and comments only (`bad-value` otherwise; every slot op checks that the file outside the slot's entry, wires renamed aside, is unchanged); an undo gives back each value byte for byte, in its place; a key a section held comes back inline.
  - `slot.group` (ADR 0046 §8): `instance`, `controls?` (indexes among `ui/main.html`'s controls, as `panel.check` counts them; absent: all). Makes the instance a slot holding what it was, with the same names: its `module` (or `project`) key becomes `slot = { … }` in its place followed by `load` (a bare project name `./<name>`; `seed` and `set` kept), every other key in its place; the interface names every port a wire, an `[exports]` target or a panel binding at the level names (auto, `{}`) and every parameter the entry sets or a wire, export or binding names. The plan is byte-identical. Refused (`bad-value`): a slot already; an instance with `pattern` or `gpu`; content that does not resolve (`unknown-module`). At the top level the host also moves the main panel's controls whose every bind lies in the instance into `ui/parts/<instance>.html`, binds made relative, the open slot card `<signal-slot bind="/<instance>">` in the place of a card left with nothing but moved controls (the part keeps its heading, and `ui/windows.toml`'s card ids follow, `<instance>:<id>`) or after a card that keeps other controls; a main panel the editor cannot read is left as it is (a `notes` line); an existing part file is `bad-value`. These are the patch's other files; the inverse is a `slot.restore` writing the `module` or `project` key back and a `panel.restore` per file.
  - `panel.restore` (inverse-only): `file` (`main.html`, `windows.toml` or `parts/<key>.html`, under `ui/`), `text` (absent: removed), `was` (absent: it does not exist). It writes the file while it holds `was` (`bad-value` otherwise). The host takes whole a text one of its own patches wrote or replaced (an undo or redo it made; a hand-written part removed with its slot included); any other text from a client holds only what the panel editor writes: an HTML file's `<signal-panel>` content in its canonical form (no comment), its text outside that element what the file holds now (a part that does not exist: exactly as a new part is written), and a `windows.toml` that reads as TOML. A part whose removal was kept is left out of the reply's `inverse`.
  - A slot deleted (`instance.remove` of a slot) takes its part with it (another file of the patch); the undo gives it back byte for byte (a `panel.restore`). Every interface edit that drops a name the slot's part binds (`.p`: `slot.interface`'s `remove`, `template`, `detach`, a `slot.restore`) is `in-use`, naming the part's controls, unless `removeControls` (true, on `slot.interface`), which removes them from the part in the same patch; a `rename` onto a name the part binds already is `bad-value`; a `rename` rewrites the part's `.old` binds to `.new` after the level's file, as the host panels' bindings are rewritten, and the reply's `panels` names it.
  - `slot.inside` (ADR 0037 "Editable insides", 2026-10-27): `slot`, `name` (optional). Makes the slot's **own inside**, `composites/<name>.toml` (default `<slot>_inside`, in a composite level `<level>_<slot>_inside`, then `_2`, `_3`, … while a project file or a library composite has the name; a given `name` that is taken or invalid is `bad-value`), from what the slot holds: nothing (an empty composite), a project composite or a `lib.*` composite (its text copied, every comment and range kept, `[composite] name` set), or a primitive (wrapped: one instance of it named after its type, every port and parameter exported); `[composite] inside_of` names the slot, its exports are renamed after the slot's ports through the match (one content output under two slot outputs becomes two exports), and the slot then `load`s it, its `map` removed (`set`, `seed` and the interface's values kept). The plan is byte-identical but for a wrapped primitive, which plans one level down (`/fx` → `/fx/gain`) and plays the same. A project as content (`./x`, `../x`) and an inside already the slot's own are `bad-value`. A composite whose `inside_of` names a slot may be loaded by that slot only (`does-not-load` otherwise, at the reference), and `modules` gives such a composite `inside_of` (additive) so the browsers list it for its slot only. A second file of the patch (below); its inverse is a `slot.restore` and a `composite.file` that removes the file.
  - `composite.file` (inverse-only): `name`, `text` (absent: the file removed), `was` (absent: it does not exist). Writes a slot's own inside's whole file, only while it holds `was`, and only a composite whose text, before and after, has the same `inside_of`, naming a slot at the patch's level; never the patch's own level, nor a new file under a library composite's name (`bad-value` otherwise).
  - **A slot op on a slot that loads its own inside keeps the inside in step**: `slot.interface`'s `remove` removes the inside's export of the port (its content's name), `rename` renames it in its place (no `map` entry is written: the plan does not change; a new name the inside exports already is `bad-value`; the `map` values naming the renamed export follow it, and a removed port's export stays while another port matches it through its `map`); `add` and `retype` leave the inside as it is (a new port is unmatched until it is wired inside). The inside's file is the patch's second file; the inverse holds its whole text (`composite.file`).
  - `export.connect`, `export.disconnect` (ADR 0037 "Editable insides"; at a composite level only, `bad-value` at the top): `role` (`input`, `output`, `parameter`), `name` (the export), `port` (`instance.port` at the level, `unknown-instance` for an instance it lacks). Wires a frame pin to an inner port: an input's or a parameter's targets gain `port` (a string, then a list), an output becomes `port` (a second source is `bad-value`: an exported output names one port); disconnect takes `port` out and the export goes with its last port. The table form keeps its `group`, `min`, `max` and `values`. Written key by key with `toml_edit` (`[exports]` made at the file's end when it has none); its inverse is `export.restore`.
  - `export.restore` (inverse-only): `changes` as `slot.restore`'s, with paths from the file's root (`["exports", "<inputs|outputs|parameters>", "<name>"]`, or `["exports"]`, the table made or removed empty); it may write only `[exports]` (`bad-value` otherwise; the file outside it is checked unchanged). A role table emptied stays (`inputs = {}`), so an undo is byte for byte in every form.

  A slot op on an instance that is no slot is `bad-value`; on a name the level lacks, `unknown-instance`. A rename's reply names the panels whose bindings it rewrote, `"panels": ["ui/main.html"]`: every `bind` address equal to `/<slot>.<old>` (through every instance path of a composite level), rewritten after the level's file, each panel compared once more just before its rename (ADR 0040); each rewritten panel is pushed to every client as `panel.written` (as `panel.write`); a panel that cannot be rewritten (changed meanwhile, reached through a link, unreadable) is a `notes` line, the rename stands, and its undo renames back the same way. At the top level, `snapshots.toml`'s values of a renamed interface parameter move to its new address (`"/fx.volume"` → `"/fx.amount"`, every snapshot and the undo snapshot) and a removed one's go, in the order the ops did them (an op's removals before its renames), written whole in its canonical text under the same writer lock (ADR 0041) and pushed to every client as the `snapshots` list, and the reply says `"snapshots": "snapshots.toml"`; a patch that moves no value leaves the file as it is; an undo of the removal does not bring the values back.

**The text.** The file is located with `toml_edit` and edited as whole lines; every other byte is kept: comments, order, formatting. A removed entry takes its own lines (its trailing comment included) and the comment lines directly above it (a section, `[instances.x]` or `[[wiring.connections]]`, also one blank line above); never a neighbour's. An entry sharing a line with others takes the separator next to it, never a comment there. Every form a project may be written in is edited: `[instances]` keys, `[instances.x]` sections, dotted keys (also when an instance's lines lie among other entries: each line is removed, and restored, in its place), inline `instances = {…}`; `connections` on one line or many, with or without a trailing comma, empty, as `[[wiring.connections]]` sections (where a new connection is a section, as TOML cannot mix the two), `[wiring]` without `connections` and no `[wiring]` at all (created after the instances: `[wiring]` and `connections = [` with one element per line). A file whose instances are all `[instances.x]` sections gets an `[instances]` table after them for the new inline entry. A connection added to a single-line array starts a new line.

**The server**, before writing anything:

1. takes the level's file from the files the project has (`unknown-level` otherwise; a file or `composites/` reached through a link is refused: `signal ui` writes only the project it serves);
2. refuses a file that changed since `base` with `conflict`, carrying the current `base` (and `level`, `file`);
3. applies the ops (`unknown-instance`, `unknown-module`, `bad-value`);
4. refuses removing an instance that a composite's `[exports]` or a panel binding in `ui/*.html` names (through every instance of the composite; the edited project's when the current one does not load, and, when the patch has export ops, the edited project's when it loads: an export disconnected in the same patch no longer names it) with `in-use` and `references: [{file, line?, text}]`;
5. loads the edited project in memory with the same validation and compile as a reload, the whole project for a composite's edit, and while playing the same checks a live reload makes (the audio sink kept): `does-not-load` with `diagnostics` (one per line, `file:line:column`);
6. computes the requests that undo and redo the patch (below), with room for every parameter its instances could be committed with meanwhile: a patch whose undo or redo would be larger than a client message (64 KiB) is `bad-value` ("not written: undoing this patch needs a message of N bytes, over the 64 KiB limit"), so every written patch can be undone;
7. refuses a patch that moves a position when `ui/` or `ui/schematic.toml` is a link (`write-failed`: positions are written only in the project's own `ui/`), and reads the level's file again, under the project's writer lock (ADR 0040): one that changed since step 2 is `conflict`, as there, and so is a patch that moves a position when `ui/schematic.toml` is no longer the text the patch was built on (a `schematic.move` from elsewhere meanwhile), whose `conflict` names the level's file and its `base` (unchanged), as every `conflict` does, so a client builds the patch again on that base and the positions as they are now;
8. writes the level's file atomically (a hidden temporary file, synced and renamed, as `commit` writes), then `ui/schematic.toml` (taken as seen by the watch); if the second write fails, the first file's previous bytes are written back, only while it still holds the patch, and the patch is `write-failed`. Each of the two files is compared once more just before it is renamed or removed (ADR 0040): a positions file changed in that instant, or a level's file changed before it is put back (the other writer's edit is kept), makes it `conflict` instead, with the level's file and its current `base`.
9. (ADR 0037, editable insides) writes the patch's **other files** (a slot's own inside: `slot.inside`, `composite.file`, a slot op keeping an inside in step) under the same lock: each is first checked to hold the text it was read with (`conflict` otherwise, nothing written) and not to be reached through a link (`write-failed`); a new or changed one is written before the level's file (which may name it), each compared once more just before its rename; a removed one after it (one that changed meanwhile is kept, and a `notes` line says so). A failure before the level's file is written puts back those already written, only while they hold the patch. A kept removal's entry in the reply's `files` gives the file's current base. The edited project of step 5 includes them, and the undo of step 6 is tried on the files as the patch leaves them.

Playing, the watch's reload then applies the file live (swap, fades, `reload` push) and `graph` is pushed once it swaps; stopped (Signal.app), `graph` is pushed at once. A `.signal` project's working folder then differs from its file: the project is edited.

Reply: `{"type": "patched", "id": 5, "level": "", "file": "project.toml", "base": "<sha-256 of the written file>", "inverse": [ops]}`, with (ADR 0037 phase 3, additive) `notes` (what a slot op says it did besides: a Replace's removed `map` and `set` entries, a panel not rebound, a slot's own inside made), `panels` (the panels a rename rebound), `snapshots` (when `snapshots.toml`'s values followed) and (editable insides, additive) `files`, the other files written, `[{"file": "composites/fx_inside.toml", "level": "fx_inside", "base": "<sha-256>" | null}]` (null: removed), each the `base` of its level's next patch, when there are any. Every other client learns of it from the `graph` push.

**Undo and redo.** `inverse` undoes the patch: sent as a patch with the file's newest SHA-256 (the reply's `base`, or a later `graph.files`), its reply's `inverse` redoes it, and so on. The ops of an inverse carry two **inverse-only** fields that the server writes and the page sends back unchanged: `edits`, the exact text edits that restore the bytes (`{"edit": "insert" | "delete", "at": {"item", "offset"}, "text"}` or `{"edit": "cut", "item", "before", "after"}`, each anchored to an entry (`instance:<name>`, `instance:<name>#<n>` for line `n` of an instance written as dotted keys, `connection:<index>`), a table header (`table:<path>`), the connections array (`array`) or the file's start (`file`), so a `commit` between a patch and its undo moves nothing), and on instance ops `layout` (`{"edits", "created"}`: the same for `ui/schematic.toml`; `created` removes the file when the edits leave it empty). An undo restores the file byte for byte, comments and order included; a parameter committed meanwhile is kept. Ops that carry `edits` are not trusted: every position must fall inside the file on a character boundary (an offset that overflows or splits a character is refused), every `delete` and `cut` must name the bytes there, a `delete` stays inside one gap between entries and a `cut` touches no other entry (`bad-value` otherwise), and the change must be exactly what the op's forward rule would make, in one direction or the other, the whole file compared byte for byte; `layout` the same, for the op's instance's position at the op's level. So `edits` can write nothing but what the op means, the comment lines directly above a restored entry and that entry's `gpu` pin, and the load in step 5 checks them.

### Schematic level bars

The schematic's level bars (`ui-controls.md` "Schematic", since 2026-10-25 the selected instance's only) are `scope` streams of its signal inputs and outputs on screen (a closed composite's: the primitive port its export reaches, an input's first target), at 7680 points per second, and one `parameters` stream of its parameters. The scopes share the run's 8 scope slots with every other scope of every client (the Panel tab's included), so the schematic takes them in order, inputs then outputs, top to bottom, and lets a slot go when its port leaves the screen, when it is hidden, when the power is off and when nothing plays. A port it cannot get a slot for shows its bar marked **no slot**, the same size as a live one; while stopped every bar is **idle**.

**Who gets a slot first** (M2.9-1b): panel scopes, then schematic bars. The schematic asks only for the slots the host says are free: `describe.scopes` gives `free` and `sinceFreedMs` (the milliseconds since the free count last rose, null before it ever did), and the host pushes `{"type": "scopes", "slots": 8, "free": 3, "sinceFreedMs": 0}` whenever the free count changes; the latest push wins over `describe`, and the schematic counts its own requests since then against it. It takes a freed slot only 2.5 s after the free count rose, whoever freed it, at its own start too, while a `<signal-scope>` refused a slot asks again every 2 s: a panel scope waiting for a slot gets it first. A slot the schematic gives up and takes again in the same redraw (one port leaves the screen as another comes on) is swapped at once; a port that comes on screen later can wait up to 2.5 s for its bar. The schematic never gives up a slot it holds for a panel scope: one opened after the schematic took every free slot waits until the schematic lets one go (a port leaves the screen, the tab is hidden, the power is off). A refused port (`no-scope-slot` or `busy`) is not asked again within 2 s, and no timer runs while no slot is free: the next `scopes` push says when one is. Tests: `ui/lib/schematic-levels.test.js` (the order, the delays, a lost race), `ui/lib/trigger.test.js` (the scope's retry), `crates/signal-ui/tests/protocol.rs` (the free count, both transports). A slot samples its port at its decimated frames, so a divided-rate output (its value held between its ticks, `semantics.md` §1) has a level too. This limit was accepted for M2.9-1 (operator decision, 2026-10-16); a stream of levels for every port would be a new stream kind.

### `subscribe`, `unsubscribe`

`{"type": "subscribe", "stream": …, "id": 2}` → `{"type": "subscribed", "id": 2, "sub": 5, "stream": …}`; the stream's frames carry `sub`. `{"type": "unsubscribe", "sub": 5}` → `{"type": "unsubscribed", "sub": 5}`. A client's subscriptions end with its connection.

ADR 0037 §7 (phase 3): a `scope` or `vector` stream's `port`, and a `trigger`'s `address`, may name a top-level slot's input or output (`/fx.y`): it is taken through the slot's match to the plan port behind the content's port (a composite's export followed to its primitive), and the reply names the port as asked. A slot port that reaches nothing now (the slot empty, the port unmatched) is refused with `inactive`, saying why. A slot's interface parameters are controls (`describe.controls`, `/fx.volume`), set, ramped and committed as any.

| `stream` | Fields | Frames |
|---|---|---|
| `parameters` | `addresses`: controls or plan parameter ports; `rate`: frames per second, at least 1 (default 30; more than 60 is taken as 60; below 1, not a number or not finite: `bad-rate`) | kind 3, every `1/rate` s: each address's base and effective value, as the runner last reported them (the parameter observation queue: up to 64 parameters per callback, round robin) |
| `meters` | `source`: `"output"` (default, the audio sink's channels) or `"input"` (the Setup's input, metered only); `rate` as above | kind 1, every `1/rate` s once levels arrived: per channel, the peak and the RMS over the callbacks since the last frame |
| `vector` | `port`: a vector output of the running plan (at most 512 elements); `rate`: snapshots per second (default 60; at least 1, else `bad-rate`; at most the port's tick rate, the sample rate over its rate divisor) | kind 4, one per snapshot: the port's elements at one frame, at every frame that is a multiple of `decimation`, a whole number of the port's ticks (`decimation = d · max(1, round(sampleRate / (d · rate)))`); the reply also gives `rows`, `decimation` and the `slot` |
| `scope` | `port`: a signal output of the running plan (`/a.out`), or a signal input (`/out.l`: the sum of its sources, each scaled, as the instance receives it); `rate`: points per second, at least 1 (default and at most the sample rate; below 1, not a number or not finite: `bad-rate`) | kind 2: blocks of 256 consecutive points, one every `decimation` frames, `decimation = max(1, round(sampleRate / rate))`; the reply also gives `decimation` and the `slot` |

**Vector streams** (M2.8-7) come from the vector adapter in `signal-output` (`crates/signal-output/src/vectors.rs`): the audio thread copies the port's elements at each snapshot frame, absolute and on the port's ticks, so a stream depends neither on the callbacks nor on when it was started, into a preallocated queue (a full queue drops the snapshot and counts it, `stats`' `vectorOverflows`). It allocates nothing there (`crates/signal-output/tests/vector_no_allocation.rs`). There are 8 slots per run (`no-vector-slot`); `describe` says so (`"vectors": {"slots": 8, "maxRows": 512}`). After a swap that removes the port the server pushes `{"type": "vector.unbound", "sub": 5, "reason": "absent"}`, and `vector.bound` when it is back. A stream is also unbound, never sampled, while the running plan gives its port a rate divisor its decimation is not a multiple of (`"reason": "decimation"`, M2.8-9: the decimation is checked again in every plan the run swaps to), or before its slot has heard of the running plan (`"unverified"`) (`crates/signal-output/tests/vector_swaps.rs`). A slot reads its port only while the port has exactly the elements the stream was started with, so it never carries another port's rows: when a swap gives the port another number of elements or another rate divisor (its instance retyped), the server pushes `{"type": "vector.reshaped", "sub": 5, "rows": 12, "decimation": 800}` and the stream carries the new width from then on (`crates/signal-ui/tests/protocol.rs`, `a_vector_stream_follows_a_swap_that_changes_its_width`; the adapter and the replay's taps: `crates/signal-cli/tests/physical_av.rs`). Errors: `not-a-vector-output`, `bad-rate`, `busy`. A replay can take the same snapshots offline (`ReplayOptions::vectors`), which is how a recorded session is shown to reproduce them (`crates/signal-cli/tests/physical_av.rs`). In `describe`, a vector port's `shape` is `{"vector": N}` and its `rate` the divisor.

**Scope streams** come from the scope adapter in `signal-output` (beside the audio adapter of ADR 0022): a decimated capture. A point is the port's value at an absolute frame that is a multiple of the decimation, so a stream does not depend on how the frames were split into callbacks or threads. **A scope stream is the output as its readers see it, fades included** (a signal input, the sum of its sources as they are read): it fades in when its instance is added, out when it is suspended or removed, and through the 64-frame fault fade after a fault (`semantics.md` §12, §14). It costs the audio thread a copy per point and allocates nothing there (measured: `crates/signal-output/tests/scope_no_allocation.rs`). **An open block is dropped, not sent, at a discontinuity**: when a swap rebinds the slot, when the slot is started again (a new `subscribe`, or `setup.apply` playing again), and when the points stop being consecutive (frames not run). So up to 255 points are lost there, and every block that arrives is 256 consecutive points. There are 8 slots per run (`no-scope-slot` when they are all in use; how many are free is in `describe.scopes.free` and the pushed `scopes`, "Schematic level bars"). After a swap that removes the port the server pushes `{"type": "scope.unbound", "sub": 5}`, and `scope.bound` when a later swap brings it back. Errors: `not-a-signal-output` (neither a signal output nor a signal input), `bad-rate`, `busy` (too many scope commands outstanding; try again).

### `set`, `ramp`, `trigger`

Live edits through the run's `Controller`, the path the parameter panel takes:

```json
{"type": "set", "id": 3, "address": "/out.gain", "value": 0.25}
{"type": "ramp", "id": 4, "address": "/drums.kick_decay", "to": 300, "ms": 5}
{"type": "trigger", "id": 5, "address": "/accent.trigger"}
```

`address` is a control (to every one of its ports) or a plan parameter port; `trigger` takes an event input of the plan. Values are clamped to the range; a ramp takes `frames`, or `ms`, or the panel's 5 ms. `at` (a frame) stamps the edit; without it the edit gets the default stamp (the current frame plus the latency). Once the runner has reported every command of the edit:

```json
{"type": "ack", "id": 3, "frame": 12544, "requested": 12544, "late": false, "outcome": "scheduled"}
```

`frame` is the **effective frame** (the latest of its ports'), `requested` the stamp's; `late` when it applied after it was requested. `outcome` is `refused` when the runner refused a command, and `abandoned` when the run stopped first (`setup.apply`). A command the Controller cannot take now is answered with `{"type": "error", "code": "refused", …}`. Errors: `unknown-address`, `bad-value`, `not-playing`.

### `note`

A live note (ADR 0039), the piano roll's keys: an event input named `audition` of the plan (`std.note_seq`'s; any other event input is refused, since the value would be a huge impulse or a tick count there) takes its value (`module-contract.md`), through the Controller as `trigger` goes, acknowledged the same way:

```json
{"type": "note", "id": 8, "address": "/melody.audition", "key": 72, "velocity": 0.8, "on": true}
{"type": "note", "id": 9, "address": "/melody.audition", "key": 72, "on": false}
```

`key` is an integer from 0 to 127, `on` true starts the note and false ends it, `velocity` (0 to 1, clamped; without it 0.8, the piano roll's default note's) is for a note on. The server sends `Set(128·key + v)` to `address`, `v` the velocity in 127ths (1 to 127; 0 for a note off: `signal_std::audition_value`), with `at` as for the others. **Never saved**: it is no parameter, so nothing is unsaved and nothing is written; a session records it as the `set` of an event input it is (`session-format.md`), and replays it. **A held note never outlives its client**: the server keeps each client's held notes (one per port, the last note on; a note off removes it only when its key is the held one, so the off of a key slid away from, or of another roll's key on the same port, leaves the held key) and, when the client goes or is evicted (a closed page, a lost connection, a socket that takes nothing), sends their note offs itself; one the Controller refuses (its command queue full) waits on the control side and is sent again at the start of every step, before any client's message, until it is taken (external review, 2026-10-31; at most one per port and key). A note off the Controller refused stays held there too (the piano roll sends it once more after 100 ms). A stopped or replaced run forgets them (the sequencer is gone with it). Errors: `unknown-address` (not an event input of the running plan), `not-an-audition-input` (an event input not named `audition`), `bad-value` (a key, `on` or a velocity of the wrong kind), `bad-address`, `not-playing`, `refused`. `ui/signal-ui.js`'s `Connection.note(address, key, {velocity, on, at})`. Not a tool of `signal mcp` (`agent-interface.md`). Tests: `crates/signal-ui/tests/protocol.rs` (`a_note_sounds_while_held_and_ends_when_its_client_goes`, both transports).

### `commit`

```json
{"type": "commit", "id": 6, "address": "/out.gain", "value": 0.25}
```

Writes a control's value into the project's `project.toml` (`value: null` removes the key: each port back to its own default), with `toml_edit` as the M2.5 panel does: only that key changes, the file is written atomically through a hidden temporary file. The value is applied live too, unless it is exactly the last value sent to every port; the running project then takes the same edit, so **nothing is applied twice**: when the live send was taken, the text this write read is exactly the text the running project was loaded or last reloaded from (or last committed), and the file still reads as written right after the write, the watch takes the written file as seen and does not reload it (no `reload` push). Otherwise (the send was refused, or another writer's edit is in the file) the watch reloads it and applies what differs from the running project. The comparison is of content, not of modification times. Reply:

```json
{"type": "committed", "id": 6, "address": "/out.gain", "value": 0.25, "file": "project.toml", "writes": 1, "sent": true, "note": null}
```

Only controls are committed (`not-editable` otherwise): a parameter inside a composite is set in the composite's file, and writing it there would change every instance of the composite.

A write that fails (a read-only folder, a full disk) answers `{"type": "error", "code": "write-failed", "message": …}`, and the value the commit sent live **stays live and unsaved** (below): it is never quietly taken as saved. So does a `conflict`: the commit's edit is based on `project.toml` as it reads it, under the project's writer lock (ADR 0040), and the file is read once more just before the rename; one that no longer holds that text (a writer that takes no lock, such as an editor, or any writer on a volume without locks) writes nothing, and the next `commit` or `retry` reads it again.

### Unsaved: `unsaved`, `retry`, `revert`

The live state and the project's text may differ (ADR 0009, 0013), but never silently: **the host knows every parameter whose live value the file does not hold, or may not hold, and tells every client** — in `describe` (`unsaved`) and as a push whenever it changes, so a second client or a reloaded page sees the same. Clients hold no state of their own about it.

```json
{"type": "unsaved", "count": 1, "lastError": "out.gain was not written to …/project.toml: Permission denied (os error 13)",
 "parameters": [{"address": "/out.gain", "file": 0.5, "inFile": true, "control": true, "applied": true,
   "error": "out.gain was not written to …/project.toml: Permission denied (os error 13)"}]}
```

A parameter is listed while:

- **a control's latest live value is not the file's** (`file`: the file's value, or the default without a key): an edit not committed yet (a drag in progress, a `set` or `ramp`), or one whose write failed (`error`: the write's error). Each new `set`, `ramp` or `commit` replaces the live value: `retry` writes the newest one, never an older failed one.
- **its latest live value did not reach every port** (`applied: false`): the Controller refused it (`refused`), a runner refused it after (the edit's ack is `refused`), or a commit was written while its live send was refused (until the reload of the written file sends every port the file's value). It stays listed whatever its value until a send of it is taken: a refused `set` back to the file's value does not make it saved, since the ports still hold what they held. `describe`'s `base` is then the last value the Controller took for every port: one it refused is never the base, but one a runner refused after the Controller took it is (it is listed `applied: false`), and stays so through later sends the Controller refuses. A plan parameter port that is no control has no live base in `describe`: `instances` gives the plan's base whatever was sent. (Through this protocol a runner does not refuse a `set`: the Controller keeps at most as many commands in flight as the engine's event queue holds.)
- **a failed reset** (`commit` of `null`) leaves each port at its default while the file has the key.
- **a plan parameter port that is no control** was edited live (`control: false`): its value is in a composite's file, which the protocol never writes; it can be reverted, not retried.

`count` is the number listed; `lastError` the most recent error still listed. A parameter whose live and file values agree again (moved back to the file's value, with that send taken) is no longer listed, and its error goes with it. A reload whose file changes a listed parameter's value sends the file's value and so clears it; a reload of other keys keeps it. A new run of the same project (`transport.play`, `setup.apply` playing again) plays the file and the host plays every listed control's live value again in it, so it stays live and unsaved; `transport.stop` keeps them, and opening another project (`project.open`) lets them go and says how many in `app`'s `message`.

| Message | Does | Reply |
|---|---|---|
| `{"type": "retry", "address": "/out.gain"}` | Commits the control's live value again (the latest one; after a failed reset, `null`), sending it live first unless every port already took it. A send the Controller refuses writes nothing (`refused`) | `committed`, as for `commit`; errors `write-failed` and `conflict` (still unsaved, with the new error), `refused`, `not-editable` (a plan port that is no control), `not-unsaved` |
| `{"type": "revert", "address": "/out.gain"}` | Sends each port the file's value (each port its own default without a key; a plan port the plan's base), and the parameter is saved. Stopped, it only clears | `{"type": "reverted", "address", "value": <the file's value or null>, "sent": <whether it played>}`; errors `refused` (still unsaved, its ports in doubt), `not-unsaved` |

Tests: `crates/signal-ui/tests/unsaved.rs` (a read-only project folder: `write-failed`, listed in `describe` and pushed to every client, retry once writable, revert, a newer edit replacing the failed value, a refused edit back to the file's value staying unsaved, a reload), `crates/signal-ui/src/panel.rs` (`the_base_is_the_last_value_the_controller_took`: a value a runner refused stays the base), `crates/signal-ui/tests/app_mode.rs` (a failed write while stopped is still unsaved when playing).

### Snapshots: `snapshot.list`, `snapshot.save`, `snapshot.restore`, `snapshot.undo`, `snapshot.move`, `snapshot.transition`, `snapshot.delete`, `snapshot.exclude`, pushed `snapshots`

ADR 0041, `project-format.md` §16: every control's value stored under a name in the project's `snapshots.toml`.

```json
{"type": "snapshot.list", "id": 20}
```

→ `{"type": "snapshots", "id": 20, "file": "snapshots.toml", "base": "<sha-256 of the file, or null without one>", "snapshots": [{"name": "Verse A", "count": 5, "values": {"/a.freq": 440, "/out.gain": 0.5}}], "undo": true, "undoCount": 5, "undoValues": {"/a.freq": 330, …}}`, the snapshots in the list's order (ADR 0041 §9); `undo` says whether there is an undo snapshot (`undoValues` null without one), listed apart from the named ones. `describe.controls[]` has `inSnapshots`: whether the control goes into snapshots. **Pushed** (without `id`) to every client after each snapshot write, so another window shows it at once. An edit of the file by another program is not pushed; the reload of the folder that follows it (`reload` while playing, `graph` while stopped) is the client's cue to list again (Signal.app's card does). A `snapshots.toml` that is a symbolic link is never read: `snapshot.list` (and every other snapshot message) is `bad-value`, without the target's text.

| Message | Does | Reply |
|---|---|---|
| `{"type": "snapshot.save", "name": "Verse A", "overwrite": false, "base": "…"}` | Saves every control (`describe.controls`) with its live base (`describe`'s `base`: an unsaved live value as it plays; a modulated control's base, never its signal) under `name`. `overwrite` (default false) replaces a snapshot of that name | `{"type": "snapshot.saved", "name", "count", "replaced", "base"}` (`name` as trimmed; `base` the SHA-256 of the file as this save left it: the bytes written, or the bytes read under the lock when they already held it) |
| `{"type": "snapshot.restore", "name": "Verse A", "base": "…"}` | First writes the values playing now of the controls this restore can change (its entries that exist and go into snapshots) as the undo snapshot (`[undo]`), in the write that reads the snapshot (none to change: the undo snapshot stays as it was): a write that fails or is a `conflict` restores nothing, and the error says why. Both writes are under one writer lock. If the `project.toml` write fails, every value is still sent; playing, the new undo snapshot is kept (it holds what played before, perhaps saved nowhere), and only when nothing reached an engine (stopped) is `snapshots.toml` put back to the undo snapshot from before. `undoSnapshot` in the reply (and in a failed restore's error) says which undo snapshot `snapshots.toml` holds afterwards: `new` (the one this restore wrote), `previous` (the one from before, put back), `unchanged` (none was written: the restore could change no control, or the values were the same) or `changed` (another writer changed the file meanwhile, so it was left as it is). Then writes each value that differs from the file into `project.toml` where `commit` writes it, all in one write (one read, edit and rename under the writer lock, ADR 0040), and sends each live as `commit` does (a 5 ms ramp; a control the file already holds but whose live value differs is only sent). The running project takes the same edit, so the reload applies nothing twice. Values are clamped to their control's range; entries whose instance or parameter is gone, or that are no control, are skipped, and so are those of a control left out of snapshots (reason `excluded`); controls the snapshot does not name are left alone. Which values are written is decided on `project.toml` as read under the lock, and while nothing plays the panel is first read again from the folder, so an edit by another program is seen. A refused send leaves its value live and unsaved as after a `commit` ("Unsaved"). **A failed write** (`write-failed`, `conflict`) still sends every value, each one the file did not hold staying live and unsaved with the error, as after a failed `commit`; the error carries `name`, `restored`, `unwritten` (the addresses not written), `sent`, `skipped` and `clamped` | `{"type": "snapshot.restored", "name", "restored": <entries applied>, "written": [<addresses written>], "file": "project.toml", "sent": <every send taken>, "skipped": [{"address", "reason"}], "clamped": [{"address", "value", "to"}], "undoSnapshot", "transitionMs": <the transition used>, "note"}`. `describe` is pushed once, after every value is written and sent, whenever anything was written or sent; `graph` (its `files` naming the new SHA-256) only when `project.toml` was written |
| `{"type": "snapshot.undo", "base": "…"}` | ADR 0041 §7: restores the undo snapshot, the values the last restore (or undo) replaced, as `snapshot.restore` restores a snapshot, after the values playing now take its place (so a second undo redoes) | `{"type": "snapshot.undone", "name": "undo", …}` with `snapshot.restored`'s fields; `unknown-snapshot` when there is none |
| `{"type": "snapshot.exclude", "address": "/transport.run", "exclude": true}` | ADR 0041 §8: leaves a control out of snapshots (`exclude` true, the default) or puts it back (false): its name added to or removed from its instance's `snapshot_exclude` in `project.toml` (`project-format.md` §4), under the writer lock, compared just before the rename. It is checked on the text read under the lock, the project loaded and planned with it, before the rename (`does-not-load` when it would not plan). Nothing is sent and nothing plays differently: the running project takes the same edit of its own text, so the watch reloads nothing unless something else changed (an edit not applied yet is still applied by it). `describe` and `graph` are pushed when the file changed; in a project that includes others the running project is not rebuilt (the watch's reload applies the file), but the panel is, and both are pushed at once. `exclude: false` needs no control: a stale name (no parameter any more) is removed so, as long as the project plans afterwards | `{"type": "snapshot.excluded", "address", "exclude", "inSnapshots", "file": "project.toml", "written"}` (`written` false when the file already said so); errors `bad-address`, `not-editable` (no control), `bad-value`, `conflict`, `write-failed` |
| `{"type": "snapshot.transition", "ms": 2000, "base": "…"}` | ADR 0041 §10: the snapshot transition time, a whole number of ms from 0 to 60000, kept as `transition_ms` in `snapshots.toml` | `{"type": "snapshot.transition", "ms", "base"}`; every client is pushed `snapshots` (with `transitionMs`); errors `bad-value`, `conflict`, `does-not-load`, `write-failed` |
| `{"type": "snapshot.move", "name": "Bridge", "to": 0, "base": "…"}` | ADR 0041 §9: puts the snapshot at place `to` (0-based) of the list without it; a place past the end is the last place (clamped); kept as `order` in `snapshots.toml` | `{"type": "snapshot.moved", "name", "index": <the place it took>, "base", "snapshots": [<the list in its new order>], "undo"}`; every client is pushed `snapshots`; errors `bad-value` (a `to` that is no whole number from 0, a name), `unknown-snapshot`, `conflict`, `does-not-load`, `write-failed` |
| `{"type": "snapshot.delete", "name": "Verse A", "base": "…"}` | Removes the snapshot (the file stays, with `schema_version` alone, after the last one) | `{"type": "snapshot.deleted", "name", "count", "base"}` (`base`: the SHA-256 of the bytes this delete wrote) |

- **`name`**: any text, trimmed, 1 to 64 characters (Unicode scalar values), with no control character, no format character (Unicode category Cf: zero-width spaces, the byte-order mark, direction marks) and no line or paragraph separator (U+2028, U+2029) anywhere in what was sent, and not made only of blank characters (`bad-value` otherwise). Names are exact and **not normalised**: a composed `é` and `e` followed by a combining accent are two names (no crate of the workspace normalises Unicode).
- **The transition** (ADR 0041 §10): `snapshot.restore` and `snapshot.undo` take an optional `transitionMs` (0 to 60000; only that key: `ms` is `snapshot.transition`'s) for that request, else the file's `transition_ms`; their reply says the one used (`transitionMs`). With a transition, each continuous control is sent a linear `ramp` of that length from the value playing at its frame (a running ramp included), and a stepped one (a gate, a trigger, or a `Generic` parameter whose whole range lies within 0 to 64 and is at least 2 wide, both values whole: ADR 0041 §10) a `ramp` of 0 frames at the start; 0 is the panel's 5 ms ramp, as before. The file holds the targets at once, so `describe`'s `base` is the target; the `parameters` stream shows the ramp. Lists carry `transitionMs`.
- **The order:** lists (`snapshot.list`, the pushed `snapshots`, `snapshot.moved`) give the snapshots in the list's order: the names `order` lists, then the others in byte order. A new snapshot goes to the end, an overwrite keeps its place, a delete takes it out.
- **`base`** (optional on save, restore, undo, move and delete): the SHA-256 of `snapshots.toml` the client listed (`null`: it had no file). A file that is no longer that version is `conflict`, carrying the current `base`, and nothing is written. Without `base` the file is taken as it is when the write reads it.
- **Every write** of `snapshots.toml` is made under the project's writer lock with the canonical text and compared just before its rename (ADR 0040): another writer's change in between is `conflict`, never lost. A `snapshots.toml` reached through a link is `write-failed`. The watch takes the written file as seen: nothing plays from it, so there is no `reload`.
- **Errors:** `unknown-snapshot` also for `snapshot.undo` without an undo snapshot; `bad-value` (a name, `overwrite` or `base` of the wrong kind), `exists` (a save under a name in use without `overwrite`), `unknown-snapshot`, `conflict`, `does-not-load` (`snapshots.toml` does not read as snapshots, which is never overwritten; or, for save and restore, the project does not load or plan), `write-failed`, `no-project` (Signal.app with no project open).
- **The JS client** has no wrapper: `connection.request({type: "snapshot.save", …})`. Signal.app's Snapshots card is `ui/app/app.js` `SignalAppSnapshots` with its logic in `ui/app/lib/snapshots.js`.
- Tests: `crates/signal-ui/tests/snapshot.rs` over both transports.

### `panel.check`

```json
{"type": "panel.check", "id": 7, "file": "main.html"}
```

The binding check of a panel in the project's `ui/` folder (`file`: an `.html` file there, by the static files' rules) against the running plan: the check `signal ui check` makes (`crates/signal-ui/src/bindings.rs`), so a panel shows at load what the command prints. `<signal-panel>` asks it once described, and again when the plan version changes. Reply:

```json
{"type": "panel.check", "id": 7, "file": "ui/main.html", "controls": 6, "bindings": 6, "ok": false,
 "diagnostics": [{"severity": "error", "file": "ui/main.html", "line": 36, "column": 28, "control": 0,
   "message": "unknown port /drums.kick_decya: /drums has kick_decay, kick_drive"}]}
```

`control` is the control's index among the file's `signal-*` elements other than `<signal-panel>`, in source order (null for the file as a whole); `ok` is false when any diagnostic is an error. ADR 0037 §7 (phase 3): a binding on a top-level slot's port is checked through its match; on an empty slot or an unmatched port it is inactive, a **warning** (`inactive: /spare.out: /spare is empty`), never an error; `<signal-slot>` binds a top-level slot of the project (`bind="/deck_a"`), loaded or not, and anything else is an error. Errors: `unknown-panel` (no such file, not `.html`, outside `ui/`), `not-playing` (the project does not plan).

### `panel.read`, `panel.write`, pushed `panel.written`

The panel editor's text (M2.9-2, ADR 0026 §5, `docs/ui-controls.md` "Editing a panel"). A write replaces exactly the content of the file's one `<signal-panel>` element and nothing else; the file stays text.

```json
{"type": "panel.read", "id": 8, "file": "main.html"}
```

→ `{"type": "panel.read", "id": 8, "file": "main.html", "exists": true, "base": "<sha-256 of the file, hex>", "text": "<the whole file>", "html": "<the content of its <signal-panel>>", "editable": true, "reason": null, "planned": true}`. `file` follows `panel.check`'s rules (an `.html` file in the project's `ui/`); a missing `main.html` (the generated default panel) reads `exists: false` with `base`, `text` and `html` null. `editable` is false, with `reason`, for a file without exactly one `<signal-panel>` element (or without its end tag outside comments and scripts). `planned` says whether the project plans, which a write needs (below). Errors: `unknown-panel`.

```json
{"type": "panel.write", "id": 9, "file": "main.html", "html": "\n  <div class=\"signal-cards\">\n    …\n  </div>\n", "base": "<sha-256 the editor started from>"}
```

`html` is the new content of the `<signal-panel>` element, as the editor's serialiser writes it (`ui/lib/panel-tree.js`); `base` is the SHA-256 of the file it started from (`panel.read`, or the last `panel.written`), or null for a `main.html` that does not exist yet. The server, never trusting the page:

1. takes `file` by `panel.check`'s rules, or a missing `main.html` (`unknown-panel` otherwise: no other folder, name or project; `signal ui` writes only the project it serves). The file must resolve inside the project: a linked `ui/` folder or a linked file is `unknown-panel`, as for `panel.read`;
2. checks `html` against the whitelist again (`ui/lib/panel-whitelist.json`, the same file the page uses): the controls with their attributes, `div.signal-cards`, `section.signal-card`, `h1`, `h2`, `p`, `div.row`, `div.signal-group`, lowercase class tokens and text, in that nesting; a comment, a script, a `style` element or attribute, an event handler, any other element or attribute is `bad-html`;
3. refuses a file that changed since `base` with `conflict`, carrying the file's current `text`, `base` and `html`, so the page can read it again;
4. finds the file's one `<signal-panel>` element (its end tag found as the start tags are, outside comments and the content of `script`, `style`, `textarea` and `title`): `not-editable`, naming why, without exactly one;
5. replaces its content only: every byte outside it (the head, styles, scripts, comments) is kept. A missing `main.html` is created with the standard head (the project's name as title, `/ui/controls/theme.css`, a dark page) and `import '/ui/controls/index.js'`;
6. checks the bindings of the new file as `panel.check` does (`crates/signal-ui/src/bindings.rs`): what it refuses is `bad-binding`, with its `diagnostics` in `panel.check`'s form; without a plan, `not-playing`;
7. writes atomically (a hidden temporary file beside it, synced and renamed, as `commit` writes `project.toml`), and the watch takes it as seen (no `reload`). A `.signal` project's working folder then differs from its file: the project is edited (`app`, "Signal.app").

Reply: `{"type": "panel.written", "id": 9, "file": "main.html", "base": "<sha-256 of the written file>", "created": false}` (`created`: the write made `main.html`). Every client is pushed `{"type": "panel.written", "file", "base", "html"}`; `<signal-panel>` shows the written panel in place (the generated panel, whose file now exists, loads the page again). Nothing is written when any step refuses; `write-failed` is a write the folder refused. This adds the project's `ui/*.html` panel files to what a client may write (Security notes, "Files").

**The plate** (ADR 0047 §2, additive). `panel.read`'s reply, `panel.write`'s reply, a `conflict`'s details and every `panel.written` push carry `plate`: the `plate` attribute of the file's `<signal-panel>` as written (`"160 90"`, the plate's width and height in plate units), or null. `panel.write` takes an optional `plate`: a string sets the attribute on the `<signal-panel>` start tag (after its last attribute; two whole numbers 1 to 1000, else `bad-html`), null removes it with the space before it, and without the field the attribute is kept; every other byte of the start tag and the file is kept, so writing back the version before (its content, its plate) gives the file back byte for byte. The cards' `place="x y w h"` are part of the content (the whitelist takes it on `section.signal-card` and on the open slot card `<signal-slot>`). The binding check judges both (`crates/signal-ui/src/plate.rs`): a malformed value or a card beyond the plate is an error, so the write is refused (`bad-binding`); overlapping cards, a card without a place on a plate and places without a plate are warnings. No new message: the page measures (Freeze layout), the server checks and writes as it does any edit.

**A slot's part** (ADR 0046, additive). `panel.check`, `panel.read` and `panel.write` take `parts/<slot>.html` and `parts/<composite>.<slot>.html` under `ui/` (a linked `ui/parts/` is `unknown-panel`, as a linked `ui/`). A part of a slot of the project that does not exist yet reads `exists: false` and is created by its first `panel.write` (`base: null`) as a comment and its `<signal-panel part="<slot>">`. Its bindings are checked at its roots (`/synth`; each instance of a composite's slot), relative (`project-format.md` §14): `.<name>` of the slot's interface (another name: an error), `/<path>.<port>` inside its content (nothing there now: inactive, a warning), nothing outside the slot; the `part` marker must name the file's slot; a file under `parts/` naming no slot is an error; a relative bind in any other panel is an error. The whitelist takes `<signal-slot>` as a direct child of `div.signal-cards` (the open slot card). The pushed `panel.written` of a part, or of a panel a patch wrote (Group into slot), carries its `file` (`parts/synth.html`); a part a patch removed is pushed with `base` and `html` null.

Tests: `crates/signal-ui/tests/panel_write.rs` over both transports (a write and its push, refused elements and attributes, a conflict, a refused binding, the text outside kept byte for byte with a `</signal-panel>` in a comment and a script, not editable, the generated panel's first write, only the served project's panels, the plate set and removed byte for byte), `crates/signal-ui/tests/app_mode.rs` (`a_panel_write_marks_a_signal_project_edited`), `crates/signal-ui/src/panel_write.rs` (the SHA-256 vectors, the whitelist, the end tag).

### `pattern.read`, `pattern.write`, pushed `pattern.written`

Pattern files (M2.11-1, ADR 0028 §7, `project-format.md` §12): the note and step data a piano roll or step grid edits, read and written whole as text, with the rules of `panel.write` and `patch`.

```json
{"type": "pattern.read", "id": 10, "name": "melody"}
```

→ `{"type": "pattern.read", "id": 10, "name": "melody", "exists": true, "base": "<sha-256 of the file, hex>", "text": "<the whole file>", "kind": "notes"}`. `name` is a pattern name, `[a-z][a-z0-9_]*`, never a path: the file is `patterns/<name>.toml` of the project served. `kind` is `"notes"` or `"steps"`, or null for a file that does not read as a pattern. A missing file reads `exists: false` with `base`, `text` and `kind` null. Errors: `bad-value` (not a name), `unknown-pattern` (the file or `patterns/` is a link, or cannot be read), `no-project`.

```json
{"type": "pattern.write", "id": 11, "name": "melody", "text": "schema_version = 1\nkind = \"notes\"\n…", "base": "<sha-256 the editor started from>"}
```

`text` is the whole new file; `base` is the SHA-256 of the file the editor started from (`pattern.read`, or the last `pattern.written`), or null for a file that does not exist yet. The server, never trusting the page:

1. takes `name` as a pattern name (`bad-value` otherwise) and refuses a `patterns/` folder or file that is a link (`write-failed`: patterns are written only in the project's own `patterns/`, as `schematic.move` writes positions);
2. refuses a file that changed since `base` (or exists when `base` is null) with `conflict`, carrying its current `base` and `text`;
3. loads and plans the project with the new text, as a reload would, and while playing checks that the running project can take it: the pattern's own errors (syntax, unknown keys, values out of range, overlapping notes) and those of the instances naming it (a wrong kind, a key the type cannot play) are `does-not-load`, with `diagnostics` (one `file:line:column: error: …` per line, also in the message) naming each problem;
4. reads the file again: one that changed since step 2 is `conflict`, as there;
5. writes atomically (a hidden temporary file, synced and renamed, as `commit` writes), creating `patterns/` if needed. The watch is **not** told the write was seen: playing, its reload applies the file live, a swap at an edit frame in which every instance survives with its state (a playing loop keeps its position; `semantics.md` §12), pushed as `reload` and recorded in a session like any swap. A `.signal` project's working folder then differs from its file: the project is edited (`app`, "Signal.app").

Reply: `{"type": "pattern.written", "id": 11, "name": "melody", "file": "patterns/melody.toml", "base": "<sha-256 of the written file>", "created": false}` (`created`: the write made the file). Every client is pushed `{"type": "pattern.written", "name", "base", "text"}`. The same push comes whenever the file changes on disk however it changed (an editor, another program; external review, 2026-10-31), seen by the server's watch, with `"origin": "file"` (a write of this server is pushed again so, with the same base, which a client ignores); a removed file or one reached through a link is not pushed. An idle editor shows the pushed text at once; one with an edit pending keeps its draft unwritten and says both changed (`ui/lib/pattern-sync.js`). Nothing is written when any step refuses; `write-failed` is also a write the folder refused. `graph.files` does not list pattern files: a pattern's base is `pattern.read`'s.

**Size.** A client message is at most 64 KiB ("Limits"): a `pattern.write` larger than that closes the client's connection, like any message, and writes nothing. So a pattern editable over the protocol is one whose text, JSON-escaped, fits 64 KiB with the message around it: about 63 KiB of TOML, some 1200 notes written one per line, or any steps pattern up to 64 lanes of 256 steps (`project-format.md` §12). A larger file is edited as text.

**The JS client.** `ui/signal-ui.js`'s `Connection` wraps the two: `readPattern(name)` resolves `{ text, sha, base, exists, kind }` (`sha` and `base` are both the reply's `base`), `writePattern(name, text, base)` resolves `{ sha, base, created }` (the written file's), and a refusal rejects with an `Error` whose `code` and `message` are the server's and whose `reply` is the error message (a `conflict` carries the current `base` and `text`). The pattern controls use exactly these two methods when a connection offers them; `ui/fake-connection.js` offers them over in-memory patterns (`ui/signal-ui.test.js`, `ui/fake-connection.test.js`).

Tests: `crates/signal-ui/tests/pattern.rs` over both transports (a read, a write and its push and live swap, a conflict, refused text naming the problem, a wrong kind, names and links, a first write, a message over the limit closing the connection with nothing written), `crates/signal-ui/tests/app_mode.rs` (`a_pattern_write_marks_a_signal_project_edited`).

### `file.read`, `file.write`, `vendor`

The project's own text as a whole file (M2.12-1, ADR 0029 §2, operator decision of 2026-10-18), for `signal mcp`'s `read_file`, `write_file` and `vendor` tools (`agent-interface.md`). They follow the rules of `patch` and `pattern.write`, and share their code.

```json
{"type": "file.read", "id": 12, "file": "project.toml"}
```

→ `{"type": "file.read", "id": 12, "file": "project.toml", "exists": true, "base": "<sha-256 of the file>", "text": "<the whole file>"}`. `file` is `project.toml`, `composites/<name>.toml` or (ADR 0037 §3, phase 3) `interfaces/<name>.toml`, a slot interface template (`[a-z][a-z0-9_]*`), never another path (`bad-value`); a missing template reads, and is created, as a missing composite. Patterns are `pattern.*`, panels `panel.*` and positions `schematic.*`. A missing composite reads `exists: false` with `base` and `text` null; a file reached through a link is `bad-value`.

```json
{"type": "file.write", "id": 13, "file": "project.toml", "text": "schema_version = 1\n…", "base": "<sha-256 it was read with>"}
```

`text` is the whole new file; `base` is the SHA-256 it was read with, or null for a composite that does not exist yet. The server, never trusting the client:

1. takes `file` as above (`bad-value`), and refuses a file, or `composites/`, reached through a link (`write-failed`), as `patch` does;
2. refuses a file that changed since `base` (or exists when `base` is null) with `conflict`, carrying its current `base` and `text`;
3. loads and plans the project with the new text as a reload would, and while playing checks that the running project can take it (`patch`'s step 5): `does-not-load` with `diagnostics`;
4. reads the file again: one that changed since step 2 is `conflict`;
5. writes atomically (a hidden temporary file, synced and renamed, as `commit` writes), creating `composites/` if needed. The watch is not told the write was seen: playing, its reload applies the file live; stopped, `graph` is pushed at once.

Reply: `{"type": "file.written", "id": 13, "file": "project.toml", "base": "<sha-256 of the written file>", "created": false}`.

```json
{"type": "vendor", "id": 14, "composite": "lib.tape_echo", "as": "echo", "base": "<sha-256 of project.toml>"}
```

Copies a built-in library composite, and the library composites it uses, into the project's `composites/` as `signal vendor` does (ADR 0027 §4, `signal_project::vendor`). It uses that command's all-or-nothing writer: temporary files linked into place, rewritten files renamed last, rolled back on failure (never over an edit made meanwhile). The host checks first:

- `project.toml` is still the version `base` names, and the vendoring was prepared from that version (`conflict`);
- when it commits, under the project's writer lock (ADR 0040), every file of the project is still exactly what the vendoring was prepared from: a file changed, added or removed meanwhile is a `conflict` naming it, and nothing is written;
- no file it would write is reached through a link (`write-failed`);
- the project as it would be left plans as a reload would (`does-not-load`).

Reply: `{"type": "vendored", "id": 14, "composite": "lib.tape_echo", "copied": ["composites/echo.toml"], "reused": [], "rewritten": []}`. Errors:

- `unknown-module`: not a library composite;
- `bad-value`: a bad `as`, or a file of a copy's name exists already;
- `does-not-load`;
- `write-failed`;
- `conflict`.

Tests: `crates/signal-ui/tests/file_write.rs` over both transports (a write applied live, a new composite, a conflict with the current text, refused text naming the problem, other files and links refused with nothing written, `vendor` with its base check and an unknown composite).


### Pushed: `reload`, `reload.error`

Every 100 ms the server checks the project folder (hidden files ignored, as `signal play --watch`) and applies a change live. It pushes `{"type": "reload", "sets": 2, "swap": 1, "removed": 0, "replaced": 0, "loadSwap": null, "message": "applied a swap to version 1 (2 sets, 0 removed)"}` (`replaced` and `loadSwap`, ADR 0037 phase 2: the slots whose content a Replace changed, unloaded by `swap` and loaded by the swap to version `loadSwap` a frame later), or `{"type": "reload.error", "message": …}` when the folder does not load or cannot replace the running project (the last good version keeps playing).

Every `reload` also names the files that changed, `files` (relative to the folder, in path order), and says whether they were all **presentation** files, `presentation` (external review, 2026-10-31, additive): files under `ui/` (the panels, their styles and scripts, `ui/schematic.toml`, `ui/windows.toml`), which no load reads. A presentation-only change runs no reload (the folder is not loaded, planned or diffed, nothing is sent to the engine) and is pushed as `{"type": "reload", "sets": 0, "swap": null, "removed": 0, "replaced": 0, "loadSwap": null, "message": "presentation files changed (ui/app.css): nothing to apply", "files": ["ui/app.css"], "presentation": true}`, then `graph` if the positions changed; any other file changed with it reloads the project as before. Stopped (Signal.app), the cached `graph` structure is likewise kept across presentation changes. The files of an included project outside the folder are not watched yet (ADR 0035 phase 2).

### Signal.app (app mode)

**`signal ui` and `transport.*`** (M2.12-1, ADR 0029 §2): `signal ui`, and `signal mcp`'s own host, also take `transport.stop` and `transport.play`; the other app messages stay refused in `signal ui`.

- `transport.stop` stops the run (as `transport.stop` in Signal.app, which has no Stop button since ADR 0033): edits waiting for reports are answered `abandoned`, the unsaved controls keep their values, subscriptions are kept.
- `transport.play` plays the project it serves again from frame 0 from its files, as `project.open` of that project does.
- Both reply `{"type": "transport", "playing"}` and push `describe`. A run that records a session or its audio refuses both with `recording`.
- Under the null driver, `--seconds` still ends a stopped run on time.
- Tests: `crates/signal-ui/tests/app_mode.rs` (`signal_ui_stops_and_plays`, both transports) and `crates/signal-cli/src/drive.rs`.

**Several windows** (ADR 0032): every window of Signal.app is one more client of the same server, with the same token: a main window loads `/ui/app/index.html`, a schematic window `/schematic`, a panel window `/ui/app/panel-window.html` (the project's `/project/main.html` in a frame); each is sent every push, so what one window does shows in all (`crates/signal-app/tests/server.rs`, three clients). The window layout, `ui/windows.toml` (`project-format.md` §13), is written by the app through the control thread (`Host::write_windows`), taken as seen by the watch; it is no protocol message. What a window's page and the app tell each other about panel cards is in `ui-controls.md` "Cards across windows"; about its view state (ADR 0047 §3, §5: the schematic's layer and hidden kinds, the plate's scale), `view.state` (the page's whole state, over `window.ipc`) and `signal-view` (the app's, when the window is ready; a schematic window says `window.ready` for it), neither a protocol message (`ui/app/lib/view-state.js`).

Signal.app's control thread runs the host in **app mode** (`Host::new_app`, M2.8-4): its window's WebView loads `http://127.0.0.1:<http port>/ui/app/index.html#ws=…&token=…` from it. App mode opens the project the app was given or else the Setup's last project, and plays every run with the Setup (its output, channel map, buffer, CPU workers, wake policy and input), with the rules of the app's state (`crates/signal-ui/src/app.rs`, shared with `signal-app`'s `AppState`). **The project plays while the app is switched on** (ADR 0033, `AppHostConfig::plays`, which Signal.app sets): when the app starts, when a project opens, and when the power comes on; Signal.app has no Play or Stop, a project starts and stops from its own transport, and Project ▸ Restart from Files sends `transport.play`. A project that does not load, or a device that does not start, leaves it stopped, with the reason in `app`'s `message`, until the next open, switch-on or restart; a `transport.stop` (a script, a test) stops it until then too. **The device's clock is the run's** (ADR 0036, the owner's decision of 2026-10-23): a run plays at the rate the output device runs at, and Signal never switches a device's nominal rate. A project's `sample_rate` is the rate of its renders and replays and a preference, not a requirement for live play: when the output runs at another rate, the run plays at the output's and `app`'s `notes` say so ("'SSL 2+ Mk II' runs at 44100 Hz; studio is written for 48000 Hz and plays at 44100 Hz"); the session records the rate played, so its replay is exact. Nor does Signal set the buffer of a device that runs for another app (ADR 0036): it plays at that device's own buffer. Signal's output fades in over 10 ms when a run starts and out over 10 ms before it stops. **Stopped by the device**: a device error is said in plain words with the rates, never as CoreAudio's bare text (the incident of 2026-10-22: "Unknown property" when the default output ran at another rate than the project's and could not be switched; since ADR 0036 no switch is tried). A stream the audio system stops while playing (the device's rate changed, it went away; cpal reports it, and the stream calls no more back) stops the run with the reason ("the device '…' changed its sample rate to 44100 Hz while playing at 48000 Hz; stopped, …"), and the next run plays at the new rate. cpal 0.18.2 reports a rate change only for a device opened by its id: the system default output's stream has no rate listener, and its AudioUnit converts the rate and plays on. In `signal ui` and `signal mcp` the run is kept, not stopped, so what it recorded (`--record-session`, `--record-audio`) is written; `signal ui` then ends with the reason and a non-zero exit, as `signal play` does; `signal mcp` serves on, as after an engine failure, until a client plays the project again, and exits non-zero if it ends so. Switched on, not stopped on purpose and with `plays`, such a run **waits for the device**: the control thread lists the devices again once a second (CoreAudio has no notification the host listens to; nothing runs on the audio thread), and once the Setup's output (or the default output) is there again (after it changed: plugged in, another default, another rate), the project plays again from frame 0 at the rate it runs at ("the output runs at 44100 Hz: playing again from frame 0"). An output that is there when the run stopped (a rate switched, a device busy for a moment) is tried once more at the next look ("Signal tries the output again in a moment"); a change of the project's files is tried once too. An output that did not change is not tried again ("Signal tries again when the output or the project's files change"); each retry in a row doubles the look interval (1 to 16 s), and after 5 in a row the wait ends ("the output failed 5 times in a row; Signal stopped trying: …"); a retried run that played 30 s resets the count; one that is gone is waited for ("Signal plays again once the output is there"); a `transport.stop`, switching off or another open ends the wait. A host without `plays` (the tests' rig) starts stopped and plays on `transport.play`. `describe` answers while stopped (with `"playing": false`), and `commit` writes while stopped. ## Binary frames

Little-endian, a 24-byte header, then the payload (`crates/signal-ui/src/frames.rs`, `decodeFrame` in `ui/lib/protocol.js`):

| Offset | Size | Field |
|---|---|---|
| 0 | u8 | kind: 1 meters, 2 scope, 3 parameters, 4 vector |
| 1 | u8 | protocol version (1) |
| 2 | u16 | reserved, 0 |
| 4 | u32 | subscription (`sub`) |
| 8 | u64 | first frame: meters, the first callback's; scope, point 0's; vector, the snapshot's; parameters, the runner's next frame when sent |
| 16 | u32 | count |
| 20 | u32 | meters: frames covered; scope and vector: decimation; parameters: 0 |

| Kind | Payload, `count` times |
|---|---|
| 1 meters | `f32` peak, `f32` RMS (linear; full scale 1) per channel |
| 2 scope | `f32` point |
| 3 parameters | `f64` base, `f64` effective per address, in the subscription's order; NaN until the runner reported it |
| 4 vector | `f32` per element of the port, in order |

## Delivery: slow and gone clients

The control thread never waits for a client. Each client has a thread that writes what the control thread queued for it and reads its messages; the queue between them is bounded (256 messages for `signal ui`). The control thread only ever tries to queue: when a client's queue is full, a **binary frame is dropped and counted** (`stats`: the client's `dropped`), and a **control reply that does not fit evicts the client** (`evicted`), since losing a reply silently would leave it waiting. Eviction sets the client's flag and drops its queue; its thread sees either and closes the connection on its own. The client's thread writes one message at a time and flushes it; while its socket takes nothing (each write waits at most 100 ms), it takes no more from the queue, so the WebSocket holds at most one message beyond what the socket took (and never more than 4 MiB, but for one message larger than that): the rest waits in the bounded queue, where the drops and the eviction above apply. A client whose socket takes nothing for 2 s is disconnected by its thread. A single outgoing message larger than the 4 MiB write limit (a 4096-voice project's `graph` is about 6 MB, M2.9-1b) is taken when nothing else is unwritten, and the limit applies again once the socket took it, so a backlog stays bounded (`crates/signal-ui/tests/app_mode.rs`, the 4096-voice `graph`, both transports). Verified with a socket whose writes keep timing out while frames keep arriving (`crates/signal-ui/src/server.rs` tests) and with a client whose writer is held (`crates/signal-ui/tests/backpressure.rs`).

## Version rules

- `protocol` is 1. The server names it in `welcome`, in the `protocol` error, and in byte 1 of every binary frame.
- Adding message types, fields, error codes or frame kinds keeps version 1. Clients ignore what they do not know; the server ignores unknown fields.
- Removing or renaming anything, or changing what a field or a frame byte means, is version 2. A server that speaks several versions answers each in the one its `hello` asked for.

## Security notes

- **Local only by default.** Both servers bind 127.0.0.1. `signal ui --remote` binds every interface, for a tablet or another Mac; it is off by default and prints a warning. Remote access then relies on the token alone, and the token travels in clear text (no TLS). Signal.app binds 127.0.0.1 only (a Setup switch for remote clients is later work).
- **A token per session.** 32 bytes from the system's random source (`/dev/urandom`), hex, new for every run of the server, compared in constant time. It is required in the first message of every WebSocket connection. It is in the URL's fragment, never in an HTTP request. Anyone with the URL can control the run and write the project's `project.toml`, so the URL is a credential: `signal ui` prints it on the terminal only.
- **Origin.** A browser connecting to the WebSocket must come from the HTTP server's own origin: `http://127.0.0.1:<http port>` (or `localhost`, `[::1]`); with `--remote`, the host the request was sent to and the HTTP port. Another site's page is refused at the handshake (403), before the token. A client without `Origin` is not a browser page and goes on to the token check.
- **Host.** Without `--remote`, the HTTP server answers only the loopback names with its port, so another site cannot read the files through a name that resolves to 127.0.0.1 (DNS rebinding).
- **Files.** Only the two `ui/` folders are served (above). A client writes only through `commit` (a top-level parameter in `project.toml`), `schematic.move` and `schematic.reset` (the project's `ui/schematic.toml`, presentation only, never through a linked `ui/` or file), `panel.write` (a panel file in the project's `ui/`, its `<signal-panel>` content only, within the editor's whitelist), `keys.set` and `keys.reset` (ADR 0034: the person's `keys.toml` beside the Setup file the server was started with, never another file), `pattern.write` (M2.11-1: `patterns/<name>.toml` of the served project, by name, never through a linked `patterns/` or file, after the same load and compile as a reload), `patch` (M2.9-3: the served project's `project.toml` and `composites/*.toml`, the files the project itself read, never one reached through a link; and its `ui/schematic.toml`, never through a linked `ui/` or file; after the same load and compile as a reload, and inverse-only `edits` limited to what the op means, the comment lines above a restored entry and its `gpu` pin), `file.write` (M2.12-1: the served project's `project.toml` and `composites/<name>.toml` as whole text, never through a link, after the same load and compile as a reload), `vendor` (M2.12-1: library composites copied into the served project's `composites/` by `signal vendor`'s writer, never through a link, after the same checks), `snapshot.save` and `snapshot.delete` (ADR 0041: the served project's `snapshots.toml`, never through a link), `snapshot.restore` (top-level parameters in `project.toml`, as `commit`) and `setup.apply` (the Setup file the server was started with).
- **`project.open` opens another project only in Signal.app's app mode**; `signal ui` refuses it (`not-allowed`) for every path but the project it serves, so a client of `signal ui` cannot point it at another folder. For the project it serves (its folder, its `project.toml`, or the `.signal` file it was started with, compared after resolving links) `signal ui` plays it again from frame 0 from its files, a `.signal` file unpacked again into a new temporary folder (M2.8-12); while recording that is refused with `recording`, as `setup.apply` does not restart a recording run. In the app, a client with the token may open any folder it names: the host then writes the Setup file the app was started with (`last_project`), serves that folder's `ui/` (its panels and `ui/assets/`, by the rules above) under `/project/`, and later `commit`s write that folder's `project.toml`. The token rules are unchanged, and the app binds 127.0.0.1 only.
- **Clients.** At most 32 WebSocket connections are served at once, a connection that has not sent `hello` yet included. Such a connection holds its place for at most 5 s from its acceptance: an absolute deadline over its WebSocket handshake and its `hello` with the token, not a timeout per read, so a client that trickles its handshake a byte at a time loses its place as one that sends nothing does (it is told `unauthorized` if its handshake was complete, else closed without a reason), and a stop ends it at once. Connections before `hello` have no budget of their own apart from the 32: anyone who can connect can open as many as it likes, so a smaller budget would refuse a newcomer just as the full one does; the deadline bounds how long any of them holds a place. One past that is refused: once it has sent its handshake it is told `{"type": "error", "code": "too-many-clients"}` and closed with code 1013 (try again later) and the reason `too-many-clients`, all within 1 s; one that sends no handshake in that time is closed without a reason (a close reason needs a WebSocket). Two threads refuse, with 16 connections waiting for them; while those are taken, accepting waits rather than drop a connection. None of these threads is waited for at shutdown (`crates/signal-ui/tests/backpressure.rs`).
- **Limits.** A client message is at most 64 KiB (a larger one closes the client's connection; a `patch` whose undo would need more is refused before it is written); numbers a client sends are checked before use (an unsupported rate is `bad-rate`, a value outside its range is clamped); messages from all clients wait in a bounded queue; at most 256 are handled per control step.

## Running it

```sh
signal ui projects/kick --open             # CoreAudio, the default output; opens the main panel
signal ui check projects/kick              # checks the panels' bindings (exit 1 with diagnostics)
signal ui projects/kick --driver null      # no device, real-time pace
signal ui projects/kick --port 8800        # a fixed HTTP port
```

`signal ui` takes every option of `signal play` (`--device`, `--buffer`, `--seconds`, `--threads`, `--rt-policy`, `--rt-computation`, `--rt-trace`, `--driver`, `--fast`, `--record-session`, `--record-audio`, `--record-boundary-data`) and always watches the folder, as `play --watch` does. It stops on Enter (or at `--seconds`), and with `--json` prints `{"url", "panel", "http", "ws"}` when it starts. The UI library's folder is the app bundle's `Contents/Resources/ui` when the program runs from a bundle, else the repository's `ui/` of the build (`--ui-dir` for another).

`signal mcp <project>` plays a project the same way for an LLM client, speaking to it in process; `signal mcp --attach <url> <project>` shares a running `signal ui` with one (`agent-interface.md`).

`signal ui` also prints the schematic's page, `http://127.0.0.1:<http port>/schematic#ws=…&token=…` (`--json`: `schematic`).

Pages and controls use the client in `ui/signal-ui.js` (reconnect included) and the web components in `ui/controls/`; `/ui/gallery.html` shows them all (`docs/ui-controls.md`).

The page at `/` is the raw protocol test page: the connection and protocol, the output meters, a scope of a chosen signal output, a slider per control (a ramp while moving, a commit on release) with its effective value, the unsaved indicator ("N unsaved parameters — last error", Retry all, Revert all; "Unsaved" above), and the `describe` reply.
