# Testing and evaluation

How Signal is tested, what the acceptance IDs (V1…) map to, and how golden renders work. The layers follow `01-inception-proposal.md` §9; the acceptance IDs are §8.4.

**Principle: metrics detect defects; humans judge quality.** A passing suite says that nothing measurable is broken: no NaN, no clipping, no DC, triggers on their frames, the same bytes as before. It does not say that something sounds good. Every milestone that changes sound ends with a recorded human verdict (V14 for M1), and no metric replaces it.

## Synchronisation model tests (M2.7-6)

The scheduler's synchronisation is three small state machines, each in its own module and written over `crates/signal-engine/src/sync.rs`, which is std's atomics in every build and loom's in the crate's own test build with `--cfg loom`: the gate's word (`gate.rs`: open, join, leave, close, epoch), the task board (`board.rs`: claim, complete or fail, successors, and the loop every thread of a job runs) and parking (`park.rs`: the `parked` flags, the wake, and each worker's loop). `shared.rs` keeps the job beside the gate's word (its one `unsafe` slot, ADR 0020) and `pool.rs` the threads, timing, requests and blocker. The model tests in `crates/signal-engine/src/model/` run that same code under loom 0.7.2, which explores the interleavings of the caller and two or three workers with its C11 memory model (stale reads of Relaxed and Acquire loads included) and checks the gate's job slot for data races:

```sh
RUSTFLAGS="--cfg loom" cargo test -p signal-engine --lib --release --locked --offline model::
```

(A seat that cannot set `RUSTFLAGS` passes a config file instead, after the subcommand so that `clippy` sees it too: `cargo test --config <file with build.rustflags = ["--cfg", "loom"]> …`. Use a target directory of its own: changing the flags rebuilds everything.) Each scenario is exhaustive within a preemption bound, 2 or 1 as listed (`LOOM_MAX_PREEMPTIONS` overrides it); CI's `model-tests` job runs them all. Threads wait for each other by parking, so a lost wake ends with every thread parked, which loom reports as a deadlock. Seconds are on the seat, release build.

**Found by the model tests.** P1 on the handshake as it was (a SeqCst store of the flag, then a SeqCst read of the gate; a SeqCst open, then SeqCst swaps of the flags) deadlocked at once: loom treats SeqCst accesses as AcqRel (loom's README, "Unsupported features"), so a worker could re-read the gate's word from before the open after the caller had read its flag unset. The C11 single order of SeqCst operations excludes that, but nothing checked it. Both halves now fence (`fence(SeqCst)` between the store or open and the reads, `park.rs`), which loom models; the SeqCst accesses stay (ADR 0020 as amended for M2.7-6, `realtime-rules.md` "Worker threads").

**AC2 (finding 1).** With `TaskBoard::participate` reverted to completing every claimed task as a success (`self.complete(t, epoch, true)`, the bug of revision 986cc16), B2a fails (`the job did not fail`, failure 0 rather than `FAILED_PANIC`) and B2b fails (`Job::failure()` is `None` though task 0 panicked); so do two tests of `failure_stop.rs`.

**Not covered.**
- **P2, the callback-start wake** (`semaphore`: every parked worker woken before the segment's open). It is in the suite but ignored: loom 0.7.2 reports a deadlock in an execution the C11 model forbids. Both later swaps of a worker's flag read the caller's own earlier `false` although the worker stored `true` and fenced, because loom lets a read-modify-write read any store maximal in its partial modification order (`rt/atomic.rs`, `match_rmw_to_stores`). It runs with `-- --ignored`. The handshake it exercises is checked apart from loom, exhaustively and on real threads (M2.7-10, "The park/wake handshake" below).
- **Beyond the bound.** Each scenario is exhaustive only within its preemption bound. The board's scenarios use 1: at 2, loom's conservative backtracking for bounded preemption explores schedules in which two workers waiting for a successor (`spin_loop`, a yield) hand the processor to each other while the thread holding its predecessor never runs, and one execution exceeds 100 000 branches. S3 uses 1 to stay within the budget (about 100 s at 2).
- **Load buffering**, which loom does not explore (its README); SeqCst accesses only as far as loom models them (as AcqRel, hence the fences).
- **Timing**: spinning before parking, `budget-spin` and `fanout`'s propagation (the model's workers block at once), and the `semaphore` policy's Mach waiter (they park).
- **The request queue's `Mutex`** (`Workers::post`): the model counts requests in an atomic.
- **What the jobs compute**: the cells, views, readers and claims of `shared.rs`, which the checked mode covers in every debug test (ADR 0020), and the engine's units and tasks, which the determinism matrix and the oracle cover.
- **GPU** completion (`crates/signal-gpu`).

### The park/wake handshake (M2.7-10)

The claim that the handshake loses no wake (`park.rs`, `realtime-rules.md` "Worker threads") rests on two checks of its own besides loom, both in the normal suite.

**An explorer of every interleaving** (`crates/signal-engine/tests/handshake.rs`, std only). One caller and 1–3 workers run two consecutive callbacks and a shutdown. The caller: under `semaphore` the callback-start wake of every parked worker, the job store, the open, the segment's wake of one, then it waits for every worker's join (a lost wake leaves it waiting with nothing to run: a deadlock), closes, and at the end stores shutdown and unparks every worker. A worker: the shutdown check and a join attempt (a join reads the job and wakes two, as `pool.rs` does), otherwise the flag store, the fence, the re-reads of the gate and of shutdown, the park unless they said not to, the flag cleared. A wake is the fence, then per flag a swap and an unpark if it was set. An unpark leaves a token the next park consumes: one (`park`) or a count (`semaphore`'s waiter). The explorer expands each distinct state once and fails on a state with no step that is not the end (lost wake), on a join that sees another epoch's job or an epoch twice (wrong epoch), and on a state reached again on its own path (no termination). The number of interleavings is computed through that memo (the executions from each state, summed), not walked one by one; `the_counts_are_interleavings` compares it with a plain walk where one is feasible (1 worker, 1 callback: 72 903 executions). States and transitions are counted exactly.

Two memory modes. **Sc**: each step is atomic in one total order, which is what C11 gives these SeqCst accesses and fences; it is the claim being checked, and a fence then changes nothing. **Buffered**: each thread's stores wait in a FIFO buffer that drains at any point; a fence, and an unpark (it releases), wait until the thread's buffer is empty; a read-modify-write acts on memory once its own store to that place has drained. That is store buffering, accesses no stronger than Release/Acquire, as loom treats SeqCst. It deliberately weakens the open, a SeqCst `swap`, to a plain store: that is not an equivalence, and a fence that matters only in this mode is not evidence that the hardware needs it. `Sc` and the SeqCst argument of `park.rs` remain the claim; `Buffered` shows what the fences add.

Abstractions, each a choice of the model rather than of the code: a join is one step (load, CAS and the job read; the gate's load-then-CAS and its leaves and close are G1–G3's subject), and the caller closes once every worker has joined; requests (`pending`, P3), spinning and timing are left out, and a park never returns without a token (a spurious return only adds a re-check; it would also make the state graph cyclic).

Every model step is on a line of the code (`each_model_step_is_in_the_code` reads each line and checks the order of `park.rs`'s steps, so swapping the flag and the gate in `run_worker` fails the suite too):

Result (the full `cargo test --workspace` run, debug profile, the test binary's three explorations in parallel: 15.7 s): no lost wake, no wrong epoch, every execution ends, for `park` without the callback-start wake (`park50`, `budget-spin`), `park` with it (P2's scenario) and `semaphore`, at 1–3 workers in `Sc` and 1–2 in `Buffered` (3 workers there take about 45 s, beyond the minute with the rest). The largest, `semaphore` with 3 workers in `Sc`: 9.4 × 10¹⁰⁶ interleavings through 4 467 060 states and 16 719 634 transitions in about 16 s; P2's with 3 workers: 6.4 × 10¹⁰⁴ through 1 914 638 states in about 7 s. Run them with `cargo test -p signal-engine --test handshake -- --nocapture` to see every count.

A broken handshake fails (`a_broken_handshake_is_caught`, 2 workers, one callback with the callback-start wake):

| Variant | `Sc` | `Buffered` |
|---|---|---|
| Worker re-reads the gate before storing its flag | lost wake | lost wake |
| Caller wakes before it opens | lost wake | lost wake |
| Worker's fence removed (`run_worker`) | holds | lost wake |
| Waker's fence removed (`Parking::wake`) | holds | lost wake |
| A blocker that forgets an unpark sent before the park | lost wake | |

The two fence rows hold in `Sc` as `park.rs` says (the SeqCst accesses alone order the handshake) and fail once accesses are weaker; the test prints each counterexample's steps.

**The wake before the open on real threads** (`park::tests::the_wake_before_the_open_is_never_lost_on_real_threads`). One worker runs the real `run_worker` over the real `Parking` and `GateWord`; its test pool implements `park::Worker` and pauses it in the calls the loop already makes (`parking`, `joinable`, `pending`, `block`), so no hook exists outside the test build. Each callback: the callback-start wake of every parked worker takes the worker's flag; on its next pass to a park the worker is held before its flag store, after the store and fence, after re-reading the gate closed, or until it has entered `block`; then the caller opens and wakes one, and the worker must join within 5 s. A callback counts as forced only if that wake took the flag and the worker was then held on a pass that began after it; the test asserts what the held worker read (the open gate, or the caller's wake taking its flag) and at least 2 000 forced callbacks per position. 3 000 callbacks per position with `park`'s token and again with a counting semaphore (a `Mutex` and `Condvar` standing in for the Mach waiter): 24 000 callbacks, no lost wake, in about 0.1 s. The forced count per position varies from run to run (2 326 to 3 000 observed); the test requires at least 2 000.

**The `semaphore` waiter** blocks and wakes through the same code as `park`: the flags, fences, swaps and re-reads are `Parking::wake` and `run_worker` under every policy, and the policy only chooses what `Shared::signal` and `Shared::block` call (`pool.rs:232-249`). The one difference is the token: `park` keeps one, a Mach semaphore counts. The handshake needs only that a signal sent before the wait is kept, which both do; a surplus count only makes a later wait return at once, and the loop re-checks after every return. The explorer runs both tokens, and the reproducer both blockers.

**Outside every model**, and what covers it instead:
- the shared data views (cells, views, readers and claims of `shared.rs`): the checked mode in every debug test (ADR 0020), `parallel.rs`, the determinism matrix and the semantic oracle;
- GPU completion (`crates/signal-gpu`): `lab/tests/gpu_partials.rs`, `lab/tests/realtime.rs` and `lab/tests/recovery.rs`, which need an adapter for computed values (skipped on the seat; the operator runs them at checkpoint);
- the Mach semaphore itself: `crates/signal-audio/tests/rt_workers.rs` and `pool::tests::every_wake_path_reaches_workers_blocked_on_the_waiter`;
- spinning, timing and `fanout`'s propagation: `pool::tests` (`idle_workers_park_after_the_spin_bound`, `fanout_propagation_ends`) and `parallel.rs`.

## The semantic oracle (M2.7-6)

`crates/signal-oracle` is a deliberately simple interpreter of `semantics.md` §§1–12 and §16 (ADR 0016): it runs a graph one frame at a time, every frame in the four phases of §2, and calls every primitive for one frame. It is written to be read, not to be fast, and shares no code with `signal-engine`: its `[dependencies]` are `signal-core` alone (`tests/independence.rs`); its input is its own (`Graph`, `Script`: instances, connections in any order, events, suspends and resumes, swaps), and it sorts each input's sources and orders the instances itself. The engine, `signal-graph` and the primitives are dev-dependencies of its tests, which run the same script through the block engine and compare the recorded audio (by bits), every `log.jsonl` line, every final parameter base and effective value, and every instance's suspension, mute and discard count.

- **Generated graphs** (`tests/generated.rs`, proptest, 256 cases fixed in the test whatever `PROPTEST_CASES` says; failures are kept in `generated.proptest-regressions`). Each case draws 2–12 instances of the standard types (`std.unit_delay` and `std.delay` likelier), with 0–2 sources on every input and parameter (modulation with scales, event connections), feedback only through state-output instances, and as the sink `oracle.probe` (eight inputs) or `std.audio_out` (its `gain`, sometimes modulated). It runs 256–2048 frames at 1, 4 or 48 kHz (fades of 5, 20 or 240 frames) with up to 12 external `set`, `ramp` and trigger events, suspends and resumes, and up to two swaps that add, remove (directly or suspend-then-swap), retype or rewire. The engine's plans are built from the spec through `signal_graph::build_plan`; the oracle's graph from the spec itself, its connections shuffled. Each case runs the engine at three configurations: a block size of 1–256 (often 1, 2, 3, 7, 64, 128 or 256), 1–8 threads (the first configuration always more than one) and a random partition. A configuration with more than one thread runs every segment on the workers (`Schedule::FORCED`) and asserts at least two tasks (a sink has no outputs, so it is a unit of its own), a parallel segment (true under `FORCED` while every task's log has room for the segment's staged external events, here at most 12 against the block capacity) and a task a worker ran (a test hook holds the caller at a job's start, for at most 2 s, until a worker has started one). `the_generator_covers_its_dimensions` checks that the generator makes every standard type, feedback, modulation, event connections, each kind of event, edits and swaps. Debug: about 13 s on the seat.
- **The goldens' projects** (`tests/goldens.rs`): `projects/kick` and `projects/pulse`, flattened by `signal-project` and converted to the oracle's graph in the test. Release builds (CI's `release-tests` job) run the whole golden render: the oracle's audio, as `audio.wav` stores it, has the golden's `audio_fnv1a64`, and its audio, log and end state equal the engine's (about 7 s). Debug builds compare the first 192 000 frames with the engine (about 4 s; the whole render would take about a minute there).
- A wrong oracle fails: with `Combine::Add` changed to subtract, the generated test fails at its first case.

### The V6 measurement

`signal_eval::aliasing` windows the signal with a periodic Hann window, takes a real FFT, and compares the energy within ±2 bins of the fundamental with the energy further than ±2 bins from every harmonic below Nyquist. The test analyses 96 000 samples (1 s, 1 Hz bins) after 1000 frames of start-up: a whole number of periods of every tone, so the window adds no leakage.

**Tones.** The tones are fixed at 1009, 2003, 4001 and 8009 Hz (owner decision sq-4aece389, option A). They do not divide 96 kHz, so the shaped tone is not periodic in whole frames and its aliases fall between the harmonics, where they are counted. The original tones, 1, 2, 4 and 8 kHz, divide 96 kHz: the shaped tone repeated every 96, 48, 24 or 12 frames, every alias landed exactly on a harmonic, and the test passed for naive `tanh` as well (ADAA 253–306 dB, naive 244–294 dB), so it could not tell antialiasing from none. That check is removed, not kept as a sanity check, because it measures nothing.

**Status: ignored pending the shaper fix.** The threshold stays at 60 dB. The current first-order ADAA `std.tanh_shaper` misses it, so the test is marked `#[ignore]` with the measured values, and it prints the shaper's ratio and that of naive `tanh(20·x)` on the same sine:

| Tone | ADAA (`std.tanh_shaper`) | Naive `tanh` |
|---|---|---|
| 1009 Hz | 49.0 dB | 43.8 dB |
| 2003 Hz | 33.5 dB | 27.3 dB |
| 4001 Hz | 26.1 dB | 18.5 dB |
| 8009 Hz | 22.0 dB | 13.1 dB |

Bringing the shaper to ≥ 60 dB is follow-up issue `2026-10-11-follow-up-bring-std-tanh-shaper-aliasing-to-60-db-on-off-div`, tracked for the M3 ADAA-versus-oversampling experiment. The `#[ignore]` is removed when that lands. The owner waived V6 for M1 on these values (sq-22037848; `roadmap.md`).

### The V8 measurement

**Early sweep.** The kick's pitch is f(t) = 48 + 132·e^(−t/τ) Hz, τ = 35 ms, t from the trigger frame (`projects/kick/composites/kick.toml`). From the first kick's trigger to 3τ (105 ms, before any ghost retrigger), the test locates every upward and every downward zero crossing of the left channel by linear interpolation, takes each crossing half a frame earlier (the shaper's delay), and reads each period between two like crossings as 1/(period). That reading is the mean of the instantaneous frequency over the period, so it is compared with the mean of f(t) over the same period, not with one point of the curve. The first period starts at the first downward crossing (≈ 2.8 ms); the output starts from 0 on the trigger frame, which is not a crossing. The onset is checked through the curve: f(0) = 180 Hz, and the test prints the onset the first period implies.

**Tolerance.** Per period, the sum of what the kick's own stages add to the reading, derived from its constants, and the measurement's resolution at the rate (`sweep_tolerance` in the test, with the derivation):

- the DC blocker's phase lead atan(10 Hz / f), which grows as f falls (≈ 0.23 Hz on the first periods, rate-independent);
- the oscillator's frame-by-frame phase sum and the feedback phase modulation, both offsets proportional to f/sr (≈ 0.06 Hz on the first period at 44.1 kHz, 0.01 Hz at 192 kHz);
- linear interpolation of a crossing of the shaped sine (below 0.001 Hz).

The resulting tolerance is 0.14–0.27 Hz. The test also requires it to reject τ counted in frames of another of the four rates (about 4 Hz off or more); a 1 % error in τ reads about 0.5 Hz off near t = τ and fails.

**Tail.** From 250 ms after the trigger to the next trigger, the frequency by zero crossings (`signal_eval::zero_crossing_frequency`) is 48 Hz within 1 %.

What remains is `seed`, `sample_rate`, `frames`, `provenance.project_file_hashes`, `log_fnv1a64` and `audio_fnv1a64`. Any change to the sound changes the audio hash; any change to an event changes the log hash; any edit of a project file changes its hash. The test also asserts that exactly these fields remain, so a field added to the manifest later must be added to the golden or listed above.

`tests/golden/pulse/manifest.json` is made the same way from `signal render projects/pulse --frames 3072000` (16 bars at 120 bpm and 96 kHz, seed 7), and `tests/golden/physical/manifest.json` from `signal render projects/physical --frames 1536000` (16 bars at 120 bpm and 48 kHz, seed 5); both are updated by the same rules.

### Updating a golden

A golden changes only for an **intentional** change of sound or of the project files:

1. Write a note saying what changed and why the sound is meant to change, and get it reviewed with the change.
2. Get a listening verdict on the new render from the PO, recorded in the repository like the milestone verdicts (V14).
3. Replace the golden with the fresh manifest that `golden_kick_16_bars` (or `golden_pulse_16_bars`, `golden_physical_16_bars`) prints when it fails.

A golden that changes without both the note and the verdict is a regression, whatever the metrics say.
