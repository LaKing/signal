# ADR 0048: The control thread never waits for the writer lock

- **Status:** Accepted (operator decision, 2026-10-31, a technical call the owner delegates). It answers an external review (Codex) and a second review of the first fix. **Supersedes part of ADR 0040**, item 2: "Waiting" (a writer waits at most 10 s) and "Re-entry" (a writer never takes the lock twice), for the UI host's control thread; for other writers (`signal vendor`, `signal snapshot`, the CLI, Signal.app's GUI thread) ADR 0040 is unchanged. The UI protocol gains the ordering below and the error codes `busy` (reused) and `project-changed`.
- **Date:** 2026-10-31

## Context
The UI host's control thread (`signal-control` in Signal.app, the host of `signal ui` and `signal mcp`) owns the `Controller`: it drains the runner's reports, detects hangs (`realtime-rules.md` "Hangs are detected, not contained") and answers every client. Under ADR 0040 each of its writers slept in `ProjectLock::acquire` while another process held the project's lock, up to 10 s. The review reproduced it: holding the lock 300 ms blocked `Host::write_windows` 311.5 ms.

A first fix queued the file requests. A second review then found that ordering mattered beyond the file requests: a live edit sent after a queued `commit` ran first and was then overwritten by the older committed value; a `retry` queued behind the lock could be overtaken by a `revert`; a Save could pack the `.signal` file before a commit queued before it; and a Save whose corrections (ADR 0042, 0043) met the lock reported success without them.

## Decision
1. **No wait on the control thread.** `Host::step` and `Host::wait` run under `transaction::NoWait`: an `acquire` there tries once and fails at once (`WouldBlock`). A file request takes the lock with `ProjectLock::try_hold`, which never waits.
2. **Re-entry through a `Holding`.** While the host holds the lock for a request, the writers it calls (`write_project`, the snapshot writer, `vendor::write`, …) take it as before; on the holding thread, for the same folder (device and inode), `acquire` and `try_hold` go on at once with a guard that releases nothing.
3. **A bounded queue, in the client's order.** A request that would wait goes into the host's queue (64 at most; one more is `busy`), with the open project's generation and the time it was queued. Each step runs the queue's head as soon as it can: one that writes files once the lock is free, holding it, its checks (`base`, conflicts) made then; the others at once when they reach the head. What queues:
   - **File writes** (`commit`, `retry`, `patch`, `schematic.*`, `snapshot.*` but `snapshot.list`, `panel.write`, `pattern.write`, `file.write`, `vendor`, and the window layout's `write_windows_then`): when the lock is held, or when anything waits already (so they keep their order).
   - **Saves** (`project.save`, the window's Save and Save As, `save_document_then`, `save_as_then`): when anything waits, or when their corrections are pending and the lock is held; they then run holding the lock, so the corrections are written first and the packed file holds every write asked before the Save.
   - **`project.open` and `project.revert`** (a client's message): when anything waits. The window's menu Open and Revert come to the host directly and do not queue; item 5 says what they do while writes wait.
   - **Live edits** (`set`, `ramp`, `trigger`, `note`, `revert`) of an address: only behind a queued request that can change that value, so the client's order holds per value: a `commit`, `retry` or live edit of the same address, a `snapshot.restore` or `snapshot.undo`, a `project.open` or `project.revert`. A live edit of another value goes on at once.
   - **Never queued:** `ping`, `describe`, `stats`, subscriptions, reads (`graph`, `modules`, `*.read`, `*.check`, `snapshot.list`), `setup.*`, `keys.*`, `app.*`, transport.
   A reply to a queued request can therefore come after replies to later messages; a queued commit sends its live value when it runs.
4. **Time-outs and stale requests.** A request that has waited 10 s runs without the lock, so its writer fails at once (`write-failed`, "another writer has held the project's lock for over 10 s"), as under ADR 0040; a queued Save then fails if its corrections are pending. A request queued for a project that is no longer open (the generation changed: the window's menu opened another, which comes to the host directly) is refused unrun, `project-changed`.
5. **A Save never drops its corrections or the writes asked before it.** A Save whose pending corrections meet another writer's lock is never made without them: the queued Saves wait for the lock (item 3). The waiting `save_document` (the window's Open with "Save", and a client's `project.open` with `unsaved: "save"`) fails with `not-saved`, nothing packed, when its corrections meet the lock **or while any request waits** (second review of batch 2: a Save made then would leave the queued writes out, and the Open after it would refuse them as another project's). For the window's Open of a `.signal` project, waiting writes count as edits: "Ask" asks (`edited`), "Save" is refused until they are written, "Discard" lets them go (each answered `project-changed`). A correction that fails otherwise (a read-only file) still does not stop the Save (ADR 0043's rule, unchanged).

## Consequences
- The control thread never sleeps on the lock: under contention its steps stay short, and pings, live edits of other values and status go on (`crates/signal-ui/tests/writer_lock.rs`).
- Replies are no longer strictly in the order of the requests; ids pair them.
- Signal.app's GUI thread still writes a previous project's layout (`flush_to`, when opening another project) with a waiting `acquire`. It is not the control thread; the window waits meanwhile.
- Panel files for a patch (ADR 0046) are read only when they are the project's own (`signal_ui::read_own_file`): no link on the way, checked again after the open against the opened file's device and inode, a regular file with one name (`nlink` 1: a hard link could be a file outside the project); it is opened only after a look says it is a regular file, with `O_NOFOLLOW | O_NONBLOCK`, so a FIFO or device at a panel's path never blocks the control thread. A swap made and undone within the open itself is not seen: it needs a local process racing the read, an accepted risk.
- Tests: `crates/signal-ui/tests/writer_lock.rs` (steps under 100 ms while another writer holds the lock; ping, a live edit of another value and `stats` answered; two queued commits in order; a live edit of the committed value kept behind its commit, so the newer value plays; one that outwaits the host's wait fails and stays unsaved), `crates/signal-ui/tests/app_mode.rs` (`a_request_waiting_for_the_lock_is_not_run_on_another_project`, `a_save_waits_for_the_writes_queued_before_it`, `a_save_whose_corrections_meet_a_held_lock_waits_or_fails`), `crates/signal-app/tests/server.rs` `the_layout_is_written_into_the_project_as_seen`, the unit test `a_held_lock_is_reentered_and_no_wait_never_waits` in `transaction.rs`, and `crates/signal-cli/tests/mcp.rs` `a_panel_file_outside_the_project_is_refused_unread` (links and a hard link).

## Alternatives considered
- **A worker thread for file transactions.** The writers read and change host state the control thread owns (the panel, the unsaved list, the `Controller` for a commit's live send), so a worker would need that state copied in and results merged back with generations; the queue gets the same non-blocking result with the writers unchanged.
- **Queue every message while anything waits.** Simple and strictly ordered, but a held lock would then stall pings and every live edit, the very stall this ADR removes.
