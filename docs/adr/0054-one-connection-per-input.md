# ADR 0054: One connection per input

- **Status:** Accepted (the owner's decision of 2026-11-05), amended the same day (§1: a control and a connection on one parameter meet in a module too). Phase 1 is in force; phase 2 follows once the owner's own projects are migrated.
- **Amends:** `docs/semantics.md` §3 (a signal input sums its connections) and §4 (an event input merges its connections' events), and ADR 0004's parameter as an input port (its modulation sum over several connections). It supersedes nothing else: fan-out (one output to many inputs) stays as it is, and so do a composite's exported parameter driving several inner parameters, the connection's `scale`, and a parameter's base set by its control (a knob, `set`, `ramp`). It amends ADR 0042's correction of a parameter value outside its range for a parameter a connection drives (§5).
- **Date:** 2026-11-05

## Context
Every input summed (a signal) or merged (events) all the connections into it, in canonical source order (semantics §3, §4). It is exact and deterministic, but it is invisible: at the Engine, `moog_voice`'s `ladder.cutoff_hz` took three ways at once (its knob as the base, `env_amt.out` and `key_amt.out` as modulation), and nothing on the drawing said that they add. The owner (2026-11-05): "Egy bemenetre nem csak egy vezeték csatlakozhat? … elágazni tud, de összegezéshez valamilyen aktív modul kell" — a wire may branch, but summing needs an active module. The owner chose this for event inputs too (the operator had proposed signals only).

## Decision
1. **One connection per input.** Every input port, signal or events, and every parameter takes at most one connection. A parameter takes its control (its base, ADR 0016 §4: a composite's exported parameter, a knob) or one connection, never both (the owner, 2026-11-05: "Egy bemenet std.* összeadókkal, nem egy bekarikázott + -al"): a knob that sets the base of what a connection modulates is a `std.const` (the knob sets its `value`) into a `std.add` with the modulation, the sum the parameter's one connection and its base 0. The operator had first drawn the two meeting at a "+" mark on the pin; the owner rejected it.
2. **Summing and merging are modules.** Signals are summed by `std.add` (two inputs) or `std.mix` (four, each with a gain); events are merged by `std.merge` (four event inputs, delivered in a frame `a`'s first, then `b`'s, `c`'s and `d`'s, each in its own order; at most 16 per frame, as every event output). What was implicit is now an instance on the drawing, with a name, and its order is its ports' order, not the sources' addresses.
3. **Fan-out stays.** One output may go to any number of inputs; at the Engine a branch is a dot.
4. **Phase 1 (now).** A plan with a fan-in still builds and plays as before (the sum, the merge, in canonical source order), with a warning per input (`GraphWarning::FanIn`, its connections named) that `signal check` and the UI show. Every editor refuses to make one: the `patch` op that adds a connection into an input that has one, or into a parameter an export of its composite sets, and the `export.connect` of a parameter onto one a connection drives, are refused (`fan-in`), and the plane's drop hints say so. (A control and a connection on one parameter is no graph warning: the plan sees a base and one connection.) The built-in library and the repository's example projects are migrated (an explicit `std.add`, `std.mix` or `std.merge`, each source on the input its old canonical order gave it, so the output is the same bit for bit: `(0 + a) + b` is `a + b`, and a merge's ports keep the sources' order; a control and a connection as §1 says, the knob's `std.const` on `a`, `base + m` being `0 + (base + m)`); a golden render that would change by it is the owner's decision, as always. Test fixtures that exercise the sum itself keep it until phase 2, and the owner's own projects (`projects/kick` among them) are the owner's to migrate.
5. **A driven parameter's base is an offset.** The base of a parameter a connection drives is what its sum is added to (0 after the migration of §1), and is not corrected to the parameter's range (ADR 0042's correction stays for every other value): its effective value is clamped every frame as before (`docs/semantics.md` §4), so `std.ladder`'s `cutoff_hz = 0` (range from 1 Hz) under a sum of 300 Hz and its modulation plays what the base 300 under the modulation played, bit for bit.
6. **Phase 2 (later).** Once the owner's own projects are migrated (the operator edits none of them without the owner's word), the warning becomes an error (`GraphError::FanIn`), and `docs/semantics.md` §3 and §4 lose their fan-in sums.

## Consequences
- What a connection carries is what its input reads: the Engine draws one wire into every input, and a sum or a merge is a card of its own.
- Orders change meaning: a merge orders events by its ports (`a` before `b`), where the implicit merge ordered them by the sources' addresses, so renaming an instance no longer reorders them. A sum of more than two signals through chained `std.add` is the chain's order, which may differ in its last bits from the canonical one; a migration that changes a golden is reported, never regenerated silently.
- An input a library restricts (ADR 0024) already had at most one connection; it is now the general rule.
- At the Engine a parameter is entered by one way: its control's leg or one wire. A file from before this ADR that still has two (a fan-in, or a control and a connection) is drawn with the pin dashed and its warning in the pin's tooltip, never summed on the drawing.
- Tests: `crates/signal-graph` (the warning: two connections into a signal input, into a parameter, into an event input; none for a fan-out; a driven parameter's base kept as written, `errors.rs`), `crates/signal-project` (the `patch` refusals: a second connection into an input, a connection into a parameter an export sets, an export onto a parameter a connection drives), `crates/signal-std` (`std.merge`: order, the 16-event cap, the module contract), the migrated library's own tests and the golden renders.
