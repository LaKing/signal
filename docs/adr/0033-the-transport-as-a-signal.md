# ADR 0033: The transport as a signal

- **Status:** Accepted (owner's direction of 2026-10-22, translated: "Start-stop is perhaps not the top-level app's job but a thing inside a project, with tempo etc." … "The transport is a composite too — it can be simple, start-stop and tempo, but it can be embellished: turntable-like speed control, dragging and spinning up, or OSC or MIDI control, maybe song-mode fast-forward — but I would carry this on a signal wire too; there may suddenly be two such transports if we want to mix two projects into one." … "And then this can be needle-precise, right?" — yes: sample-accurate; design by the operator, delegated). Builds on ADR 0003 (the core knows only frames), ADR 0028 (patterns, the tick clock, the sequencers) and ADR 0024 (rules on inputs the library declares); changes ADR 0023's toolbar (Play and Stop removed). Supersedes nothing: the tick clock and every golden stay.
- **Date:** 2026-10-22

## Context
Musical time is `std.transport`: a tempo clock whose `tick` events the sequencers count (ADR 0028 §5). A count only goes forward one tick at a time. It cannot stop in place and go on, jump to a bar, run backwards, slow down like a turntable, or follow an external clock, and a project cannot hold two independent ones in a way a person can see on a wire. Play and Stop are the app's toolbar buttons (ADR 0023), so starting and stopping is the application's state, not the project's, which is the opposite of rule 4 (text is the truth) for something a project means.

The owner wants the transport to be an ordinary composite in the project, carried on a signal wire, embellishable, possibly twice in one project, and needle-precise.

## Decision
1. **A position signal: `std.playhead`** (in `signal-std`, category `event`; tempo is a library concept, never the core's, ADR 0003). Outputs `position` (signal, beats, f64), `running` (gate 0/1), `tempo` (bpm·rate while running, else 0) and `jump` (events: one `Trigger` on every frame a seek lands on). Parameters `bpm` ([20, 400], default 120, as `std.transport`'s), `run` (gate, default 1, so a project with a transport plays as soon as it starts; combine **`replace`**, so a connected gate — OSC, MIDI, a sequencer — starts and stops it, where `add` would keep 1 + 0 running) and `rate` (a multiplier of the tempo, [−16, 16], default 1, combine **`replace`**: unconnected it is its base, connected the signal replaces it; 0 holds, negative plays backwards: scrub, turntable, reverse, fast-forward). Input `seek` (events): `Set(b)` jumps the position to *b* on its frame, `Trigger` to 0 (rewind).
   **Precision (normative, tested in `crates/signal-std/src/playhead.rs`):**
   - With *v(n) = run·bpm·rate / (60·sr)* beats per frame, `P(n + 1) = P(n) + v(n)`, `P(0) = 0`. Within a **segment** (bpm, rate and run unchanged, no seek), `P(n) = p₀ + ((n − f₀)·(bpm·rate·run)) / (60·sr)`: computed from the segment's start, never summed per frame. **No accumulated drift**: at an integer `bpm·rate` the position is the exact one correctly rounded on every frame, however long it runs (tested over one hour at 132 bpm and 48 kHz, 172.8 million frames, every second checked bit-exactly, ending on exactly 7920 beats; a plain per-frame sum is off by about 9·10⁻⁶ beats by then).
   - At every change the segment is **rebased** (`p₀ ← p₀ + (n − f₀)·v`) with Neumaier's compensated summation into a (sum, compensation) pair. A `rate` that changes on every frame makes every frame a segment of one, so the position is a compensated sum of the per-frame speeds since the last seek (tested over one hour with the rate alternating every frame: within 4 units in the last place of the exact value at every sampled frame, measured 0; a plain sum is off by about 1.4·10⁻⁶ beats).
   - The state depends only on the frame values: identical for any k-partition and thread count (tested in calls of 1, 7, 64, 4096 frames and a mixed cycle, with tempo, rate and run steps and sweeps, seeks, a stop and a reverse; and in the engine on 1 and 4 threads, below).
   - Bound: the position is clamped to ±10⁶ beats (the engine's magnitude bound; 5.8 days at 120 bpm), where it holds.
2. **Connected inputs, domain-free** (`signal-core`, `signal-graph`, `signal-engine`, `signal-oracle`). A primitive can ask whether a port of its descriptor has a connection: `Inputs::is_connected(port)`, from the plan, the same for every call of a plan and changed only at a swap (the slot is rebuilt with the plan, so a swap that connects or disconnects an input reaches the kept instance at the swap frame, allocating nothing; `crates/signal-engine/tests/connected.rs`). An unconnected input still reads 0 (`semantics.md` §3); the flag tells it from a source that outputs 0. And a library can make two inputs of a type **exclusive** (`Registry::exclusive_inputs`, a structural rule like ADR 0024's restricted inputs): a plan that connects both is refused with `GraphError::ExclusiveInputs`, located at the connection into the second ("`/transport.position -> /drums.follow: /drums.follow and /drums.tick are both connected; a std.step_seq8 takes `tick` or `follow`, not both`"). Neither names a domain concept (`crates/signal-engine/tests/domain_scope.rs`).
3. **Sequencers follow a position.** `std.note_seq` and `std.step_seq8` get an optional signal input **`follow`** (beats): the operator's design called it `position`, but `std.note_seq` already has a `position` output and a type's ports share one namespace (ADR 0028 §6's note). Connected, it drives the sequencer instead of `tick`; both connected is refused (2). Unconnected, nothing changes: the tick path is bit-identical (every golden and render hash below is unchanged). Each frame compares the position *x(n)* with the frame before (`crates/signal-std/src/follow.rs`):
   - **Forward by at most one beat:** the beats crossed, `[x(n − 1), x(n))`, fire what starts inside them, looping over the pattern's length (loop *m* starts at *m·L*): a note fires on the first frame whose position is past its start, exact in beats (no ticks, no `ppq`); its end is its start plus its length in beats, and it ends on the first frame past that; steps fire at `i·step` (+ `swing/100·step` on odd steps, exact, so nothing wraps). Consecutive frames share their bound, so every beat is crossed by exactly one frame. This is the operator's half-open `[prev, cur)`: on a grid that falls on whole frames, a sequencer following `std.playhead` plays exactly what the same sequencer counting `std.transport`'s ticks plays, **one frame later** (the tick lands on the beat's own frame, the crossing on the first frame past it): tested sample for sample and event for event on both sequencers (`follow.rs`) and on every drum hit of the studio (below). 1 frame is 21 µs at 48 kHz.
   - **Not moving** fires nothing and ends the sounding note: a stopped transport releases its note (there is no `running` input; a stopped position simply does not move).
   - **A seek** is marked on the sequencer's `reset` input, where `std.playhead.jump` arrives on every frame a seek lands (`lib.transport` exports `jump`; `projects/studio-transport` wires it): a forward seek of at most one beat cannot be told from motion on the position alone (it would fire every step it skips, merged on one frame, and start the last skipped note late). As a fallback for a position from elsewhere, a move backwards, more than one beat forward, more than 64 loops in one frame, the first frame, and a swap that connected `follow` are seeks too. On a seek nothing fires retroactively, the sounding note ends on this frame, and the next frame resumes from the new place. A note starting exactly there fires (a rewind plays the downbeat); **a note that spans the new place is not restarted** — it began before the place, so playing it would start a note late and cut at its start, and the next note plays on time. A transport playing backwards therefore plays nothing.
   - `note_seq.position` shows the exact place in the loop, `step_seq8.step` the step whose grid beat is at or before it. `ppq` is not read.
4. **`lib.transport`**, a library composite (`crates/signal-lib/lib/transport.toml`, the `## 0.2` changelog section, pinned `7f20f2bbed23372b`): `std.playhead` with `bpm`, `run`, `rate` and the `seek` input exported and `position`, `running`, `tempo` and `jump` out (wire `jump` into the sequencers' `reset`). It is the extension point: vendored (`signal vendor`), it can be embellished (a spin-up lag on `rate`, a scrub wheel, an external clock smoothed into `rate`, song-mode jumps into `seek`); two transports are two instances, each with its sequencers. **It has no `tick` output:** a tick count cannot follow a seek or a reverse (a counter has no way to jump back), so a tick derived from the position would be exact only while it plays forward; sequencers follow the position directly, and `std.transport` keeps the tick clock for the counted path.
5. **Panels control library composites.** A panel binds the exported parameters of a `lib.*` instance (`/transport.run`) as it binds a project composite's (`crates/signal-ui/src/panel.rs`): before, only project composites' exports were controls.
6. **The studio stays as it is** (its golden, `ae83d794a40b6941`, unchanged). **`projects/studio-transport`** is a copy wired through `lib.transport` and position-following sequencers, with a panel card **Transport** (a play toggle bound to `run`, Rewind, a button into `/transport/playhead.seek`, the tempo knob, moved from the rhythm section, and a rate fader). Its golden (`tests/golden/studio-transport/manifest.json`, 16 s) is new, not a regenerated one (`testing-and-evaluation.md`).
7. **Signal.app: no Play or Stop.** The toolbar keeps the power switch; **Project ▸ Restart from Files** (native menu, and the context menu in place of Play/Stop) sends `transport.play`, which plays the open project again from frame 0 from its files, playing or not. **The project plays while the power is on** (`AppHostConfig::plays`, which Signal.app sets): when the app starts, when a project opens (while off: when switched on), when the power comes on. A project that does not load, or a device that fails, stays stopped with the reason in the window until the next open, switch-on or restart. The protocol renames nothing: `transport.play` and `transport.stop` stay for `signal ui`, `signal mcp`, scripts and tests; in app mode `transport.play` while playing now restarts (it did nothing, since the toolbar disabled Play while playing), as `signal ui`'s already did. One flow changes: Setup ▸ Refresh, refused while playing (listing devices pauses metering), now says to switch the power off.

## Alternatives considered
- **A `tick` derived from the position** in `lib.transport` for the old sequencers: exact only for forward motion (a seek or a reverse cannot be counted), and redundant once both sequencers follow a position; left to `std.transport`.
- **A `running` gate into the sequencers** to release notes on a stop: a stopped position does not move, which says the same without a second wire, and keeps one input per sequencer.
- **A mode parameter on the sequencers** (ticks or position): a setting that can disagree with the wiring; the wiring itself (`is_connected`) decides, and the graph refuses the ambiguous case.
- **A sentinel value** on the position (e.g. NaN when unconnected): an unconnected input reads 0 by the semantics, and any value is a valid position; connectivity is a property of the plan, so the plan says it.
- **Inferring every seek from the motion alone:** a forward jump of less than a beat looks like fast motion; an explicit `jump` event marks it, and the inference stays as a fallback for positions from elsewhere.
- **The interval `(prev, cur]`** (a note fires on the frame whose position reaches it, frame 0 for the downbeat): it misses a note exactly at the place where a stopped or rewound transport resumes (`(p, p + v]` excludes *p*) unless a seek fires notes at its own frame, which would play a note before the transport has started moving. `[prev, cur)` resumes correctly everywhere at the cost of one frame against the tick clock, uniformly.
- **Summing the speed per frame** (a phasor): drifts with the number of frames (measured above); the segment formula has none at a steady tempo, and the compensated sum keeps a modulated one within a few units in the last place.
- **Keeping Play and Stop in the toolbar** beside the transport: two places that start and stop one project, one of which is not in its text.

## Consequences
- `signal-core` gains `Inputs::with_connected`/`is_connected` and `Registry::exclusive_inputs`; `signal-graph` a `GraphError::ExclusiveInputs` check; the engine and the oracle hand every call its plan's connections. The module contract documents both (`module-contract.md`).
- `std.playhead`; a `follow` input on `std.note_seq` and `std.step_seq8` (their descriptors gain a port, so `signal modules` lists it); `lib.transport` in the library (`NOT_IN_DEMO`: the library demo's golden is never regenerated).
- `projects/studio-transport` and its golden; the kick, pulse, physical, physical-av, studio and library-demo renders are unchanged (`signal --json render projects/<p> --seconds 120`, release: 9eec9e756e2d891d, 0e2925144758dd17, a3381da11f117c70, 6e949ac556b7e1b5, ae83d794a40b6941, c625006298c22e3b).
- Signal.app's toolbar loses Play and Stop; the native menu gains Project ▸ Restart from Files; app mode plays while switched on.
- The owner's listening verdict on `projects/studio-transport` (start, stop, tempo, a jump on its panel) is the milestone's exit condition (`roadmap.md`, M3.1).
