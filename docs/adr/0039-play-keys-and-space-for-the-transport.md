# ADR 0039: The piano roll's keys play, and Space plays and stops the transport

- **Status:** Accepted (operator decision, 2026-10-23, from the owner's request, translated: "In the piano roll, could the piano keys be pressable? … Space should be start-stop of the sequencer"). Builds on ADR 0033 (the transport as a signal: `std.playhead`'s `run`), ADR 0034 (one keymap, scopes and precedence, the bare-key rule for the menu), ADR 0028 (patterns, `std.note_seq`) and ADR 0035 (an include's controls). Supersedes nothing; changes ADR 0034 §4 (Space and Shift+Space no longer scroll the view) and fills its "window" level of precedence (the `project` scope).
- **Date:** 2026-10-23

## Context
The piano roll's keyboard strip only showed the keys; pressing one did nothing, so a melody could be edited but not tried out by ear before it was written. Notes reach an instrument only from the pattern: `std.note_seq` plays its table, and there was no path for a note played by a person.

Starting and stopping is the project's since ADR 0033 (`/transport.run` on studio-transport's Transport card), but only by clicking that toggle. Space, the usual play key, scrolled the page down a screen (ADR 0034 §4), which nobody asked for once Page Up and Page Down did.

Two constraints shape both: the core knows no notes (rule 1), and where sources meet they combine in canonical order (rule 3).

## Decision
1. **`std.note_seq` gets an optional event input `audition`** (in `signal-std`: notes are a library concept, the engine only carries the events). Its value is a whole note in one event, so a note's key and velocity can never arrive on different frames: `Set(128·key + v)`, `key` an integer in [0, 127], `v` an integer from 0 to 127, MIDI's convention: `v ≥ 1` starts a note at velocity `v/127`, `v = 0` ends the held note if it has that key, a `Trigger` ends it whatever its key. Anything else (another value, a `Ramp`) does nothing. `signal_std::audition_value(key, velocity, on)` encodes it (velocity rounded to 127ths, at least 1 for a note on).
2. **Merged into the voice, in canonical order.** A frame's `audition` events apply after the frame's pattern ticks (or crossing of the followed position), in their order on the port, which the engine fixes (by stamp, then source; rule 3). A held audition note **takes the voice**: it starts as a pattern note does (`key`, `hz`, `velocity`, `on`, the gate high; the note it takes over from ends, merged into the frame's `off` and `on` by the existing per-frame rule), the pattern's notes starting while it is held are not heard, and when it ends the pattern's note it took over from does not come back (as ADR 0028's last-note priority: a note taken over from never resumes): the next pattern note plays on time, also one starting on the very frame of the release (its `off`, then the pattern note's `on`, the gate staying high; a key pressed and released within one frame was never held before it, so there the pattern's note stays taken). A second audition note takes over from the first (a slide across the keys: legato). The pattern's position, loop and ticks go on underneath, unchanged; a `reset` or a seek does not end an audition note. `process` allocates nothing and its output is the same in any partition (the contract suite, both modes). **Unconnected** (every existing project) nothing changes: no events, no held note, every output bit for bit as before, every golden unchanged.
3. **A protocol message `note`** (`docs/ui-protocol.md`): `{"type": "note", "address", "key", "velocity", "on"}` to an event input **named `audition`** of the running plan (any other event input is refused, `not-an-audition-input`: there the value would be an impulse of up to 16383 or thousands of ticks), through the Controller as `trigger` goes and acknowledged the same way; the server encodes the value (1). A generalised `trigger` with a value was the alternative; a `note` keeps the encoding in one place (the library's function) and lets the server **end a client's held notes when the client goes** (a closed page, a lost connection), so no note outlives the hand that holds it: per client and port it keeps the last note on, and a note off removes it only when its key matches (the off of a key slid away from, or of a second roll's key on the same port, leaves the held key). A note off the Controller refuses stays held there; the page sends it once more after 100 ms. It is never saved (no parameter, so nothing is unsaved); a session records it as the `set` of an event input it is, which `session-format.md` already allows and replay already plays (tested).
4. **The piano roll's keys** send it: a press on the keyboard strip is a note on, the release (or a cancel, a lost pointer capture, the roll leaving the page or changing connection) its note off; the pointer is captured. **Velocity** grows from 0.3 at the key's far end to 1 at its tip, along the key's own length (a black key is shorter): a fixed velocity would be simpler, but the sequencer's `velocity` already drives the voice in the studios, so where the key is pressed is heard. **A slide** over the keys moves the note: the new key first, then the old one's off, which the sequencer ignores (it no longer holds that key), so the voice goes on legato and glides where its `glide` says. The held key is lit. **Where the notes go:** the roll's new `audition` attribute (an event input named `audition`, or `none`, checked by `signal ui check` and `panel.check`); without it the `audition` of the sequencer whose `position` the roll's `position-bind` already follows when it has one (`/melody.position` → `/melody.audition`: the roll's playhead names its sequencer, so studio and studio-transport need no change); else, when the project has exactly one `std.note_seq`, its `audition`; else none. With no target, nothing playing or no connection, a press only lights the key, and a refused note is not reported (no error per press).
5. **Space plays and stops the project's transport.** A new keymap command **`transport.toggle`** ("Play / stop the transport", `Space`) in a new scope **`project`**, the parent of `view` (whose parent was `app`): precedence is now text field, focused control, view, project, app (ADR 0034 §3's "window" level). `view.page_down` and `view.page_up` lose `Space` and `Shift+Space` and keep Page Down and Page Up. A focused button, toggle, step grid, meter or scope keeps its own Space (their scopes shadow the project's, as the built-in keymap always had them shadow the view's), as do a native button or link, an open menu and a text field; a focused fader, knob, pad, value, piano roll or schematic has no Space, so there it plays and stops.
6. **What it toggles:** never the app's power or the run (`transport.play` and `transport.stop` stop the audio), but the `run` of the project's `std.playhead` instances, through the top-level controls (`describe.controls`) whose plan ports reach one: studio-transport's `/transport.run`, a composite's export; an include's transport is a control of its own. A control whose run a connection drives (`modulated`) is skipped: a value set by hand would not be what plays. Several are **toggled together**, so two transports (two-studios) stay in step: if any runs (base ≥ 0.5) all stop, else all play. Each is written as a click on its toggle writes it (`commit`: live, then `project.toml`), so the unsaved marks, the toggle on the panel and every other client see exactly what a click does; a press before the next `describe` push counts what this page sent (forgotten again if that write is refused). Nothing to toggle, nothing playing, no connection: nothing happens, silently. The pure part is `ui/lib/transport-toggle.js`; `ui/controls/keyboard.js` runs it on the page's own connection, so it works in Signal.app's main window and its tabs, its panel windows and frames, the schematic window, and `signal ui` in a browser.
7. **Not a menu item.** Project ▸ Play/Stop Transport would want Space as its chord, which ADR 0034 §12 refuses for the menu (the native menu would take it from every text field), and a menu item without a chord would need the app to ask a page for the description. It stays a page command; the menu keeps Restart from Files.
8. **Conflicts.** A control's chord hiding a parent's is reported only where the built-in keymap has no such shadow for the same chord, scope and command, whichever parent it hides (`ui/lib/keys.js` and `crates/signal-ui/src/keys.rs` alike): a person who puts Space back on `view.page_down` is told that it hides the transport there, once, not again for every control that keeps its Space.
9. **Not a tool of `signal mcp`.** A held note sounds until its note off and is a new source of modulation in every gain fan-in the sequencer reaches, which the gain guard cannot judge beforehand (`agent-interface.md`); an agent edits a pattern, which is checked. Space is a page key, so the agent has `set_parameter` on `/transport.run` as before.

## Alternatives considered
- **Two inputs, key and velocity** (or the velocity as a parameter): a note split over two events can land on two frames, and a velocity parameter would be a saved value changed by playing. One event per note is atomic.
- **Pattern priority** (the pattern's notes take the voice back from a held key): what is pressed would cut in and out with the melody; while auditioning, the key held is what should sound.
- **A separate audition voice** (a second gate and key output): every instrument would need wiring for it, and the studios' voices are monophonic; merging into the existing outputs makes it work wherever the sequencer is wired.
- **A generic `send` of any payload to an event input**: the encoding would live in the page, and the server could not end a lost client's notes by key.
- **Space toggling the power or `transport.play`/`stop`**: those stop the audio and the device; ADR 0033 made starting and stopping the project's own `run`.
- **Shift+Space for the transport, Space kept for scrolling**: the owner asked for Space, and Page Up and Page Down scroll since ADR 0034.

## Consequences
- `std.note_seq`'s descriptor gains `audition` (`signal modules` lists it; the schematic shows the pin); no library composite uses `std.note_seq`, so no pinned library hash or changelog entry changes, and every render golden is unchanged (the input is unconnected in every project). `signal-ui` depends on `signal-std` (it was a dev-dependency; the lock file is unchanged).
- The UI protocol gains `note`; the server keeps each client's held notes.
- The keymap gains the `project` scope and `transport.toggle`; Space and Shift+Space no longer scroll; `keys.toml` overrides that name `view.page_down` with Space still read, now reported as hiding the transport.
- The piano roll gains `audition` (in `ui/lib/panel-whitelist.json`) and playable keys.
- The owner's verdict (pressing keys on studio-transport's roll while it plays and while stopped, and Space in the main window, a panel window and the schematic) is the exit condition (`roadmap.md`).
