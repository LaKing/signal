# ADR 0053: A project's panel acts only on its project

- **Status:** Accepted (operator decision of 2026-11-01, on the owner's delegation of the panel trust model question raised by the review of 2026-11-01).
- **Builds on:** ADR 0023 (the UI protocol and its session token), 0032 (Signal.app opens projects; panel windows), 0049 (mutations name the project they mean). It supersedes nothing; it narrows what the token handed to project content allows.
- **Date:** 2026-11-01

## Context
The review of 2026-11-01 (`panel-script-holds-token`, P1, reproduced in process) found that a project's panel, `ui/main.html` and the scripts it loads, received the session token: in a Signal.app panel window through the window page's URL fragment (its same-origin frame can read it), and from `signal ui`'s printed panel URL. With it, a downloaded project's script could `project.open` any other folder, rewrite that folder's files, change the machine's Setup and keymap, and send data to another host with `fetch`. The owner's open question was whether panels are trusted code.

## Decision
1. **A panel is project content.** A project's panel, its scripts and its skins are code that came with the project, possibly downloaded. They are trusted only within their own project. Signal's own pages (`ui/app/`, the schematic, Settings), `signal mcp` and the CLI keep full authority.
2. **A panel token.** The server makes a second token, the *panel token*, for the project open now: its identity is a `.signal` project's file (so Revert to Saved keeps it), `signal ui`'s project as given, else the folder. Whenever another project is open, a new panel token is made, every client of the old one is closed, and the old one admits nothing more. Pages that run project content get only the panel token: `signal ui`'s printed panel URL, and Signal.app's panel windows, whose page (`ui/app/panel-window.html`) holds the project's frame; Signal.app loads its panel windows again with the new token when another project opens.
3. **What a panel token allows.** Its client (`welcome.scope: "project"`) may send what a panel and a panel window need: reading and streaming the project, live edits and commits, its own files (each confined to the project by its existing rules), snapshots, the transport, Save of a `.signal` project, and the reads `app.get`, `keys.get` and `slot.projects` (the sibling projects a slot can load, by name, description and ports). Everything else is refused, `not-allowed`: `project.open`, `project.revert`, `setup.*`, `device.route`/`device.unroute`, `keys.set`/`keys.reset`, `app.power`. The check is made in the host before a message is queued or run (`crates/signal-ui/src/host/scope.rs`), and a message from a client whose project is no longer open is refused (`project-changed`) even before it is closed; a panel client's messages that arrive, or wait for the writer lock, after it was evicted or closed are refused unrun, so a gone client never falls back to the session's authority.
4. **Nothing off-host, no service worker.** Every file served carries a Content-Security-Policy that allows scripts, styles, images, fonts, media and frames only from the server, connections only to it and its WebSocket, no workers, no plugins and no form posts; a request for a service worker's script is refused. A skin URL or panel style sheet on another host is refused by the UI library too.
5. **Defence in depth, not the boundary.** The panel window's frame gets `sandbox="allow-scripts allow-same-origin allow-forms allow-modals allow-downloads"`: it cannot navigate the window or open popups. A same-origin script can lift such a sandbox, so the boundary is the token, not the frame. Cross-origin isolation of the frame (serving project content from another origin) was considered and not taken: the panel window's page reaches into its frame to show only its cards (`ui/app/lib/cards.js`, `view-state.js`), which a cross-origin frame forbids, so it would need a message protocol between them; the token gives the same guarantee for the project's authority without that.

## Consequences
- A malicious panel can still do anything its own project's files allow (rewrite its `project.toml`, play loud within the project's own gain, which the output adapters bound as before), read the sibling project listing, and trigger the native menu's commands through the window's IPC (each of which asks the person or acts on the open project). It cannot open another project, write outside its own, change the machine's Setup or keymap, or connect to another host by fetch or WebSocket. Channels the CSP does not govern remain: WebRTC, DNS prefetch, and (in `signal ui`'s browser only; Signal.app's windows navigate only to its server) a page navigating itself away.
- A project's own `project.toml` can name other project folders as slot contents or includes (`project = "../pulse"`, ADR 0037), which the engine then reads as modules; a panel's `patch` can add such a reference as a person's edit would. That reading is the project format's, not the panel's (the downloaded `project.toml` can name any folder by itself), and is not narrowed here; `signal mcp` keeps its `--load-root` rule for agents.
- `signal mcp --attach` needs the session token (the `ui at` URL), not the panel URL.
- The main window renders a panel's written content within the editor's whitelist and its SVG skins through the sanitizer (namespace-aware since the same review), never the panel's scripts, so it keeps the session token.
- Tests: `crates/signal-ui/tests/panel_scope.rs` (`a_gone_panel_s_messages_never_run`: a panel's `project.open` and `keys.set` arriving just after the app's open never run; the malicious panel fixture `tests/fixtures/malicious-panel`: `project.open`, a `file.write` of another folder, `setup.apply`, `keys.set`, `app.power`, `device.route` and `project.revert` refused with nothing done; its own project still read; closed and its token refused once the app opens another project; both transports), `crates/signal-ui/src/http.rs` (the policy and the service-worker refusal), `crates/signal-app/src/window.rs` (a panel window's URL carries the panel token). Checked in headless Chrome under `signal ui --driver null` on a scratch copy of `projects/studio`: the panel, a panel window, the app page, the schematic and the test page load and connect under the policy with no violation.
