# ADR 0032: Several windows over the screens

- **Status:** Accepted (owner's requests of 2026-10-22, translated: "I have several screens, but the app currently uses only one screen. There should be some mechanism so that every screen can be used."; then, of the panel's cards: "These should be freely movable, drag-and-drop style. The Window menu should have a reset option that puts everything onto the primary window. If not every screen is present, or the screen resolution or the screen type changes, it should automatically reset to a default state. The screen layout may be part of the project, but behind a key that describes the screens: resolution, arrangement, etc."; design by the operator, delegated). Extends ADR 0023 (one window with a WebView on the app's server); supersedes nothing.
- **Date:** 2026-10-22

## Context
Signal.app had one tao window with one wry WebView on its own UI server (ADR 0023). The server already serves the app's page, the schematic alone (`/schematic`) and the project's panels (`/project/…`), and takes up to 32 WebSocket clients at once, each sent every push (`ui-protocol.md` "Delivery"), so several pages on one running project stay consistent: the project's files are the truth and every client is told of every change. What was missing is more windows, a way to spread the panel over them, and a way to come back to the same arrangement on the same desk without carrying a wrong one to another.

## Decision
1. **Several windows.** Signal.app opens any number of windows on the one running project and server, each a tao window with its own WebView, which can be dragged to any screen or made full screen natively. A window shows one view: **main** (the app's page, as before), **schematic** (the schematic page alone) or **panel** (`ui/app/panel-window.html`: the project's main panel in a frame, showing the cards that window holds). Every window is one more client of the same server, with the same session token, so nothing new is needed on the server for them; a test connects three clients and sees one's Play pushed to the others (`crates/signal-app/tests/server.rs`).
2. **Menu.** A native **Window** menu: New Main Window (⇧⌘N), New Schematic Window, New Panel Window (an empty panel window to drop cards into), Reset Layout, then the system's Minimize, Zoom, Enter Full Screen and Bring All to Front, and the system's list of open windows (`set_as_windows_menu_for_nsapp`). A window's title says its view: "Signal — Schematic — kick.signal", "Signal — Panel — kick.signal"; a main window's stays the project's title. Save and Interface Setup go to the front main window's page; without a main window, one is opened for them.
3. **Closing.** Closing a window closes it; closing the **last** window quits as closing Signal's one window did, with the "Save changes?" prompt for an edited `.signal` project (and Cancel keeps it open). Quit asks the same. This is the macOS behaviour of an app whose windows are views of one document, and keeps every existing prompt.
4. **The screen configuration's key.** The connected screens are described by a readable key: for each monitor (by position, left to right, then top to bottom) its name as tao gives it (on macOS `Monitor #<model number>`, the monitor's type), its size in pixels, its scale factor and its top-left corner in pixels, joined by ` | `, e.g. `Monitor #41234 3024x1964@2 +0+0 | Monitor #16711 2560x1440@1 -2560-200` (`layout::screen_key`). Another resolution, scale, arrangement or monitor, or a missing screen, is another key. The screens are looked at once a second (tao reports no screen change on macOS). A new key is taken only after 3 polls in a row see it (displays waking or reconfiguring are left out of tao's list, or report a scale of 1, for a moment); a poll that lists no screen (every display asleep) waits, however long; a key that comes back to the one taken within those polls changes nothing. While the screens are unsettled nothing is applied and nothing is written, and what changed meanwhile is dropped: macOS migrates the windows off an unplugged screen, and those moves are never written, under the old key or the new (`layout::Tracker`). One display asleep while the others stay is indistinguishable from one unplugged (tao gives no sleep state): after the 3 polls the other key's layout (or the default) applies, nothing is written for it unless the person changes it, and when the display returns its key's layout, never overwritten, applies again.
5. **The layout is project text, behind the key** (rule 4: the GUI holds no hidden state). `ui/windows.toml` in the project folder holds one entry per key: its windows in order, each with its view, its screen (an index in the key's order), its frame's corner from that screen's in points, its content's size in points, and for a panel window the ids of the cards it holds (a main window's `cards` are the order of the cards it shows first). It is presentation only, like `ui/schematic.toml`: it never changes what the project plays, renders or hashes (no file `signal render` loads); it is packed in a `.signal` file like every file under `ui/`, so moving a window edits a `.signal` project. The app writes it a second after the last move, resize, open, close or card move (once a poll after it saw the same screens), without waiting for the answer (the event loop never waits for the write and its sync; a failure goes to the log and is tried again once settled anew), through the control thread (`Host::write_windows`: atomically, through a hidden temporary file, the watch taking the write as seen, so nothing reloads; refused for a project that is no longer open and through a linked `ui/`), with `toml_edit`, changing only the current key's entry: other keys' entries and the file's comments stay as written. A layout that is the default state is written as no entry. A window's place and size are its normal frame's; a full-screen window records `fullscreen = true` and opens full screen again. **The guard:** for 2 seconds after a layout is applied (or the screens were unsettled), the windows' moves and resizes are the system's (placing, constraining, migrating) and are not changes; a window opened or closed, or a card moved, always is; a move after the guard is the person's and is written. Quit and opening another project write what is pending at once, the guard kept. A project opened from a page (its Setup tab) is told to the app afterwards: the pending change is then written into the previous folder project directly.
6. **The default state.** One main window, centred on the main screen (the one with the menu bar) inside its visible area, of the Setup's `[window]` size (else 1200×800 points, no larger than the screen), holding every card. At start, when another project opens, and when the screen configuration changes, the project's entry for the current key is applied; without one (another desk, a missing screen, another resolution or monitor: all other keys), the default state applies, automatically and without a prompt. A window of an entry is kept inside its screen's visible area (moved, and made smaller only when larger than it; the visible area is the screen less 40 points of menu bar, since tao reports no visible frame). **Window ▸ Reset Layout** applies the default state now and removes the current key's entry.
7. **Cards move between windows from their context menu** (see Refinements: first designed as drag and drop). The project's main panel, `ui/main.html` (or the generated one), stays the one source of its cards: a panel window shows the cards it holds, in its order; a main window's Panel tab shows every card, one held elsewhere as a placeholder. Cards are hidden, ordered and collapsed with CSS only, never moved in the DOM, so the panel file, its editor and `panel.written` see the panel as written. A card's id is its `id` attribute when it has one, else the slug of its first heading (`kick`, `output`; the second card of the same heading `kick-2`), else `card` (`ui/app/lib/cards.js`); giving cards an `id` keeps their place across a renamed heading. Splitting a panel over several windows is therefore only this layout; a project that wants several panels of its own writes several HTML files in `ui/` (text is the truth), which `signal ui` serves under `/project/`. The Setup keeps only the default main window's size (`[window]`); the windows are not machine settings.
8. **A window's page and the app** talk through wry's IPC (`window.ipc.postMessage`) and window events: the app tells each page what it shows (`signal-window`), a page says what the person chose (`card.move`, `card.order`, `window.show`, `window.fit`; `ui-controls.md` "Cards across windows"). These are not UI protocol messages.

## Refinements
- **2026-10-22, the owner on the Mac (three 3840×2160 screens):** "Window dragging isn't right. First, the new window is filled too — maybe it should be empty by default. The grabbable area is not obvious... it worked half-heartedly on the first test, then suddenly almost every instrument's surface disappeared." Decided (the operator): a panel window shows nothing until the app says which cards it holds (it was the whole panel until then), and an empty one says to drag a grip there; every card gets a visible **grip** along its top edge, the only place a move starts, with a label following the pointer while dragged and an insertion marker in the window under it (`card.over`, `signal-card-over`), Escape cancelling; a click or right click on the grip opens a menu (Move to each other window, to a new window, back to the main window) as a way that needs no drag; a main window shows a card held elsewhere as a placeholder in its place ("— in Panel window 1 (screen 2)", Show, Bring back), so nothing disappears; a window opened by a drop takes the card's size, its corner at the pointer and wholly on that screen; New Panel Window opens at 600×400 points centred on the front window's screen; a panel window whose cards change fits its height until the person resizes it. The owner's file put a 480×360 window at y = 1740 of a 2160-point screen: that is a drop near the bottom (tao's y runs down from the main screen's top, for windows and pointer alike), not a flipped axis; tested with the three-screen key (`layout.rs`, `three_screens_side_by_side`). The grips and placeholders are an overlay outside `<signal-panel>`, since the panel editor matches its tree to the panel's children by position.

- **2026-10-22, owner: "OK, not drag and drop — the panel elements should be movable from the context menu."** The drag of the refinement above (the grip bar, the pointer capture, the label, `card.drag`, `card.over`, `signal-card-over`, `card.cancel`, `signal-card-drop`, `card.place`, the insertion marker and a new window where the drop landed) is removed. A right click on a card (its background or heading; a bound control keeps its own menu, a text field the system's, Edit layout its own interactions) opens its menu: Move to each other window by its name, Move to new panel window (the card's size, centred on this window's screen), in a panel window Bring back to main window, and Move up / Move down where the window has other cards (`card.order`), in place of reordering by dragging. In a main window these items come first in the app's own menu; in a panel window the same menu element opens in the page (its look and keys). The empty panel window's hint says to right-click an instrument and choose Move to; the placeholders, closing that gives cards back, the window names and the height fit stay.

## Alternatives considered
- **The layout in the Setup** (the machine file): first designed so, since windows are not what a project means; replaced by the owner's request that the layout may be part of the project behind a key that describes the screens. Keyed by the screens, it never carries a wrong arrangement to another desk, and it travels with a project between identical desks.
- **Restoring a window onto the main screen when its screen is gone:** guesses an arrangement the person never made; a different configuration falls back to the default state by construction instead.
- **Several panel pages per window as the means to split a panel:** needs the project to be rewritten into several files to move one card; cards moved between windows keep one panel file.
- **Drag and drop:** HTML5 drag and drop across WebViews is blocked by wry's file-drop handler, which takes every drag entering a WebView, and cannot open a window where the drop lands; a drag carried by the app (built, then removed) was found hard to grab and to follow on the owner's screens; the context menu needs neither.

## Consequences
- Moving a window or a card writes `ui/windows.toml`, so a `.signal` project shows "Edited" and asks "Save changes?" as a moved schematic box does.
- A write of `ui/windows.toml` changes the folder's state, so a stopped project's cached structure is built again at the next `graph` (no reload, no push).
- Not verified here (headless): the windows on real screens, the card menu in the WebViews (beside the app's own menu and the controls' menus), the screen change while running, and full screen. For the operator's review on the device.
- Tests: `crates/signal-app/src/layout.rs` (the key, the default state, placement inside the visible area, recording, card moves and Move up / down, three screens side by side, `ui/windows.toml` per key and Reset), `crates/signal-app/src/window.rs` (the Window menu, every view a page of the same server, titles), `crates/signal-app/tests/server.rs` (several clients, the write taken as seen, the refusals), `ui/app/lib/cards.test.js` (card ids, what each window shows, the card menu and what it sends, which right clicks are the card's).

**2026-10-30, amended by ADR 0047 §3.** A panel window shows its cards at their places on the plate, cropped to their bounding box and scaled to fit; `card.order` and Move up / Move down are removed (order on the plate is place); `ui/windows.toml` keeps `cards` as membership only. A held card keeps its whole box under its placeholder.
