# ADR 0036: Joining the device without a glitch

- **Status:** Accepted (operator decision on the owner's report of 2026-10-23; §1 by the owner's decision of the same day: "the global clock is given by the audio interface, and everything should run on it"). Amends ADR 0011 (the driver opens the device at the project's rate "with a fixed buffer"), retires the rate switch of e4a415e, and adds an `unsafe` exception (AGENTS.md rule 9, ADR 0017's rules), approved by the owner on 2026-10-23: "I approve. signal-audio/src/device_props.rs may be added to AGENTS.md rule 9's permitted files containing unsafe code, on the basis of ADR 0036."
- **Date:** 2026-10-23

## Context
The owner's report: when something plays in Chrome and another window starts with sound, a small jump is heard. That is a weak point of CoreAudio in general; in Signal, a new instance or a newly joining project must start without one.

A CoreAudio device's I/O cycle and its nominal sample rate are shared by every process that plays on it. Before this ADR, `CoreAudioDriver::start`:

- requested the Setup's buffer (`buffer = 128`) through cpal's `BufferSize::Fixed`, which sets `kAudioDevicePropertyBufferFrameSize` on the device while the stream is built;
- since e4a415e, switched the nominal rate to the project's with a throw-away stream before the stream that plays (`switch_rate`), so that the change's notification reaches no playing stream;
- started at full level and stopped at full level: a step at either edge.

Measured on BlackHole 64ch (2026-10-23, silent scratch copies of `projects/pulse`, `audio_out` gain 0, `signal play … --seconds 2` as client A, a second `signal play` as client B 0.6 s later): with the build before this ADR, B at 96 kHz while A played at 48 kHz switched the device to 96 kHz, and A's stream stopped ("the device 'BlackHole 64ch' changed its sample rate to 96000 Hz while playing at 48000 Hz"). That is a fact for the rate. For the buffer, B requested 128 frames and ran 376 callbacks in 1 s (128 frames each) while A kept 512-frame callbacks; a third process read `kAudioDevicePropertyBufferFrameSize` as 512 throughout, so the property as another process reads it is per client and does not show B's request. That a smaller request changes the I/O cycle of a hardware device for every client, which the others hear as a jump, is an assumption (the HAL serves the smallest buffer any client asks for), not measured here: BlackHole is virtual and cannot be heard, and the owner's devices are not reconfigured for a test.

## Decision
1. **The device's clock is the run's** (the owner's decision). A live run is prepared at the rate the output device runs at (`signal_audio::live_rate`: its nominal rate, else its stream format's, else the project's when neither reads), and Signal never switches a device's nominal rate, whether or not another client uses it. `switch_rate` and its throw-away stream (e4a415e) are removed. A project's `sample_rate` is the rate of its offline renders and replays and the rate it is written for, a preference, not a requirement for live play: when the output runs at another rate, the run plays at the output's, with a notice in plain words ("'SSL 2+ Mk II' runs at 44100 Hz; studio is written for 48000 Hz and plays at 44100 Hz": `app`'s `notes` in Signal.app, stderr in `signal play`). Nothing in a plan depends on the project's rate: primitives read the rate from `prepare` (`EngineConfig::sample_rate`, built at the live rate), and the session recorder records the rate played, which its replay runs at, so the replay is exact. A device whose rate changed between the open and the start is refused (`rate_moved`), never switched; one whose rate changes while it plays stops the run (the plain-words fault, as before), and Signal.app's wait for the device plays again at the new rate once the output is there. The input (metered only) is opened at its own rate.
2. **A device that runs for another client is joined as it is.** Before a stream is built (output and input), the driver reads the device's shared state: `kAudioDevicePropertyDeviceIsRunningSomewhere`, `kAudioDevicePropertyDeviceIsRunning` (this process), `kAudioDevicePropertyBufferFrameSize` and `kAudioDevicePropertyNominalSampleRate`. `plan_join` (`crates/signal-audio/src/join.rs`, plain code, tested with mocked states) decides the buffer:
   - **running somewhere** (another app, or Signal's own input on the same device): no buffer is set (`BufferSize::Default`; callbacks hold the device's current buffer, which the callback already runs in pieces up to `max_frames`);
   - **Signal would be the only client**, or **the state does not read:** the Setup's buffer is requested, as before.
   The engine is sized for the period the device will run at (`CoreAudioDriver::period`, `output_period`): block capacity, latency (two periods) and the hang period follow it, and Signal.app's status line and `signal play` show it (`signal play --json`'s `device`: `shared`, `period`, `set_buffer`).
3. **`buffer = "device"`** in the Setup never requests a buffer, even when Signal is alone (`docs/project-format.md` "Setup"). The interface dialog does not offer it yet (follow-up); it shows the default number, and choosing another number there replaces `"device"`.
4. **The output fades** (output policy, ADR 0022): when its stream starts, the CoreAudio driver asks the Runner to ramp the device output in over 10 ms (raised cosine, `signal_output::fade`), and on a deliberate stop the callback ramps it out over 10 ms, the Runner running on, before handing it back and the stream stops. The fade is applied in `signal_output::Runner::process` after the conversion and the ceiling, only when a driver asks: offline renders and the null driver never fade, so render hashes, goldens and the null-driver identity tests are unchanged. It allocates, locks and blocks nowhere (`crates/signal-audio/tests/no_allocation.rs` runs it). A stream the audio system stopped (a fault) has no callback left to fade in.
5. **The unsafe exception.** The reads need CoreAudio's C API, so `crates/signal-audio/src/device_props.rs` is the fourth module allowed `unsafe` code. It only **reads** properties (`AudioObjectGetPropertyData` into a local of the property's own type and size, used only on status 0 with the full size written); it never sets one. It declares `AudioStreamBasicDescription` itself (`PhysicalFormat`, `repr(C)`, size asserted at 40 bytes) for the measurement probe (`crates/signal-audio/tests/device_state.rs`, ignored by default). `crates/signal-engine/tests/unsafe_scope.rs` lists it and checks that every use there follows a `SAFETY:` comment and that it sets no property.

## Consequences
- Joining a device that another app plays on changes neither its buffer nor its rate; Signal plays at the device's buffer then (often 512 frames: more latency than the Setup's 128, and the status line says so).
- No live run switches a device's rate; before, the switch stopped the other client's stream (measured above for a second Signal). A project plays live at the device's rate, so it may sound at another rate than its renders (a primitive's output at 44.1 kHz is not its output at 48 kHz resampled); its replay runs at the rate played and is exact; the notice says so. Signal.app's own display of the project's rate (`signal-app`) is not changed here (follow-up: show the rate played).
- cpal still sets the device's physical format while it builds a stream when it finds a matching one that differs (`set_physical_format`, cpal 0.18.2). On BlackHole the physical format read the same before, during and after the runs above (the probe, 2026-10-23); on the owner's devices only the current formats were read, nothing was played. A device whose current physical format is not the first float format cpal finds remains a residual risk, outside Signal's code.
- **Residual risk, the rate (TOCTOU).** cpal 0.18.2 also sets the nominal rate while it builds a stream when the device's differs (`set_sample_rate`, `device.rs`). The driver checks the rate before the build, so this happens only if the rate changes between that check and the build; it reads the rate again after the build and refuses the start in plain words (`rate_moved`), but by then cpal may have switched the device. Closing it needs a cpal that does not set the rate, outside Signal's code.
- **The open decides the join once.** `CoreAudioDriver::open_with` reads the state and decides; the engine is sized for that period; `start` keeps to the decision and refuses in plain words when the device changed so that it no longer holds (another app started on it: Signal will not set its buffer; its buffer changed). A device another app left between the two is still joined as it is. A device that runs for this process (Signal's own stream, just stopped) is read again for up to 100 ms until it no longer does; measured on BlackHole, it reads stopped at once after `stop` (37 ms, the 10 ms fade included).
- **A flapping device.** Signal.app's wait for the device doubles its look interval with each retry in a row (1 to 16 s) and stops after 5, saying so; a retried run that played 30 s resets the count.
- A live edit of `sample_rate` is no longer refused: it changes the rate of the project's renders, never the running engine's.
- `kAudioDevicePropertyDeviceIsRunningSomewhere` is true for Signal's own input on the same device too; such a device is then also joined as it is.
- `setup.check` still checks that the output offers the project's rate (it lists what a render would need); a live run no longer needs it.
- Follow-ups: offer `"device"` in the interface dialog; report it in `setup.get` (the UI protocol still reports the number); show the rate played in Signal.app's window.
