# ADR 0027: The core set, the built-in library, and where algorithms stay native

- **Status:** Accepted (owner's request of 2026-10-17: "before we start, we should produce all the completely fundamental building elements from which these and more complex structures can be built… NI Reaktor's pattern: in Primary you can already build a lot, but still there came the core cell… a foundation, a built-in set in the application, from which everything can be built: hardware emulations, physical-world simulations, signal conversions, signal processing"; and the same day: "these core-cell-like things can be in Rust; I don't insist that they be visually editable; it's enough if a core cell module is a Rust source text", then "ok, let it be so"; design by the operator, delegated). Refines ADR 0001 (primitives and composites) and ADR 0005 (ports). Consistent with ADR 0010; supersedes nothing.
- **Date:** 2026-10-17

## Context
The owner's list (LFO shapes, envelopes, wavetable and FM oscillators, filters, effects, spectrum displays, new controls) needs a foundation first: a complete set of fundamental elements, built into the application, from which every module can be built. Reaktor's model is Primary modules over core cells, whose insides are atoms compiled into one piece of code. Signal's equivalent of an atom is a Rust primitive (ADR 0010); the owner does not require editing core cells visually.

Measured (operator, 2026-10-17, one Apple Silicon performance core, release build, `signal render` and `signal bench`; scripts and raw output in the M2.10 issue record):
- A primitive instance costs about **2.5 ns per frame** in block execution (chains of 100 to 4000 `std.add`, 48 and 96 kHz), and about **22 ns per frame** inside a one-sample feedback loop, whose members run at k = 1 (`docs/semantics.md` §13, `crates/signal-engine/src/units.rs`). One 1000-instance cycle on all cores measured 41 ns, slower than on one thread (unexplained).
- A fixed-coefficient TPT state-variable filter built from today's std primitives (6 instances, 5 in one loop) is **bit-exact** with `std.svf` over 10 s of noise, and costs 119 ns per frame against 12 ns (9.8×). A modulated one would need about 24 instances (about 28×, estimated).
- A fused kernel (the same filter as a 12-operation register-file interpreter, outside the engine) costs about 20 ns per frame, bit-identical.
- Determinism held in every case: the same hash across k = 1, 64, 256 and 1 or 18 threads.

Two traps found: canonical fan-in order is by source address, so a sum inside a composite can associate differently depending on addresses outside it; and constants computed outside the engine's `libm` (by hand, in TOML) can differ by one ulp.

Missing from std today: division and the transcendental functions, comparison and selection, a sample-rate source, memory, value events from signals, triggered randomness, vector utilities.

## Decision
1. **The core set is a deliberately complete, minimal set of Rust primitives in `std.*`**, marked by a new descriptor field `category` (`core`, `generator`, `filter`, `envelope`, `delay`, `physical`, `event`, `visual`, `io`), which groups the palette and `signal modules --category`. Not `core.*`: that prefix is the converters' (`docs/module-contract.md`), and "core" already names the domain-free crates. The existing std arithmetic is part of the set and keeps its names. Every core primitive:
   - passes the contract suite and states its formula in its rustdoc;
   - is total: finite in, finite out (`div` by 0 gives 0, `sqrt` of x < 0 gives 0, `log` of x ≤ 0 gives the log of the smallest normal, `pow` defined everywhere), each case documented and tested; and within the engine's magnitude bound (`docs/semantics.md` §7): results are clamped to ±1e6, so a core primitive never faults on its own (M2.10-1 review, operator decision 2026-10-17);
   - takes **ordered operands** (`a`, `b`, …) wherever association matters, so a result never depends on fan-in address order;
   - computes transcendental functions with `libm` (ADR 0007).

   | Group | Primitives (✓ exists) |
   |---|---|
   | Arithmetic | add✓ sub✓ mul✓ div neg abs✓ min✓ max✓ clamp✓ scale✓ mod (floored) fract floor round (half-even) sign |
   | Functions | sqrt exp log pow sin cos tan tanh atan2 (radians), sin_cycles (cycles, the oscillator convention) |
   | Constants and rate | const, sample_rate (sr and 1/sr), frames (frames run: lo and hi, count = hi·1e6 + lo) |
   | Compare and select | compare (lt, le, eq, ge, gt, ne → gate), select (gate > 0 ? a : b), and, or, not |
   | State (hides the loop) | unit_delay✓ delay✓ phasor (wrap, reset), counter (triggers → count, modulo, reset, wrap trigger), integrator (TPT step, reset), lag✓ onepole✓ |
   | Memory | buffer (N frames, N fixed per instance, allocated in prepare; write index, value, gate; R read taps; interpolation none, linear, Hermite; read-after-write within a frame defined), table (read-only, from parameters or a project asset; interpolated) |
   | Events | sample_hold✓ latch (a Set value held as a signal) to_events (a signal → Set on change or trigger) edge✓ route (events to a or b by a gate) counter clock_div✓; merge is event fan-in (ADR 0016 §3) |
   | Randomness | noise✓, random (trigger → a uniform value held; the instance's seeded stream, ADR 0008) |
   | Vectors | pack, unpack, index (fractional), reduce (sum, min, max, mean, in element order), elementwise add and mul; widths registered on demand |

2. **Granularity follows the measurement.** An acyclic node costs about 2.5 ns per frame, so a core primitive is one formula term. A node in a loop costs about 22 ns, so every common one-sample recurrence is one stateful primitive (phasor, counter, integrator, smoother, delay), and library composites are written acyclic where they can be. A composite meant for polyphonic use that closes a loop over more than about 8 nodes is a sign that its algorithm belongs native (3).

3. **What stays native Rust** ("a core cell is Rust source text"): algorithms whose per-sample feedback crosses many terms are std primitives: filters with modulated coefficients (state-variable, ladder, biquad, allpass, comb), band-limited oscillators (polyBLEP, wavetables with mip levels, FM operators with feedback), interpolated delays and reverb cores (FDN), physical models, envelopes with exact timing, FFT and spectra, nonlinear zero-delay-feedback solvers. Same contract, same suite.

4. **The built-in library: composites shipped with Signal.** A module reference `lib.<name>` resolves to a composite shipped in a new crate `signal-lib` (TOML embedded with `include_str!`), a third form beside `std.*` primitives and bare project composites (`project-format.md` §4). The registry refuses `lib.` names; a project composite may not shadow a library one. They are ordinary composites (ADR 0010: no logic in composites), listed by `signal modules`, read-only, and `signal vendor lib.<name>` copies one into the project's `composites/`, where it is the project's own text (ADR 0009).
   - **Versioning:** the library is the app's MAJOR.MINOR. A change of a composite's output is a new name or a MINOR change with a changelog entry; names are never reused; a removed one warns for one MINOR first. The render manifest lists every library composite used with its hash (ADR 0008); a `.signal` file records the library version (ADR 0025).
   - **Validation:** every library composite with a native counterpart is rendered against it on the same stimulus: bit-exact, or within a stated, measured tolerance; the cost ratio is recorded in `docs/benchmarks.md`. Native primitives remain as references and as the fast path.

   **Note (2026-10-17, M2.10-3): how §4 was built, and what it refines.**
   - **Where resolution lives.** `signal-lib` holds the text only (`lib/<name>.toml`, its hash, `VERSION`); `signal-project` resolves `lib.` references, reads them by the composite rules and hands them to `build_plan` as definitions named `lib.<name>`, so the graph and the engine are unchanged. The core only reserves the `lib.` prefix in the registry, as it reserves `core.`.
   - **Shadowing.** "A project composite may not shadow a library one" is read as: a project composite named `lib.<name>` is refused with an error naming the library composite, and so is a direct reference to `lib.<name>` (in `project.toml` or a project composite) in a project that also has a composite `<name>`. A project composite `<name>` beside the library's `lib.<name>` is otherwise allowed: `signal vendor` writes exactly that file, and a later library that adds `lib.<name>` must not break a project that already owns `<name>`. References inside library composites do not count, so vendoring one dependency alone keeps the project loading.
   - **Category and description.** A composite file may declare `category` and `description` in `[composite]`; a library composite must. The category is checked when the plan is built against the categories the registry's types carry (the vocabulary is `signal_std::category`'s, never `signal-project`'s, AGENTS.md rule 1), so a registry without a type in some group would refuse that group; `crates/signal-lib/tests/library.rs` checks every library category against `signal_std::category::ALL`.
   - **Cycles** among library composites are refused when a plan is built (the graph's recursive-composite error), and a test plans every shipped composite on its own; there is no build script.
   - **Provenance.** The manifest's `library_composite_hashes` lists the library composites the plan instantiates, absent when none, so renders without them keep their manifests and goldens byte for byte. A `.signal` archive records the library version in the zip comment (`signal-library <MAJOR.MINOR>`), not as an entry: an archive holds only project files (ADR 0025). A session records `library_version` and the hashes of the library composites of every plan version (the union), which `signal replay` compares with its own library's, warning on a difference.
   - **Versioning in practice.** `crates/signal-lib/tests/pinned.rs` pins each composite's render on a fixed stimulus long enough for its whole signal path (`lfo_shapes` once per shape, every output), and fails on a changed hash until `tests/pinned.toml` and a `CHANGELOG.md` entry under the current `## MAJOR.MINOR` naming the composite with the new hash agree; earlier sections are history, frozen by their hashes in `tests/released.toml`.

   **Note (2026-10-18, M2.10-4): the validation suite, and the cost of cycle units.**
   - **The pairs.** Seven std types are rebuilt from core primitives as library composites (`lib.svf_core`, `lib.onepole_core`, `lib.lag_core`, `lib.adsr_core`, `lib.osc_core`, `lib.delay_core`, `lib.tanh_shaper_core`), listed in `signal_lib::VALIDATION` with their native types and rendered against them by `crates/signal-lib/tests/validation.rs` (noise, saw sweep, impulses, parameter steps, audio-rate modulation; 48 and 96 kHz). Bit-exact: the state-variable filter (fixed and audio-rate modulated cutoff, every output), the one-pole, the oscillator's sine, and the delay at whole-frame delays. Within a stated tolerance: the lag and the envelope (1e-9), the delay at fractional delays (1e-9 times the input's largest magnitude, the interpolation position's rounding times the signal's slope, measured up to 3.4e-10 of it with a 959 940-frame delay past 10⁶ frames; between 1 and 2 frames a documented difference, the native's causal fallback), the shaper (no ADAA; 1e-9 + 0.035·Δu² per frame, the midpoint rule's curvature term, a meaningful comparison at low drive only). The reasons are in each composite's file and in `docs/benchmarks.md` ("Validation pairs"), with the costs. They are library composites, read-only and listed by `signal modules` with `"reference_for": "std.<type>"` (operator's decisions at the M2.10-4 review: the UI's `modules` reply now lists every library composite too, so the schematic palette shows them under `library` and adds them by a patch, and puts the references in their own group `reference`, last and closed; opening a library composite's inside stays for a later issue), but references rather than building blocks: the library demo leaves them out (M2.10-3's "the demo uses every library composite" now excludes `VALIDATION`), and the native types stay the fast path.
   - **What the suite showed about composites.** A composite's intermediates are signals, so the engine's ±1e6 bound (`docs/semantics.md` §7) applies inside it where a native keeps unbounded internal state: τ in frames, ms·sr and frame counts cannot be signals beyond 10⁶, so the lag and the envelope compute their coefficients in another order (the reason for their tolerance; the envelope's attack length, where attack·sr also passes 10⁶, is computed scaled by 2⁻¹⁶ and so rounds exactly as the native's), and the envelope's attack and the delay's length are capped at about 10⁶ frames, which matters only above 16.7 kHz (attack) or 99 999 Hz (delay). The filters cap their cutoff at 318 309 Hz so π·fc stays bounded (acting only above 649 610 Hz), and `std.sample_rate` itself faults above 999 999 Hz. An intermediate beyond ±1e6 faults where it is a `std.add` or `std.mul`, and is clamped silently where it is one of the M2.10-1 types that bound their output (`std.sub`, `std.div`, `std.tan`, `std.exp`, `std.scale`, `std.clamp`), so near the bound a composite faults or clamps where its native's unbounded internal state does neither: the filters, the lag, the oscillator's phase input and the shaper take an input up to 10⁴ without a fault (and agree with their natives there as stated), the envelope and the delay up to 10⁶ like their natives (measured: `HEADROOM` in the suite). None of this changes the decision; it is what "written acyclic where they can be" (§2) costs when they cannot.
   - **The cost of cycle units** (Alternatives, "A cheaper path"). Measured on one host, release build, one thread (`docs/benchmarks.md`, "The cost of cycle units"): a sampling profile (`sample`) of a 1000-node loop of `std.add` and instrumented section timing (a scratch-only patch, `docs/measurements/m2.10-4-cycle-timing.patch`) put the per-node, per-frame cost of a cycle member (about 24 ns) in the engine's fixed per-call work: the fault guard and output commit, the input and parameter gather, the call setup and the out-of-line `Inputs`/`Outputs` accessors; the primitive's own arithmetic is a few percent. Nothing in it is specific to cycles: an acyclic chain rendered at `--block 1` costs the same per node as a loop, and the cycle unit's own per-frame loop is under 1 % of the profile; a loop node costs what any node costs at *k* = 1, where a block of 256 frames shares that work (about 2.5 ns). No change was made: each candidate (below) touches the per-call path every render goes through, so its bit-identity needs the full oracle and determinism matrix, and none was proven within this issue. The options, for a later issue that designs one: a one-frame specialisation of the call path for cycle members (`commit`'s and `gather`'s general per-frame loops, bounds-checked row writes, fade and event handling run here for a single frame, and the gather's per-parameter staged-event and ramp work could be skipped when none is pending); making the `Inputs`/`Outputs` accessors inlinable across crates; and, beyond the engine's per-call model, the fused core-composite compiler above. Revisit as the Alternatives say.

5. **Rates for core math** (decided in the issue that builds it): core arithmetic, function, compare and select types become rate-generic, an instance key `rate = <divisor>` choosing the divisor, so a coefficient graph can run at control rate with the converters inserted as today, Signal's substitute for Reaktor's compute-on-change. If that contract change is refused there, coefficient graphs run at divisor 1 at the measured cost.

   **Note (2026-10-17, M2.10-1): not done in M2.10-1.** The core types built there (arithmetic, functions, constants and rate, compare and select) are at divisor 1 only, and coefficient graphs run at divisor 1 at the measured cost. The reasons: (a) a type's rate is fixed by its `'static` descriptor (`ModuleDescriptor::rate`, `docs/semantics.md` §16), so a per-instance divisor needs a descriptor made per type and divisor, as the converters' are, in the core registry; (b) `rate` cannot simply become an instance key: instance keys other than `module` and `gpu` are parameters (`project-format.md` §4) and `std.particles` already has a parameter named `rate`, so it would need a reserved key or another spelling, with the format, the schema, patch ops and the panel's file writer; (c) the swap survival rule ("same type and descriptor", §12) and the oracle's independent implementation of §16 would have to learn per-instance rates for the oracle's bit-for-bit parity to hold; (d) nothing needs it yet: no library coefficient graph exists, and an acyclic node costs about 2.5 ns per frame at divisor 1 (Context), so doing it before a measured need would put the renders' bit-identity at risk across the graph compiler for no gain. **Revisit** when the first library composite's coefficient graph measurably misses its budget (`docs/benchmarks.md`); a separate issue then designs the per-instance rate (key spelling, descriptor synthesis, survival rule, oracle parity).

   **Note (2026-10-17, M2.10-2): core set II, how §1's memory and vectors were built.**
   - **`buffer`: capacity in the type, `size` live.** §1's "N fixed per instance, allocated in prepare" is met by the allocation, which is fixed per type, not by N, which is live. `prepare` receives no parameter values (`PrepareContext`: sample rate, block capacity, random stream, lent resource, generation), and a swap keeps an instance whenever its type and descriptor are unchanged, a live edit of a parameter being a `set` to the kept instance. So the memory `prepare` allocates cannot depend on `size`. It is the type's: `std.buffer1k`, `std.buffer64k`, `std.buffer1m` (2¹⁰, 2¹⁶, 2²⁰ frames; `signal_std::BUFFER_CAPACITIES`), one `'static` descriptor per capacity, as the vector widths are a type per width. `prepare` allocates that capacity and writes every element, so no page is first touched on the audio thread. `size` (1 … capacity) is read every frame like any parameter: a live edit, a `set` or a modulation takes effect on its frame, and positions are taken modulo the current size (the buffer holds none of its own; contents beyond it are kept, hidden until it grows). **Why** (review, 2026-10-17): the first delivery, a single `std.buffer` that allocated 2²⁰ frames (8 MiB) per instance whatever its `size`, read `size` once on the instance's first frame and kept it, so a live edit of `size` on a surviving instance was silently ignored, and the running state no longer matched the file (AGENTS.md rule 4); its zeroed pages were also first touched on the audio thread. That `std.buffer` was never released and is removed, not kept as an alias. Set aside again: a contract change giving `prepare` the instance's initial parameters with a survival rule that compares them (engine, oracle, graph and diff, the kind of change §5's note declined).
   - **`table` from parameters only.** Its values are the instance's parameters `v0…`; the project-asset route is not built: the loader reads no file besides `project.toml` and `composites/`, a `.signal` archive keeps no other folder, and an instance key that names a file is not a number (`project-format.md` §1, §4, §10; ADR 0025). An asset route needs a project-format change of its own.
   - **Widths.** A vector width is part of a `'static` descriptor, so each vector operation and the table are one type per width (`std.pack4`, `std.table16`), at the widths of `signal_std::VECTOR_WIDTHS` (2, 4, 8, 16, 64, 256, 1024), made once per process like the converters' descriptors. A width is added to that list when something needs it (`module-contract.md`, "The standard library").
   - **Categories.** Every M2.10-2 type is in `core`; the earlier state and event types (`unit_delay`, `delay`, `lag`, `onepole`, `sample_hold`, `edge`, `clock_div`) keep the groups M2.10-1 gave them.

6. **UI:** the palette groups by `category` (and library, project); a library composite opens by semantic zoom (ADR 0026), read-only, with "vendor to edit"; a native primitive shows its formula when selected.

## Alternatives considered
- **A fused core-composite compiler** (a composite compiled at plan time into one kernel: SSA over a register file, interpreted, later JIT). It would bring a loop composite from about 10× native to about 2× (measured, micro-benchmark). It is not a DSL in ADR 0010's sense (the text is the same TOML), but it is a second execution engine whose bit-identity with the per-frame reference, faults, state carried across swaps (ADR 0006) and trust boundary would all need proving; it would supersede parts of ADR 0002 and 0016. **Revisit** when a project from the owner's list misses its budget because of loop-heavy library composites with no native counterpart, or a library composite in polyphonic use exceeds 10× its native reference.
- **A cheaper path for cycle units in the engine** (the same semantics, less per-call cost at k = 1): compatible with this decision; measured first (M2.10).
- **A `core.*` namespace:** rejected (the converters').
- **Visual editing inside core cells:** not required by the owner.
- **Per-project Rust modules compiled by the app:** a Rust toolchain at run time, `unsafe` dylib loading without a stable ABI, and native code that can hang or cause undefined behaviour inside the process. WASM (wasmtime) would sandbox it and bound its time, at about 1.5–3× native and a large dependency. Either needs its own ADR, superseding ADR 0010's "no scripting yet". Not now.

## Consequences
- About 30 new std primitives with contract tests, and a `category` on every std type.
- A new crate `signal-lib`, a third module-reference form, manifest provenance for library composites, `signal vendor`.
- A validation suite pairing library composites with native references, and costs predictable from the measured overheads (about 2.5 ns per acyclic node, 22 ns per loop node).
- New algorithms with dense per-sample feedback still need a Rust primitive and a rebuild (ADR 0010 unchanged).
