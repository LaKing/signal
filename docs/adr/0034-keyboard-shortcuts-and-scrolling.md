# ADR 0034: Keyboard shortcuts and scrolling

- **Status:** Accepted (owner's request of 2026-10-23, translated: "Scrolling is confusing when there is a piano roll and a full window, and the key combinations aren't clear either — e.g. Page Up / Page Down don't navigate the view. Let's make a keyboard shortcuts config file and an editor for it, customisable in settings/preferences."; design by the operator, delegated)
- **Date:** 2026-10-23

## Context
Every control handled its own keys with `event.key` comparisons spread over a dozen files (`ui/controls/*.js`, `ui/lib/*-model.js`, `schematic-view.js`, `panel-edit.js`, …), and the native menu's chords were characters in `crates/signal-app/src/window.rs`. Nothing listed them all, and none could be changed.

The wheel was taken by whatever was under the pointer: a knob or fader changed its value, the piano roll scrolled its grid, the step grid's level knobs changed their level, each calling `preventDefault`. Scrolling a panel stopped dead (or changed a parameter) as soon as the pointer crossed a control, and inside the piano roll the page never scrolled. Page Up and Page Down did nothing in Signal.app: the main window's tabs scroll a box inside the page (`.tab-scroll`) or a frame (the panel), never the document the browser scrolls, and a focused knob took them as large steps.

## Decision
1. **One keymap, as text.** `ui/lib/keys.default.js` is the built-in keymap and the single source: commands with stable ids (`view.page_down`, `schematic.fit`, `transport.restart`, `window.new_main`, `piano_roll.delete`, …), each with a label, its scope and zero or more chords. Scopes are `app` (the menu bar), `view` (the page), `text` and `menu` (conventions, fixed), and one per control (`slider`, `xy`, `button`, `toggle`, `meter`, `oscilloscope`, `value`, `piano_roll`, `step_grid`, `schematic`, `schematic_edit`, `palette`, `panel_edit`), each with a parent (`view`, whose parent is `app`). The pages (`ui/lib/keys.js`), the native menu (`signal-app`), the server's check of the person's file (`crates/signal-ui/src/keys.rs`) and the docs read it; no control compares `event.key` for a command any more. A command marked `fine` also takes Shift for a finer step (Shift stays the fine modifier, as before); a command marked `fixed` (the Edit menu's, Hide, Minimize, full screen; text fields' and menus' conventions) is listed, never rebound.
2. **Chords.** Modifiers `Ctrl`, `Alt`, `Shift`, `Cmd` (written in macOS order, ⌃⌥⇧⌘) and a key: a letter, a digit, one character, a named key (`PageDown`, `Space`, `Escape`, `F1`…`F20`, …) or `Wheel` for wheel gestures. A character is the one typed (`+`, never `Shift+=`): layouts differ (the owner's Hungarian one puts `0`, `+` and `/` elsewhere), and Shift with a character is refused with a reason. With ⌥, whose characters on a Mac are others (`⌥,` types `≤`), the key's code decides. Outside a Mac, Ctrl acts as Cmd.
3. **Precedence.** An open text field keeps every key; then the focused control's scope; then the view (`view.*`: the page); then the window (nothing yet); then the app's menu. In the DOM this is the event's own path: a control handles its scope's chords and stops the event, and what it does not handle reaches the document's listener (`ui/controls/keyboard.js`). A child scope's chord that a parent also has is the child's while the control has the focus: a focused slider keeps Page Up and Page Down for large steps (the ARIA slider convention), a focused piano roll uses them to scroll its keys and the schematic to pan.
4. **The view's keys.** Page Up, Page Down, Space and Shift+Space, Home and End (and ⌘↑, ⌘↓, ↑, ↓) scroll the scrolling box around the focus, else the page's view: in Signal.app's main window the shown tab, or the panel frame's page, which the app registers (`setViewScroller`). A focused toggle no longer takes Page Up, Page Down, Home and End (it is no slider): there they scroll the page.
5. **Who takes the wheel.** The wheel scrolls the page by default. A control that scrolls, zooms or changes a value with the wheel takes it only when it **owns** it: it fills its window (the schematic: `<signal-schematic>` filling its tab or window; any control covering most of the window, or with `wheel="own"`; `wheel="page"` never), it has the focus (a click or Tab, until the focus leaves or **Escape**), or the **wheel modifier** is held. The modifier is the command `view.wheel_inside`, **⌥ by default**: Ctrl+wheel is what a trackpad pinch sends (it zooms), Shift+wheel is a horizontal scroll on a Mac with a mouse, and ⌘ is the menus' modifier and the piano roll's zoom; ⌥ alone was free. The modifier only takes the wheel: it is left out before a control's wheel chord is looked up, so ⌥⌘+wheel over a piano roll zooms as ⌘+wheel does once it is clicked, and a wheel chord holding it is reported as a conflict. The piano roll's zoom of the keys moved from ⌥+wheel to ⇧⌘+wheel for this.
6. **No scroll chaining.** A gesture (wheel events without a pause of 300 ms; a trackpad's momentum included) is decided once, by its first event, over the whole control (the document's capture listener, `registerWheel`), and keeps going where it started (`WheelLatch`, `ui/lib/wheel.js`): scrolling the page over a focused piano roll goes on scrolling the page, and a gesture a control took never scrolls the page, even when the pointer leaves it, crosses a part of it without a wheel use, or the control reaches its end. Values and zooms follow the vertical travel only: a sideways trackpad swipe changes nothing (Shift+wheel's horizontal delta counts).
7. **A hint.** When a gesture starts over a control that does not take it, a one-line hint appears by the pointer for 1.4 s: "Click to use the wheel here, or hold ⌥" (the modifier from the keymap). It is fixed-position and takes no pointer, so the layout never moves; a page scroll passing over controls shows none, nor does a gesture starting within a second of one of the page's (a mouse's slow notches). The fader, knob, piano roll and step grid take `wheel` as a panel attribute.
8. **The person's overrides: `keys.toml`.** A machine's preference, never a project's: beside the Setup file (`~/Library/Application Support/Signal/keys.toml`; with `--setup` or `SIGNAL_SETUP`, beside that file). It holds only overrides, as TOML, one table per id's first part: `[view]` `page_down = ["PageDown", "Space"]`, `[]` to unbind (a quoted `"view.page_down" = […]` also reads). Reading never fails: an unknown command, a fixed one, a chord that does not parse or of the wrong kind (a key for a wheel command), and a wheel modifier without a modifier are reported with the file's line and column and left out; a file that is not TOML or of another version is reported and the built-in keys are used. Conflicts are reported, located at the override that made them: two commands of one scope on a chord (fixed commands first, then the built-in order, keep it), a scope's chord hiding its parent's where the built-in keymap does not, and a wheel chord holding the wheel modifier. Signal.app shows the problems as the toolbar's notice and in Settings; `signal ui` and the app also print them.
9. **Written as text, watched.** Settings writes each change at once with `toml_edit` (the file's comments and other entries kept), atomically (a temporary file, synced, renamed); an override equal to the built-in chords is removed, so the file holds only what differs. The server looks at the file every 250 ms; an edit made elsewhere applies at once: every page is pushed the new keymap and the native menu's chords follow it.
10. **Protocol.** `keys.get`, `keys.set` (`command`, `keys`: a list of chords or null), `keys.reset` (one `command`, or every one) and the pushed `keys` (the overrides, the file's path, its problems and conflicts, `fallback`), in every mode of the server (`docs/ui-protocol.md` "Keyboard shortcuts"). The pages resolve the keymap themselves from the built-in file and the overrides, with the server's rules (both read `ui/lib/fixtures/keys-cases.json` in their tests).
11. **The native menu follows the file.** Each of Signal's own menu items is a keymap command marked `menu` (`MenuAction::command`): its first key chord is the item's (`muda`'s `KeyAccelerator`), set again whenever the keymap changes. A command's other chords are taken by the page and handed to the app (`menu.run`, wry's IPC). In a browser the page runs the app commands it can (Open, Save, Interface Setup, Restart, Settings, Keyboard Shortcuts).
12. **Settings and Help.** Signal ▸ **Settings…** (⌘,) opens a Settings window (its own, not part of a project's layout; a list of pages, Keyboard Shortcuts the first): every command by scope, searchable by name, id, chord or scope; its chords; Add… records a chord by pressing it (or a wheel gesture, for a wheel command; or typed, for Escape or Tab); × removes one; Reset puts a command back; Reset All… every one; a mark shows what differs from the built-in keymap; a chord another command holds is said inline with Replace, Add Anyway and Cancel, and the file's conflicts show on both commands. **Help ▸ Keyboard Shortcuts** (⌘/) opens the same page as a reference (read only, denser; Customize… switches). Interface Setup… moves from ⌘, to ⌥⌘, (macOS keeps ⌘, for Settings); New Main Window stays ⇧⌘N (ADR 0032). A menu command's chord needs Cmd, Ctrl or Alt, or a function key: the native menu would take a bare key from every text field (refused in the file, the protocol and the Settings page). In a text field, Cmd and Ctrl chords still reach the app's commands (the field commits first). `keys.set` and `keys.reset` refuse a file the server does not read (not TOML, another `version`), and write a linked `keys.toml` where the link points.

## Alternatives considered
- **The keymap in Rust, sent to the pages.** The pages need the keymap before any connection (the gallery, node tests, a page whose server has not answered yet) and the server needs it without a page; a JSON file both read (as `ui/lib/panel-whitelist.json` already is) is one source for both and for the docs.
- **The built-in keymap as TOML.** Readable with comments, but the pages would need a TOML reader before they could handle a key; JSON modules load synchronously in WebKit, Chrome and Node. The person's file is TOML, as the Setup is.
- **Keys in the Setup file.** The Setup is rewritten whole by its own code (`Setup::save`), which would lose comments; a separate file is edited by `toml_edit` and can be shared between machines on its own.
- **⌘ (or Ctrl) as the wheel modifier.** ⌘+wheel is a zoom (the piano roll's, and many apps'), and a trackpad pinch arrives as Ctrl+wheel, so either would take or zoom by accident. Shift+wheel is already a horizontal scroll.
- **A control takes the wheel when the page cannot scroll.** It would change with the window's size: the same gesture on the same knob would scroll or turn it depending on where the panel ends.
- **Hover to take the wheel (after a delay).** Unpredictable while scrolling through a long panel; a click is explicit and already focuses the control (the focus ring shows the owner).

## Consequences
- The wheel over a knob, fader or step-grid level no longer turns it until the control is clicked (or ⌥ is held); a scroll through a panel is never interrupted. Escape gives the wheel back.
- Page Up, Page Down, Space, Home and End scroll every tab and panel; inside a focused control they are the control's where it has them.
- Every shortcut is listed in one file and in Settings; the toggle's Page and Home/End keys and ⌥+wheel in the piano roll changed (above); ⌘, opens Settings, ⌥⌘, the interface setup.
- A broken `keys.toml` never stops Signal: the built-in keys work and the problem is shown.
- New commands are added to `ui/lib/keys.default.js` first; a control looks its commands up (`keyCommand`, `wheelCommand`) and never compares `event.key` for one.
